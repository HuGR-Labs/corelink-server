🔍 Entendendo o Workspaces — o que mais gera dúvida

O problema: montar um ambiente de dev numa máquina nova = git clone + npm install + build = 15–30 min, e nunca fica idêntico ("na minha máquina funciona").

A solução (a CLI clw): clw snapshot empacota o diretório inteiro num objeto content-addressed no CAS · clw hydrate materializa esse ambiente exato em segundos em qualquer lugar (dedup: o que já está no cache é pulado) · clw run memoiza comandos determinísticos — nunca rodam de novo se os inputs não mudaram.

⚠️ NÃO é Gitpod / Codespaces — não é uma VM ou IDE na nuvem. É o estado do seu workspace virando um arquivo teleportável. A máquina é descartável; o workspace vive no cache.

Use cases: máquina nova / formatou o Mac → ambiente idêntico em segundos · trocar de branch pesada sem rebuild · onboarding (dev novo hydrata o workspace exato do time) · CI runner efêmero hydrata o workspace quente → build começa hot · agente de IA hydrata um sandbox isolado e descartável.

Pin (o add-on pago) = manter o snapshot garantidamente quente → o hydrate é sempre instantâneo (vs. cold, que existe mas pode precisar remontar).

A diferença: Cache guarda pedaços (outputs). Workspaces guarda a árvore inteira. Runners é o compute que consome os dois.  A sinergia: o runner boota quente porque hydrata o workspace, que está quente porque o cache lembra os builds.  A independência: você não precisa de Runners pra assinar o Cache — por isso há planos standalone e bundle.
