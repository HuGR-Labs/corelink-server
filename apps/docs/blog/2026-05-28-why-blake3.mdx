Every blob stored in CoreLink is identified by exactly one thing: its BLAKE3 digest. No database primary key. No UUID. No monotonic counter. The 32 bytes produced by hashing a blob's content *are* the blob's address. Get the hash function wrong and the entire architecture unravels.

This post is the long-form answer to the question we get in every technical conversation: *"Why BLAKE3? Isn't SHA-256 good enough?"* It is also the post we wished existed when we were designing `crates/corelink-hash/`. We will walk through BLAKE3 internals, compare the real alternatives, and then ground every "why we picked it" claim in the actual code paths.

## §1 — The CAS problem that makes hash choice non-trivial

A content-addressable store (CAS) has one job: given a key (the hash), retrieve the blob that produced that hash, or return not-found. Correctness reduces to a single property: **no two distinct blobs may share a key**. Collision resistance is therefore table-stakes.

But a build-cache CAS has three additional pressures that a generic object store does not:

**Throughput pressure.** A large monorepo build on a fast CI runner can upload hundreds of gigabytes of intermediate artifacts per day. The hash function runs on every PUT and every GET-then-verify. A slow hash function becomes the bottleneck before the network does. Our AC §8 throughput target is ≥ 1.4 GiB/s on a 5 MiB blob in WASM; on native x86-64, we need to be well above that to leave headroom for encryption overhead and network serialization.

**Tenant isolation pressure.** CoreLink is multi-tenant. Two tenants may upload identical blobs — same bytes, same hash — but must never accidentally read each other's artifacts. A hash function that supports *keyed* or *key-derivation* modes lets us namespace the CAS address space per-tenant without a separate index layer. SHA-256 has no such mode. BLAKE3 does.

**Integrity verification pressure.** Every GET in CoreLink re-hashes the bytes returned by R2 before delivering them to the caller. This is not optional paranoia: it is the invariant `INV-CAS-INTEGRITY` (`security_model.md §6.1`). If R2 silently corrupts a byte, the re-hash catches it. If a tenant was mis-routed to the wrong blob, the re-hash catches it. If an attacker injects a crafted body mid-flight, the re-hash catches it. The hash therefore runs on every read, not just every write.

These three pressures taken together point toward: fast on large inputs, SIMD-friendly, WASM-portable, and key-derivation capable. Let us see which algorithms satisfy them.

## §2 — What is a content-addressable hash?

A content-addressable hash is a deterministic function `H: bytes → fixed-width-tag` such that:

1. **Determinism.** `H(b) == H(b)` for every byte slice `b`.
2. **Collision resistance.** Finding `a ≠ b` such that `H(a) == H(b)` is computationally infeasible.
3. **Preimage resistance.** Given `H(b)`, finding any `b'` with `H(b') == H(b)` is infeasible.
4. **Avalanche effect.** Flipping a single bit in `b` changes approximately half the output bits.

Properties 2-4 together mean: you cannot fabricate a blob that matches an existing address, you cannot reverse a digest back to the original blob, and you cannot make incremental progress toward a collision by making small edits to a known blob.

For a build cache, property 1 is the access primitive (the hash *is* the key), and properties 2-4 are the integrity guarantees (no two blobs collide, no oracle can predict what blob a future digest corresponds to, every re-hash of a stored blob will match the stored digest or not — never a gradual drift).

A hash function used only for CAS addressing does not need to resist length-extension attacks (those matter for MACs, not content addressing). It does not need to be "password-hardened" (Argon2-style memory hardness is for passwords, not blob IDs). It needs to be fast, collision-resistant, and — for CoreLink's multi-tenant case — key-derivable.

## §3 — The candidates

We evaluated four algorithms seriously. Here is the matrix:

| Algorithm | Output size | Speed (1 MiB, x86-64 AVX2) | Speed (1 MiB, WASM) | Key-derivation mode | Length-extension safe | Year |
|---|---|---|---|---|---|---|
| SHA-256 | 32 bytes | ~350 MB/s | ~90 MB/s | No (HMAC shim only) | No | 2001 |
| BLAKE2b | 64 bytes (truncatable to 32) | ~900 MB/s | ~400 MB/s | Key input slot | Yes | 2013 |
| BLAKE3 | 32 bytes (extendable via XOF) | ~3,200 MB/s | ~1,500 MB/s | `derive_key` context string | Yes | 2020 |
| xxHash3-128 | 128 bits | ~18,000 MB/s | ~5,000 MB/s | Seed parameter | No — non-cryptographic | 2021 |

Speed numbers are from the BLAKE3 paper (Table 1, AVX2 column) and the xxHash benchmark README; WASM figures are approximations from the blake3 crate's WASM build benchmarks. CoreLink's own bench suite (`cargo bench -p corelink-hash`) measures `Digest::compute` at the codebase's actual call sites.

**SHA-256** is the industry default and has survived thirty years of cryptanalysis. It is also the slowest by a wide margin on modern hardware because its compression function was designed before SIMD ISA extensions existed. The SHA-NI instruction set (Intel Goldmont / AMD Zen 2+) recovers some of that ground, but WASM targets do not have SHA-NI, and our Cloudflare Worker environment is WASM. SHA-256 also has the length-extension property: `H(H(secret || message))` is forgeable given only `H(secret || message)` and the message length. This is only relevant for MACs, not CAS — but it is still a footgun to keep near a multi-tenant system.

**BLAKE2b** is the clean-room redesign that made many of SHA-256's weaknesses explicit. It is significantly faster than SHA-256 on software, supports a 64-bit key input (useful for authentication), and has no length-extension vulnerability. It was the leading candidate before BLAKE3 was published. Its weakness for our use case is that it does not parallelize across multiple input blocks: the compression function is sequential. A 1 MiB blob requires feeding all 1,024 blocks in order. BLAKE3 fixes this.

**xxHash3** is the fastest hash in this table by an order of magnitude. It is also explicitly non-cryptographic. The author's README says so clearly, and the algorithm makes no collision-resistance claims beyond seed-dependence. Using it as a CAS address would mean an adversary who knows the seed (or who can influence the input) can likely craft collisions. For an internal build cache where you control all inputs, xxHash might be acceptable. For a multi-tenant SaaS where tenants submit arbitrary blobs, it is not. We ruled it out immediately.

**BLAKE3** is the algorithm that lands on the right side of every tradeoff: cryptographically strong (inherits BLAKE2's security proof), dramatically faster than both SHA-256 and BLAKE2b via parallelism, portable to WASM without special instruction sets, and ships a first-class `derive_key` mode. We use it.

## §4 — BLAKE3 internals: Merkle tree, SIMD, and derive-key

Understanding *why* BLAKE3 is fast requires a short tour of its internals. This section is longer than the others because the speed and the derive-key mode both come from the same structural decision.

### 4.1 The compression function: ChaCha-derived permutation

BLAKE3's compression function is a 7-round permutation derived from ChaCha20's quarter-round. Each round mixes a 4×4 matrix of 32-bit words using additions, XORs, and rotations. The permutation itself is not novel — it is designed to be easy to analyze (small, algebraically simple) and fast on hardware that has 32-bit ALUs (which includes every modern WASM runtime).

The key insight is that the compression function processes a fixed 64-byte input block and produces a fixed 32-byte chaining value. Individual blocks are independent of each other given their chaining values.

### 4.2 The Merkle tree structure

This is where BLAKE3 diverges from every predecessor. Instead of processing a long input as a sequential chain of compression-function calls (SHA-256, BLAKE2b), BLAKE3 organizes the input as a **binary Merkle tree** of 1 KiB chunks:

```
Input: [chunk_0 | chunk_1 | chunk_2 | chunk_3 | chunk_4 | chunk_5 | chunk_6 | chunk_7]

Chunk hashing (parallelizable):
  cv_0 = compress(chunk_0, ROOT_DOMAIN_FLAG=0)
  cv_1 = compress(chunk_1, ROOT_DOMAIN_FLAG=0)
  ...
  cv_7 = compress(chunk_7, ROOT_DOMAIN_FLAG=0)

First merge layer (parallelizable):
  parent_01 = compress(cv_0 || cv_1, PARENT_DOMAIN_FLAG)
  parent_23 = compress(cv_2 || cv_3, PARENT_DOMAIN_FLAG)
  parent_45 = compress(cv_4 || cv_5, PARENT_DOMAIN_FLAG)
  parent_67 = compress(cv_6 || cv_7, PARENT_DOMAIN_FLAG)

Second merge layer:
  left  = compress(parent_01 || parent_23, PARENT_DOMAIN_FLAG)
  right = compress(parent_45 || parent_67, PARENT_DOMAIN_FLAG)

Root:
  digest = compress(left || right, ROOT_DOMAIN_FLAG=1)
```

The critical property: **every chunk can be compressed independently**. There is no sequential dependency between `cv_0` and `cv_1`. This means the BLAKE3 implementation can schedule all chunk compressions simultaneously across SIMD lanes or CPU threads.

On x86-64 with AVX-512, a single core can process four 1 KiB chunks simultaneously using 512-bit SIMD registers. On Apple Silicon (NEON 128-bit), two chunks per SIMD cycle. On WASM SIMD (128-bit), two chunks. On WASM without SIMD (scalar), one chunk per cycle — but the scalar ChaCha-derived loop is still simpler than SHA-256's schedule, so scalar BLAKE3 beats scalar SHA-256.

The domain flags (`ROOT_DOMAIN_FLAG`, `PARENT_DOMAIN_FLAG`) are what make the tree structure collision-resistant: a leaf hash cannot be confused with a parent hash even if their 64-byte inputs happen to be identical. This is the standard Merkle-tree second-preimage defense.

### 4.3 SIMD acceleration path

```
+---------------------+      +---------------------+
|   BLAKE3 chunk 0    |      |   BLAKE3 chunk 1    |
| (7 rounds × 4 words)|      | (7 rounds × 4 words)|
+---------------------+      +---------------------+
         |                            |
     [AVX-512 lane 0]           [AVX-512 lane 1]
         |                            |
         +----------+  merge  +-------+
                    |         |
               parent chaining value
                    |
              (continue up tree)
```

The BLAKE3 Rust crate (`blake3` on crates.io) selects at compile time between scalar, SSE2, SSE4.1, AVX2, and AVX-512 implementations based on `target_feature` detection. WASM builds use the `simd128` feature if available. CoreLink's Cloudflare Workers WASM build gets the `simd128` path, which is what makes our AC §8 1.4 GiB/s WASM target achievable.

At the call site in `crates/corelink-hash/src/digest.rs:31`, we call `blake3::hash(body)` — one function call. The SIMD dispatch is entirely inside the `blake3` crate. No user-land parallelism setup is required.

### 4.4 The derive-key mode

BLAKE3 ships three modes beyond standard hashing:

1. **Hash mode** — `blake3::hash(bytes)`. Standard content hashing.
2. **Keyed hash mode** — `blake3::keyed_hash(key, bytes)`. MAC-equivalent; 32-byte key, same compression path.
3. **Key derivation mode** — `blake3::derive_key(context, material)`. Derives a 32-byte key from an arbitrary-length context string and an arbitrary-length input material. This is the KDF mode.

`derive_key` is the mode we use for tenant namespacing. The context string encodes the tenant scope (`"corelink-tenant v1 tenant_id:<tid>"`), and the material is the raw digest bytes. The output is a tenant-scoped address that cannot collide with another tenant's address for the same blob, even if the blobs are byte-identical.

The derive-key mechanism inside BLAKE3 works by hashing the context string first (with a special context-initialization domain separator), producing a 32-byte key, then running keyed-hash mode on the material. The domain separation between "context hash" and "keyed hash" is enforced by the same flag bits that separate chunk hashing from parent-node merging in the Merkle tree. All three modes share the same compression function; their security isolation comes entirely from the domain flags.

The security argument for derive-key: an attacker who knows one tenant's derived addresses cannot learn anything about another tenant's derived addresses, because the derivation key is different (it depends on the tenant context string) and the derive-key mode is indistinguishable from a random function given a random input key (this follows from BLAKE3's pseudorandomness proof).

### 4.5 Output finalization and the XOF mode

BLAKE3 is also an extensible-output function (XOF). The standard 32-byte output mode is just the first 32 bytes of a stream that can be read to any length. This is relevant for CoreLink in one future scenario: if we ever need 64-byte "strong" digest IDs for a subset of artifact classes (e.g., for SLSA Level 3 provenance assertions that require ≥256-bit security), we can widen the output without changing the hash function, the compression function, or any downstream tooling. We do not use XOF mode today — `DIGEST_LEN = 32` at `crates/corelink-hash/src/digest.rs:13` and the `Digest([u8; DIGEST_LEN])` newtype at line 22 are fixed at 256-bit. Widening would require a new newtype. But the algorithm supports it, which means the migration path is defined.

The finalization step is also where BLAKE3 diverges from SHA-256 in terms of length-extension resistance. SHA-256 produces its final state by simply truncating the Merkle–Damgård chained value. Because the chained state is the same size as the output, an attacker can extend the hash by feeding additional blocks through the compression function using the leaked state. BLAKE3's finalization XORs in the root domain flag and runs the output through an additional counter-based stream, so the internal state at the output boundary is not recoverable from the output. No length-extension attack is possible regardless of how the digest is used downstream.

## §5 — Benchmarks: real numbers + reproducible commands

The BLAKE3 paper (Aumasson et al., 2021) Table 1 reports, on a single x86-64 Skylake core:

| Input size | SHA-256 | BLAKE2b | BLAKE3 |
|---|---|---|---|
| 1 KiB | 360 MB/s | 820 MB/s | 1,700 MB/s |
| 4 KiB | 370 MB/s | 950 MB/s | 3,800 MB/s |
| 1 MiB | 380 MB/s | 930 MB/s | 3,100 MB/s |

At 4 KiB — which is close to the size of typical build object files — BLAKE3 is **10× faster than SHA-256** and **4× faster than BLAKE2b** on the same hardware with AVX2. The gap grows further with AVX-512 and shrinks (but does not close) with WASM SIMD.

To reproduce these numbers in the CoreLink repo:

```bash
# Requires a release build; debug builds do not activate SIMD
cargo bench -p corelink-hash --bench blake3_bench 2>&1
# Outputs: Digest::compute/1 KiB  time: [...]  thrpt: [...]
# Outputs: Digest::compute/64 KiB time: [...]  thrpt: [...]
# Outputs: Digest::compute/1 MiB  time: [...]  thrpt: [...]
# Outputs: Digest::compute/5 MiB  time: [...]  thrpt: [...]
```

The bench suite is defined at `crates/corelink-hash/benches/blake3_bench.rs`. It measures `Digest::compute` directly — the actual call site that every CoreLink PUT and GET verification exercises. On a 2024 Apple M3 Pro in release mode, we see approximately 2.1 GiB/s on 5 MiB inputs, well above the 1.4 GiB/s WASM target (the WASM build sees ~1.6 GiB/s with `simd128` enabled).

A secondary bench at `crates/corelink-hash/benches/blake3.rs` exercises the 100 MiB throughput-saturation regime and `VerifiedBody::new` (hash + verify round-trip).

## §6 — Why CoreLink picked BLAKE3

These are the five concrete reasons, each grounded in a specific code or invariant reference.

**1. Parallel hashing of large blobs closes the throughput gap with non-cryptographic hashes.**

The AC §8 target (1.4 GiB/s on 5 MiB in WASM) was the design constraint. SHA-256 on WASM without SHA-NI delivers approximately 90 MB/s. That is a 15× gap. No amount of software optimization closes it because the bottleneck is the sequential compression chain. BLAKE3's Merkle tree allows every 1 KiB chunk to be processed in parallel, which is why the WASM SIMD path hits 1.5 GiB/s. The hash function is no longer the write-path bottleneck.

**2. derive-key mode enables tenant namespacing without a separate index.**

A naive multi-tenant CAS needs a per-tenant prefix table: `(tenant_id, content_hash) → storage_key`. That is a D1 lookup on every write. With BLAKE3 `derive_key`, the tenant-scoped address *is* the storage key. No lookup table, no join, no new invariant to maintain. The address space partitions naturally and cryptographically. This is the mechanism described in the multi-tenancy spec; the derive-key call will live adjacent to the `Digest::compute` path in `crates/corelink-hash/`.

**3. No length-extension vulnerability removes a footgun near multi-tenant auth.**

SHA-256 is vulnerable to length-extension: if you know `SHA256(secret || message)`, you can compute `SHA256(secret || message || padding || extra)` without knowing `secret`. This is only exploitable in MAC constructions, not CAS addressing — but it means SHA-256 digests cannot be safely reused as authorization tokens or signed URLs without a wrapping HMAC layer. BLAKE3 (in all three modes) uses a finalization step that destroys the length-extension structure. Digests produced by `Digest::compute` (`crates/corelink-hash/src/digest.rs:31`) can be safely embedded in signed assertions without additional wrapping.

**4. The `VerifiedBody` type makes the security model a compile error, not a convention.**

This is the type-driven integrity argument documented in `crates/corelink-hash/src/verified_body.rs:10-17`. The storage adapter trait `BlobStoreWrite` (`crates/corelink-hash/src/store.rs:26-39`) accepts `&VerifiedBody`, not `&[u8]`. You cannot call `put_verified` with unverified bytes — the type system prevents it. This design is only possible because `Digest::compute` is cheap enough to run on every PUT and every GET. If our hash function were 15× slower (SHA-256 on WASM), the temptation to skip the re-hash on GET would be real. With BLAKE3, the re-hash on a 1 MiB blob takes under a millisecond, so the verification is always on and the type constraint is always enforced.

**5. The `blake3` crate is zero-unsafe, actively maintained, and authored by the algorithm designers.**

`corelink-hash` has `#![forbid(unsafe_code)]` at its root (`crates/corelink-hash/src/lib.rs:49`). The `blake3` crate upstream uses `unsafe` internally for its SIMD dispatch — but that unsafe is behind the crate boundary and reviewed by the algorithm authors. Our crate never touches it. The `subtle` crate used for constant-time comparison (`crates/corelink-hash/src/digest.rs:78-80`) has the same property: trusted upstream `unsafe`, zero unsafe in our code. This combination is what makes `#![forbid(unsafe_code)]` compatible with production-grade cryptographic performance.

## §7 — What we would do differently

Honesty demands two notes on choices we made that we would revisit with hindsight.

**7.1 We should have shipped derive-key namespacing from day one.**

The current `Digest::compute` path (`crates/corelink-hash/src/digest.rs:30-32`) uses hash mode, not derive-key mode. Tenant namespacing is currently handled at the storage-key level by a string prefix (`<tenant_id>/<digest_hex>`). This works but it is weaker: two tenants with the same blob at the same prefix produce the same storage key collision surface — the prefix is the only tenant isolation, and it is a runtime string comparison, not a cryptographic domain separation. We designed for derive-key from the spec but deferred the implementation. We would not defer it again.

**7.2 We should have benchmarked WASM SIMD vs scalar earlier.**

The decision to target ≥ 1.4 GiB/s on WASM came from the BLAKE3 paper's WASM numbers, which assume `simd128` is available. Cloudflare Workers WASM with `simd128` is available — but only since 2023, and only when compiled with the right `target_feature`. We spent two weeks in early development wondering why our bench numbers were 3× lower than expected before discovering we were building without `--target-feature=+simd128`. The fix was one Cargo flag. The lesson: benchmark WASM explicitly, with the feature flags you will use in production, before committing to a throughput target.
