# Data handling

This page documents **where customer data physically lives**, **how it is
protected**, and **how long we keep it**. Everything below is verifiable —
either by reading the open-source code, by inspecting your tenant via the
admin API, or by requesting the attestation pack at `trust@humangr.com`.

## What we store

CoreLink's data surface is intentionally narrow:

| Data class | What it is | Where it lives |
| --- | --- | --- |
| **Content-addressable blobs** | Build artefacts, action outputs, intermediate caches keyed by BLAKE3 / SHA-256 digest | Cloudflare R2 (per-tenant prefix) |
| **Action cache metadata** | Action-result records, REAPI v2 metadata | Cloudflare D1 (per-tenant database) |
| **Hot path / counters** | Short-TTL counters, idempotency keys, rate-limit windows | Cloudflare KV |
| **Per-tenant coordination state** | Tenant-scoped Durable Object instances | Cloudflare Durable Objects |
| **Identity records** | User identities, MFA, session tokens | Clerk (per CoreLink tenant) |
| **Billing records** | Customer ID, subscription ID, invoice references | Stripe; mirrored summary in Neon control DB |
| **Audit chain** | Append-only Merkle-linked audit events | Cloudflare R2 (audit prefix) + reconcile job in D1 |
| **Telemetry & logs** | Latency histograms, error counts, aggregate metrics — **no customer artefact content** | Grafana Cloud (no PII / no payloads) |

We do **not** store: PHI, cardholder data (Stripe holds it), customer email
beyond what's needed for billing notifications, or copies of customer code
outside the CAS surface.

## Residency

> **Where data lives today (be precise):** CoreLink serves tenants from two
> live regions — the **US (ENAM, Eastern North America)** default and a
> **physically-EU (WEUR)** region for EU tenants.
> - **US tenants:** all data — CAS blobs, action-cache entries, metadata,
>   audit chain — is physically stored in the **United States**.
> - **EU (`weur`) tenants:** CAS and action-cache blobs are stored in
>   **physically-EU Cloudflare R2 buckets** (`corelink-cas-eu` /
>   `corelink-ac-eu`, both **EEUR / East EU**), served via our London / `lhr`
>   cluster — **EU-origin data physically stays in the EU**. This is a
>   **delivered** capability for EU-region tenants, not roadmap.
>
> The remaining jurisdictions in the model below — **Brazil / São Paulo
> (`sam`)** and **APAC (`oce` / `apc` / `mea`)** — are still **roadmap /
> enterprise-on-request**. In particular, **Cloudflare R2 has no
> South-America region**, so Brazilian-jurisdiction *physical* residency is
> not yet technically possible (`sam`-bound data resides in the US or EU under
> SCCs). Treat any non-US, non-EU region as a forward-looking commitment until
> it ships and a real `locationHint`-based verification passes.

Where data is stored under a US (or, for `sam`, US/EU) binding, cross-border
transfers are governed by **SCCs + supplementary measures in the DPA** (see
[Compliance](./compliance)).

### Region availability

Every tenant has a `primary_region` set at provisioning, from a closed enum:

| Pin | Region | Geography | Status |
| --- | --- | --- | --- |
| `enam` | Eastern North America (Iowa / Virginia) | United States | **Live (default)** |
| `weur` | Western Europe | EU (physically-EU R2, EEUR; served via `lhr`) | **Live — EU data stays in the EU** |
| `wnam` | Western North America | United States | Roadmap / on request |
| `sam` | South America (São Paulo) | Brazil | **Roadmap** — no Cloudflare SA region; physical BR residency not yet possible |
| `oce` | Oceania (Sydney) | AU / NZ | Roadmap / on request |
| `apc` | Asia-Pacific (Tokyo / Singapore) | JP / SG | Roadmap / on request |
| `mea` | Middle East (Dubai) | UAE | Roadmap / on request |

What `primary_region` controls:

- **R2 object placement.** For the live regions, blobs are written to that
  region's R2 buckets (US buckets for `enam`; physically-EU EEUR buckets for
  `weur`). The residency guard maps `weur`→`lhr` and refuses cross-region
  access (`INV-REGION-NO-CROSS-LEAK`). *(Roadmap regions: in-jurisdiction
  buckets ship with the region.)*
- **D1 placement.** Per-tenant D1 database created in-region.
- **DO placement.** Durable Object instance colocated with D1.
- **Failover semantics.** During a region outage, the failover path is always
  within the tenant's residency boundary and is documented per region in
  [`specs/_runbooks/RB-DR-DRILL.md`](https://github.com/HumanGuardrail/corelink/blob/main/specs/_runbooks/RB-DR-DRILL.md).
  For Brazil specifically, see
  [Brazil residency & LGPD](/residency/lgpd-brazil) — Art. 33 §1º allows
  out-of-region temporary processing during a documented emergency.

The residency-enforcement crate (`corelink-privacy`) enforces the region
binding for the live regions. The Brazil-specific verification script
(`scripts/verify-lgpd-residency.py`) **fails-loud** rather than emitting a
green attestation, because Brazilian physical residency is not yet provisioned
(no Cloudflare SA region). A signed per-tenant residency-proof API
(`/v1/tenant/me/residency-proof`) is on the roadmap and is not a capability
you should rely on today.

## Encryption

### At rest

All persistent storage is encrypted at rest with **AES-256-GCM**:

- **R2 blobs** — Cloudflare-managed SSE (AES-256-GCM) by default.
- **R2 blobs with BYOK** — additional customer-side envelope encryption per
  blob (per-tenant DEK wrapped by the tenant's KMS root key). See
  [BYOK customer-managed keys](/security/byok) for the four supported
  providers (AWS KMS, GCP Cloud KMS, Azure Key Vault, HashiCorp Vault).
- **D1 + KV + DO** — Cloudflare-managed encryption at rest.
- **Backups** — encrypted at rest with the same envelope as the source.

### In flight

- **External traffic:** **TLS 1.2 minimum**, 1.3 negotiated by every client that supports it, with HSTS
  (`max-age=63072000; includeSubDomains; preload`). HTTP/2 + HTTP/3
  available. Cipher suites limited to AEAD (AES-256-GCM, ChaCha20-Poly1305).
- **Edge-to-origin:** mTLS between Cloudflare edge and backing data planes
  per `CTRL-NET-002`.
- **Service-to-service:** internal calls between Workers are routed through
  Cloudflare's encrypted internal fabric.

The full cryptography baseline is in the
[Security overview](/security#cryptography-baseline).

### In use

Worker isolates provide per-request memory isolation (V8 isolate model).
Customer artefact bytes are not held in long-lived memory between requests;
each request gets a fresh isolate.

When BYOK is enabled, **plaintext data encryption keys (DEKs) never leave
the request scope**. They are decrypted from the customer's wrapped form,
used to encrypt or decrypt the blob in-flight, and discarded before the
isolate is recycled.

## Retention

Retention is **driven by data class**, not by a global default:

| Data class | Default retention | Customer-controlled? |
| --- | --- | --- |
| Content-addressable blobs | Customer-configurable; default LRU 90 days | Yes — per-tenant TTL + manual purge |
| Action cache metadata | Mirrors blob TTL | Yes — coupled to blob lifetime |
| Audit chain | **7 years** | No — compliance-driven minimum |
| Identity records (Clerk) | While account active + 30 days post-cancel | Yes — DSR erasure available |
| Billing records (Stripe + control DB) | 7 years (tax / accounting) | No — regulatory requirement |
| Telemetry aggregates (Grafana) | 13 months | No — operational retention |
| Backup snapshots | 35 days rolling | No — operational retention |

### Right to erasure

CoreLink supports GDPR Art. 17 and LGPD Art. 18 erasure requests:

- **Tenant-initiated erasure** via the admin API (`DELETE /v1/tenant/me`)
  triggers a verifiable erasure workflow with cryptographic attestation
  (`INV-DATA-ERASURE-COMPLETE`, `INV-ERASURE-ATTESTATION-SIGNED`).
- **Audit-chain redaction** uses the salt-rotation pattern documented in
  `ADR-S11-003` — the audit record remains for integrity, but the
  PII-bearing claim becomes cryptographically unrecoverable.
- **Backup tombstones** — erasure requests propagate to rolling backups
  within 35 days (the backup window); a tombstone is recorded on day 0
  so a Type II auditor can trace the chain.

See the [DSR runbooks](https://github.com/HumanGuardrail/corelink/tree/main/specs/_runbooks)
(`RB-DSR-INTAKE-FAILURE`, `RB-DSR-ERASURE-INCOMPLETE`) for the operational
side.

## Customer data flow (high-level)

> The storage below is physically in the tenant's region: **US (ENAM)** for the
> default region, and **physically-EU (WEUR / EEUR)** for EU tenants (storage
> served via the `lhr` cluster). Brazil/`sam` and APAC region pins are roadmap.

```
                ┌─────────────────┐
                │   Your CI / IDE │
                └────────┬────────┘
                         │ TLS 1.2+
                         ▼
       ┌─────────────────────────────────┐
       │ Cloudflare Edge (tenant region) │
       └────────┬────────────┬───────────┘
                │            │
        ┌───────┘            └─────────┐
        ▼                              ▼
  ┌────────────┐               ┌──────────────┐
  │ Workers    │ tenant region │ Durable Obj  │
  │ (isolate)  │◄──────────────┤ (per-tenant) │
  └─────┬──────┘               └──────────────┘
        │
        ├──► R2 (per-tenant prefix; US/ENAM or EU/EEUR buckets per region; BYOK envelope if enabled)
        ├──► D1 (per-tenant DB, in tenant region)
        ├──► KV (per-tenant namespace, short-TTL only)
        └──► Audit chain (append-only, Merkle-linked)
```

## Verifying it yourself

You don't have to take our word for any of the above. Three options:

1. **Read the code.** The repo is
   [`HumanGuardrail/corelink`](https://github.com/HumanGuardrail/corelink).
   The residency enforcement, BYOK envelope, and audit chain are
   all open. (Note: US/ENAM and physically-EU/WEUR residency are live;
   Brazil/`sam` and APAC physical residency are roadmap, not GA.)
2. **Hit the admin API.** Endpoints under `/v1/tenant/me/*` return signed
   attestations of encryption status and audit-chain head. The
   region-pin/residency-proof attestation is part of the residency roadmap and
   is not relied-upon today.
3. **Audit your own data.** Audit-chain inclusion proofs are exportable as
   RFC 6962 proofs you can verify offline. See
   [Audit chain](/security/audit-chain).
