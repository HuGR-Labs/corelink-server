# Role catalog

The four canonical CoreLink roles and what each one is for. The role enum is
defined in
`corelink-auth-schema/src/sim.rs`
and the SQL `CHECK` constraint lives in `specs/03_architecture/data_model.md`
§4.1 line 174.

---

## `Owner` — full access including billing

> "I sign the contract, I see the invoice, I can do anything in this tenant."

### Can do

- Everything an `Admin` can do (see below), **plus**:
  - View and mutate billing surface (the `billing` capability of an
    owner dashboard session; never a minted cache PAT).
  - Grant or revoke the `Owner` role on other users.
  - Act as approver for destructive operations.
  - Initiate Enterprise BYOK setup (KMS root key wrap) — *planned — Enterprise BYOK with customer-managed KMS is on the roadmap; the current endpoint returns HTTP 501 (not wired).*

### Cannot do alone

- Execute any of the 5 destructive admin ops without a second approver
  (Owner or Admin). The dual-approval gate is bypass-proof — see
  `INV-ADMIN-DUAL-APPROVAL` in
  `specs/03_architecture/invariant_registry.md`.

### Common use cases

1. Initial tenant setup — first signup user is auto-`Owner`.
2. Procurement / Finance escalations — Owner reads invoices, applies tax
   exemption, downgrades / upgrades tier.
3. BYOK setup — *planned — Enterprise BYOK with customer-managed KMS is on the roadmap*; the endpoint currently returns HTTP 501 and is not wired.

### Example workflow: Change a tenant's tier under dual approval

The approval is recorded **first**, on its own route, and the mutation
presents it afterwards:

```
1. Approver-B: POST /v1/admin/approve
     { "approval_id": "<fresh uuid>", "op_kind": "set_tenant_tier",
       "tenant": "<tenant_id>" }
   Gated by CORELINK_ADMIN_APPROVER_AUTH_KEY — a DIFFERENT credential
   from the mutate gate, so one key holder cannot both approve and mutate.
2. Operator-A: POST /v1/admin/mutate
     { "op_kind": "set_tenant_tier", "tenant": "<tenant_id>",
       "tier": "<tier>", "approval_id": "<same uuid>" }
   Gated by the x-corelink-internal-auth header (fail-CLOSED 403; the
   body is not even parsed until the gate passes).
3. Server: the approval_id must exist in the ledger (else 403
   "dual-approval not found"), must bind to the same derived resource
   (else 403 "dual-approval scope mismatch"), must not be self-approved
   (403), and is single-use (replay → 409 "dual-approval already used").
4. Mutation executes; the handler returns the resource string.
```

`POST /v1/admin/approve` is a route of its own
(`crates/corelink-container/src/routes/admin.rs:129`), not a field on the
mutate body. The served admin plane accepts exactly two `op_kind` values —
`set_tenant_tier` and `rotate_admin_token` (`admin.rs:1056-1071`). The
`AdminOpType` variants named further down this page (`ConfigRollback` and
siblings) are **not served by this handler**. The type lives in
`crates/corelink-dual-approval`, which *is* reachable from
`corelink-server` in the dependency graph — but only under
`cargo tree --target all`: the edge is `wasm32`-gated
(`crates/corelink-clerk-cf/Cargo.toml:108`). It therefore does not enter
the container binary, which builds for `x86_64-unknown-linux-gnu` —
a target `Dockerfile:182` reaches **by absence of `--target`**, so
searching that file for the triple finds nothing.

## `Admin` — tenant administrator

> "I run the team's CoreLink setup. I invite people, mint tokens, read audit
> logs. I don't see the invoice."

### Can do

- Read and mutate tenant config.
- Mint and revoke PATs for any user in the tenant.
- Read tenant audit log.
- Invite, demote, and revoke users below `Owner`.

  These four are gated on the **dashboard session role**, not on a PAT
  scope. The granular `admin:*` scope names that used to be cited here
  were never implemented and were removed in B-080.
- Act as approver for destructive operations (under
  `INV-ADMIN-DUAL-APPROVAL`).
- All CAS read/write (`cache:r`, `cache:w`, `cache:find-missing`).

### Cannot do

- View or mutate billing — the `billing` capability is `Owner`-only.
- Grant or revoke the `Owner` role.
- Single-handedly execute any destructive op
  (`ConfigRollback`, `RetentionPolicyReduce`, `FeatureFlagDisable`,
  `SecretRotationStart`, `TenantTombstone`) — requires a second Admin or
  Owner via the dual-approval gate (see `INV-ADMIN-DUAL-APPROVAL`).

### Common use cases

1. Day-to-day admin: onboarding a new engineer (invite + assign Developer
   role + mint their first PAT).
2. Forensics: querying audit log after a suspected leak — see
   [Audit role changes](../../how-to/rbac/audit-role-changes).
3. Co-signing a config rollback or feature-flag disable initiated by
   another Admin.

### Example workflow: Revoke a leaked PAT

```
1. Admin: receives alert "PAT tok_abc...XYZ used from unusual region".
2. Admin: revokes the token in the dashboard (https://humangr.com/corelink/),
   or calls the HTTP API directly:
   → POST /v1/customer/keys/{pat_id}/revoke (single-actor; no approver
     required; this is a non-destructive op).
3. The pat row is stamped revoked_at — idempotent (re-revoking keeps the
   original timestamp). No caller-supplied reason is recorded: the endpoint
   takes no request body.
4. Audit chain entry written.
5. Clients holding that PAT receive 401 on subsequent requests, once the
   edge PAT-verify cache entry expires (≤5s; ADR-0030 bounds revocation
   at ≤60s p99).
```

## `Developer` — CAS read/write, no admin surface

> "I build code and need to read/write the cache. I don't touch tenant
> settings."

### Can do

- Read CAS blobs and AC results (`cache:r`).
- Write CAS blobs and AC results (`cache:w`).
- Execute `FindMissingBlobs` (`cache:find-missing`).
- Mint **their own** PAT with subset of their granted scopes.
- (Phase 2) Report action execution status (`execute:action`,
  `report:result`).

### Cannot do

- *(Correction: a Developer **can** delete CAS blobs. `DELETE /v1/cas/{tenant}/{hash}`
  is gated on the cache-WRITE capability, not on a delete-specific scope, so any
  write-capable token deletes. The `cache:delete` scope is defined but no
  enforcement point reads it.)*
- Mint PATs for other users.
- Read tenant config or audit log.
- Invite, demote, or revoke users.
- Act as approver for destructive operations (the dual-approval gate
  requires the approver to hold `Admin` or `Owner` — see `AdminRoleStore`
  in `crates/corelink-dual-approval/src/gate.rs`).

### Common use cases

1. CI service account: assign Developer role, mint a PAT with
   `cache:r | cache:w | cache:find-missing` scope mask.
2. Engineer on the team: same as above, but PAT is bound to
   `issued_to_user = <their UUID>` for forensics.
3. ML training pipeline writing intermediate artifacts to CAS.

### Example workflow: Mint a CI PAT for yourself

```
1. Developer: opens admin UI → "My tokens" → "Mint new token"
2. Selects scopes: cache:r, cache:w, cache:find-missing
3. UI displays the token once (Argon2id hash is stored; raw is gone after
   close).
4. Developer: copies the token into the CI secret store
   (GitHub Actions, GitLab CI, etc).
5. PAT used in Authorization: Bearer header on every cache request.
```

## `Viewer` — read-only

> "I look at dashboards and audit logs. I don't write anything."

### Can do

- Read CAS blobs and AC results (`cache:r`).
- Read tenant audit log — useful for SecOps observers. The `/v1/audit/*`
  routes (analytics + export) are gated by `requires_audit_read`, which
  any read-capable token satisfies, so a read-scoped PAT works. The
  dashboard's own Audit log page (`GET /v1/customer/audit`) is stricter
  (`requires_billing_admin`) because it carries billing / account PII.
- View tenant config.

### Cannot do

- Write or delete CAS blobs.
- Mint any PAT.
- Mutate any tenant config.
- Invite, demote, or revoke users.
- Act as approver for destructive operations.

### Common use cases

1. Auditor account — temporary `Viewer` granted to an external auditor for
   SOC 2 evidence review. Revoked at end of audit.
2. SecOps / compliance team member — needs to inspect the audit chain but
   should never originate writes.
3. Read-only dashboard consumer — internal metrics dashboard wired to a
   `Viewer` PAT.

### Example workflow: Hand a SOC 2 auditor temporary access

```
1. Owner or Admin: invites auditor@firm.com with role=Viewer.
2. Auditor signs in via Clerk SSO; membership row written.
3. Auditor mints a PAT (forbidden — Viewer cannot mint).
4. Admin: mints a PAT on the auditor's behalf with `cache:r` scope,
   time-boxed expiry (e.g. 14 days). (There is no `admin:audit` scope to
   add — it never existed; the audit log is read from the dashboard.)
5. After audit closes: Admin revokes the PAT (no reason is recorded — the
   revoke endpoint takes no request body) and demotes the membership row
   (deleted_at = now()).
```

> **Audit storage note:** The shipped guarantee is an append-only audit chain with a keyed, signed head (tamper-evident, detect-at-verify). R2 Object-Lock immutable storage (WORM-style 7-year retention) is a roadmap item (WI-S09-007), not shipped today.

## Role transition matrix

Who can change whom:

| Initiator → target | → Owner            | → Admin     | → Developer | → Viewer    |
|--------------------|--------------------|-------------|-------------|-------------|
| `Owner`            | Grant / revoke     | Grant / revoke | Grant / revoke | Grant / revoke |
| `Admin`            | ❌                  | ❌           | Grant / revoke | Grant / revoke |
| `Developer`        | ❌                  | ❌           | ❌           | ❌           |
| `Viewer`           | ❌                  | ❌           | ❌           | ❌           |

> **Last-Owner safeguard:** A tenant must always retain at least one `Owner`.
> The admin API rejects any operation that would demote the final Owner. This
> is enforced by the membership soft-delete path, not by the dual-approval
> gate (it's a single-actor invariant, not a destructive op).
