# Audit chain and Merkle proofs

> **DRAFT — pending Legal + Finance + Security review.** The customer-facing
> proof API is in active design; field names and endpoints below are
> illustrative.

CoreLink writes every administrative or data-plane mutation to an append-only
audit log. The log is structured as a Merkle tree following **RFC 6962**
(Certificate Transparency) so that any consumer can verify, with a small
inclusion proof, that a specific event is part of the public log head without
trusting CoreLink.

## What each event records

`{actor, tenant_id, token_hash, op, path_hash, timestamp, request_id, outcome}`

Sensitive fields (`token_hash`, `path_hash`) are pseudonymized via tenant-scoped
HMAC keys so the log can be retained without retaining the underlying secrets.

## Retention and immutability

- **Retention:** 7 years (aligned with SOC 2 Type II observation expectations).
- **Backing store:** R2 bucket in Object Lock Governance mode.
- **Reconciliation:** daily drift check against Cloudflare analytics; alerts
  fire when drift exceeds 0.1 percent.
- **Chain key rotation:** annual; rotation is forward-only and does not
  invalidate prior inclusion proofs.

## Customer-facing verification

Inclusion proofs are delivered through the audit **export**, not a
standalone per-event command. `--include-merkle-proofs` embeds a Merkle
inclusion proof in every exported event row, and `--verify` re-validates
every proof before the file is written (fail-closed):

```sh
corelink audit export --tenant <tenant_id> --since <ms> --until <ms> \
  --include-merkle-proofs --verify
```

To re-check an export you already hold, `corelink audit verify <path>`.

For the streaming NDJSON envelope from `GET /v1/audit/export` — one
`{event, proof}` line per audit row plus a trailing manifest line —
`corelink audit verify-ndjson` re-verifies the whole chain against the
chain-head anchor the server publishes in the
`X-CoreLink-Audit-Export-Chain-Head-Anchor` response header. It reads the
envelope either from disk (`--ndjson <file> --chain-head-anchor <hex>`) or
over HTTP (`--url <url> --bearer <PAT>`, which recovers the anchor from the
response header), exiting 0 on full chain integrity and non-zero on any
divergence.

The chain key and its rotation policy are documented in
`security_model.md §7.2`.

### See it in your browser

The customer dashboard ships an in-browser audit-chain visualization at
`/customer/audit/visualization`. The page renders the chain head, your
tenant's leaves, and an inclusion-proof modal where each sibling-hash step
is verifiable client-side via the `@corelink/client` WASM bundle (which
reuses the canonical Rust `corelink-client-verify` truth per ADR-0016).

Spec: `specs/_audits/sealed/2026-05-15-audit-viz-spec.md`.

## Privacy interaction with DSR erasure

When a Data Subject Request causes erasure, the `subject_id` field is
pseudonymized to `erased_<hash>` using the audit-pseudonym key so that the
inclusion proof of the original event remains verifiable while the personal
data itself is removed (`CTRL-PRIV-014`).
