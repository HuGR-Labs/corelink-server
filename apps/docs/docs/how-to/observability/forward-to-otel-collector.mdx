# Forward CoreLink metrics + traces to an OpenTelemetry Collector

**Source:** CoreLink (any tenant, any tier).
**Destination:** an [OpenTelemetry Collector](https://opentelemetry.io/docs/collector/)
deployment you operate (sidecar, daemonset, or central pipeline).
**Transport:** OTLP/gRPC (`grpcs://collector:4317`) or OTLP/HTTP
(`https://collector:4318`).
**Auth:** bearer token (`Authorization: Bearer <token>`) or IP allow-list
on a private endpoint.

**Why pick OTel Collector over Datadog or Grafana Cloud directly:** the
Collector is a vendor-neutral router. Once CoreLink streams to it, you
can fan-out to **any backend** (Honeycomb, New Relic, Splunk
Observability, AWS CloudWatch, self-hosted Prometheus + Tempo + Loki,
multiple destinations simultaneously). This is the **most flexible**
option and the one we recommend for enterprise customers who don't want
vendor lock-in.

---

## Prerequisites

- An OpenTelemetry Collector reachable from CoreLink's egress IP range.
  We publish CoreLink's egress IP allow-list at
  [Trust → Data handling](../../trust/data-handling#corelink-egress-ip-ranges).
- TLS enabled on the Collector endpoint (CoreLink rejects plaintext
  `http://` / `grpc://` for non-localhost endpoints).
- A bearer token rotated quarterly. The Collector validates it via the
  `bearertokenauth` extension.
- CoreLink CLI ≥ 0.1.0 and a CoreLink tenant ID + admin PAT.

## Step 1 — Configure the Collector to accept OTLP from CoreLink

Sample Collector config (`otel-collector-config.yaml`):

```yaml
extensions:
  bearertokenauth:
    scheme: "Bearer"
    tokens:
      # SHA-256 of the canonical token (the Collector validates against
      # this hash; never store the raw token in config).
      - "${COLLECTOR_BEARER_TOKEN_SHA256}"

receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
        tls:
          cert_file: /etc/otel/cert.pem
          key_file:  /etc/otel/key.pem
        auth:
          authenticator: bearertokenauth
      http:
        endpoint: 0.0.0.0:4318
        tls:
          cert_file: /etc/otel/cert.pem
          key_file:  /etc/otel/key.pem
        auth:
          authenticator: bearertokenauth

processors:
  # Drop CoreLink's pseudonymous tenant_tier label only if your
  # privacy posture requires it (default: keep — it's already PII-free).
  # attributes:
  #   actions:
  #     - key: tenant_tier
  #       action: delete

  batch:
    timeout: 5s
    send_batch_size: 1000

exporters:
  # Pick one or more downstream backends:
  # otlphttp:                # → another OTLP backend (Honeycomb, NR, ...)
  # prometheusremotewrite:   # → Prometheus / Mimir / Grafana Cloud
  # awscloudwatch:           # → AWS CloudWatch Metrics
  # ...
  logging:
    verbosity: detailed

service:
  extensions: [bearertokenauth]
  pipelines:
    metrics:
      receivers:  [otlp]
      processors: [batch]
      exporters:  [logging]
    traces:
      receivers:  [otlp]
      processors: [batch]
      exporters:  [logging]
```

Deploy and verify the Collector is healthy:

```bash
curl -sf -H "Authorization: Bearer ${TOKEN}" \
  https://collector.example.com:13133/health
```

## Step 2 — Wire CoreLink to the Collector

Edit your CoreLink tenant config:

```toml
[observability.export]
variant = "otel_collector"

[observability.export.otel_collector]
endpoint     = "https://collector.example.com:4318"   # HTTP — CF Workers-friendly
protocol     = "http"                                  # "grpc" | "http"
bearer_token = "${OTEL_BEARER_TOKEN}"                  # ≥ 8 ASCII chars
timeout_ms   = 2000
opt_out_low_value_metrics = false
```

**Why we recommend HTTP over gRPC on CF Workers.** CoreLink's edge runs
on Cloudflare Workers, and `worker::send_future` plays better with
HTTP/1.1 + HTTP/2 than with bidirectional gRPC streaming. If your
Collector is reachable on the same private network with gRPC, prefer
`protocol = "grpc"`; otherwise stick with HTTP.

### How the `[observability.export]` surface is wired in the container

The Rust data-plane container reads the `[observability.export.*]`
surface as **environment variables** (the Durable Object forwards them
from `wrangler.toml`'s `[env.*.vars]`). The container constructs the
selected exporter at router-build time and streams a canonical
`MetricPoint` + `TraceSpan` per data-plane request through the
fail-OPEN boundary. The env mapping for the OTel-Collector variant:

| TOML key | Container env var |
|---|---|
| `variant = "otel_collector"` | `CORELINK_OBSERVABILITY_EXPORT_VARIANT=otel_collector` |
| `otel_collector.endpoint` | `CORELINK_OTEL_COLLECTOR_ENDPOINT` |
| `otel_collector.protocol` | `CORELINK_OTEL_COLLECTOR_PROTOCOL` (`http` default \| `grpc`) |
| `otel_collector.bearer_token` | `CORELINK_OTEL_COLLECTOR_BEARER_TOKEN` (optional) |

When `CORELINK_OBSERVABILITY_EXPORT_VARIANT` is unset / `disabled`, or
the selected variant's config is missing/malformed, the export layer is
**not mounted** — the data plane serves exactly as before (fail-SAFE: a
bad observability config never bricks CoreLink). The chosen `region`
label is taken from `R2_CAS_REGION`.

:::note Operator step — the collector endpoint + network egress
The container **constructs the exporter and emits real request-path
metrics/spans through it today** (visible in the container logs under
`target: "corelink_otel_export"`). The exporter's actual OTLP/HTTP
**network egress to your collector is the remaining operator step**: you
provide the reachable `CORELINK_OTEL_COLLECTOR_ENDPOINT` (+ bearer), and
the wire transport itself lands behind its own chaos test as a
deferred-real follow-up in `corelink-telemetry`. Until egress ships, the
per-request emit is observable in logs and via the
`corelink.observability.export_*` audit events.
:::

Apply:

```bash
corelink config apply --file corelink.toml
```

The Admin API validates:

- `endpoint` starts with `https://` / `http://` / `grpcs://` / `grpc://`.
- `bearer_token` length ∈ `[8, 4096]` and is pure ASCII.
- `timeout_ms` ≥ 100.

Real auth is verified on first export attempt; a failure becomes a
`corelink.observability.export_failed` audit event but does not break
CoreLink's request path.

## Step 3 — Verify the wire

```bash
# 1) CoreLink-side: tail the audit log
corelink audit tail --filter "event_type=corelink.observability.export_ready"

# 2) Collector-side: with exporters: [logging], you should see batches
#    arriving every 5s. Sample log line:
#    {"corelink_cas_put_requests_total":{...,"labels":{"tenant_tier":"pro","region":"us-east-1","result":"ok"}}}

# 3) End-to-end: fire a known request against CoreLink, then look for
#    its trace span in the Collector log:
corelink cas put --tenant t1 --file /tmp/probe.bin
```

If `corelink.observability.export_failed` shows up instead:

| Failure reason | What it means | Fix |
|---|---|---|
| `auth reject from vendor: 401` | Bearer token wrong | Re-issue in step 1, re-apply CoreLink config |
| `transport failure: tls handshake` | Cert chain wrong on Collector | Check Collector logs; verify intermediates |
| `transport failure: connection refused` | Collector down or wrong port | Verify `4317` (gRPC) vs `4318` (HTTP) |
| `vendor rejected payload: 400` | Collector / OTLP version mismatch | Upgrade Collector to ≥ 0.95 (canonical OTLP/1.0) |

## Step 4 — Fan-out to multiple backends

This is where the Collector shines. Add exporters to your Collector
config and update the `service.pipelines.metrics.exporters` /
`service.pipelines.traces.exporters` lists. CoreLink only knows about
the Collector; the Collector handles fan-out:

```yaml
exporters:
  otlphttp/honeycomb:
    endpoint: https://api.honeycomb.io
    headers:
      x-honeycomb-team: "${HONEYCOMB_KEY}"

  prometheusremotewrite/mimir:
    endpoint: https://mimir.example.com/api/v1/push

service:
  pipelines:
    metrics:
      receivers:  [otlp]
      processors: [batch]
      exporters:  [otlphttp/honeycomb, prometheusremotewrite/mimir]
    traces:
      receivers:  [otlp]
      processors: [batch]
      exporters:  [otlphttp/honeycomb]
```

## Step 5 — Sampling

By default CoreLink samples request-scoped traces at **1% in production
/ 100% in staging** (per
[`observability_model.md §6.3`](https://github.com/HumanGuardrail/corelink-server/blob/main/specs/03_architecture/observability_model.md#63-sampling)).
You can override via the Worker sampling config; lowering to 0.1%
reduces APM cost by ~10×.

Errors + p99 SLO breaches are **always sampled** regardless of the base
rate (tail-based sampling decision; canonical Google SRE Workbook
Chapter 6).

## Cost expectation

The Collector is **free software**; you pay only for the compute that
runs it + the downstream backend's ingest. Sizing for a typical
CoreLink Pro tenant:

| Resource | Size |
|---|---|
| Collector CPU | 0.25 vCPU steady, 1 vCPU peak |
| Collector RAM | 256 MiB steady |
| Throughput | ~10k samples/min metrics + ~100 spans/min traces |
