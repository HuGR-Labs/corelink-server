# Audit role changes

## When to use this guide

You need to answer questions like:

- "Who promoted Alice from Developer to Admin, and when?"
- "Show me every Owner-role grant in this tenant in the last 90 days."
- "Did the dual-approval gate fire on the rollback we did last Tuesday?"

This guide shows how to query the CoreLink audit chain for role changes
and dual-approval events.

> Team and role management itself is **dashboard + HTTP API only** —
> there is no CLI for it. Manage members at
> `https://humangr.com/corelink/en/customer/team`, or through
> `GET /v1/customer/team`, `POST /v1/customer/team/invite`
> (`{email, role}`) and `DELETE /v1/customer/team/{user_id}` (invite and
> remove are owner/admin only). Reading the audit trail — the subject of
> this guide — is what the `/v1/audit/*` routes and the `corelink audit`
> command do.

## Prerequisites

- You hold `admin:audit` scope.
- A PAT with that scope
  (`Authorization: Bearer corelink_<env>_…`), or a Clerk session in the
  dashboard. Mint and list PATs with `POST /v1/customer/keys`
  (`{name, scopes[]}`) and `GET /v1/customer/keys`; revoke with
  `POST /v1/customer/keys/{pat_id}/revoke`.
- API base URL: `https://corelink-api.humangr.com`.

## The audit chain in one paragraph

Every administrative or data-plane mutation is written to an append-only
log structured as an RFC 6962 Merkle tree. Role-relevant events live in
two streams:

1. `admin_op_log` — the table-backed log of every dual-approval-gated
   operation, with `outcome` ∈ `{approved, denied_missing, denied_sig,
   denied_caller_eq, denied_collusion, denied_mfa_stale,
   denied_approver_not_admin, denied_nonce_replay, denied_clock_skew}`
   (`crates/corelink-dual-approval/src/types.rs::ApprovalOutcome`).

2. The CloudEvent audit chain — the broader log. The two event types
   pinned to source constants are `corelink.admin.op.executed` and
   `corelink.admin.op.denied`
   (`crates/corelink-dual-approval/src/audit.rs`). Membership and role
   mutations land in the same tenant stream, but this guide does not
   print their `type` strings: discover the exact values your tenant
   emits with Query 1 below, then filter on them.

Both are read through the `/v1/audit/*` HTTP routes and the
`corelink audit` CLI. The deeper
[audit chain explainer](../../explanation/security/audit-chain.mdx) covers
the underlying mechanism (Merkle proofs, retention, etc).

## Query 1 — which event types fired in a window

`GET /v1/audit/analytics/event-count` aggregates the tenant's audit rows
by CloudEvents `type` over `[from, to)` (Unix epoch **milliseconds**),
with an optional exact-match `event_type` filter:

```bash
curl -sS \
  -H "Authorization: Bearer corelink_<env>_…" \
  "https://corelink-api.humangr.com/v1/audit/analytics/event-count?from=<epoch_ms>&to=<epoch_ms>"
```

The response carries a `buckets` array — one entry per distinct
`event_type` seen in the window, each entry pairing that `event_type`
with its row `count`. Run it unfiltered first to learn the exact type
strings your tenant emits, then re-run with `&event_type=<type>` to
isolate one of them.

> Emails appear only as hashes (`email_hash`) per
> `INV-AUDIT-NO-RAW-PII`. To resolve back to a human, cross-reference
> with the team page (`https://humangr.com/corelink/en/customer/team`)
> while the membership is still active.

## Query 2 — when they fired

`GET /v1/audit/analytics/timeline` buckets the same window over time:

```bash
curl -sS \
  -H "Authorization: Bearer corelink_<env>_…" \
  "https://corelink-api.humangr.com/v1/audit/analytics/timeline?from=<epoch_ms>&to=<epoch_ms>&granularity=3600000"
```

`granularity` is the bucket width in milliseconds and defaults to
`3600000` (1 h). The route rejects a request with `400 Bad Request` when
`(to - from) / granularity` exceeds 1000 buckets, or when `granularity`
is above 24 h.

## Query 3 — pull the events themselves, with Merkle proofs

For high-stakes audit evidence (SOC 2, legal, customer audit), export the
window and verify the chain. The HTTP surface streams NDJSON — one
`{event, proof}` line per audit row plus a trailing manifest line — and
publishes the chain-head anchor in the
`X-CoreLink-Audit-Export-Chain-Head-Anchor` response header:

```http
GET /v1/audit/{tenant}/export?from=<epoch_ms>&to=<epoch_ms>
Authorization: Bearer corelink_<env>_…
```

The CLI drives the same route. `corelink audit` is the only audit verb
the CLI ships:

```bash
# Export the window, embedding + re-validating Merkle inclusion proofs.
corelink audit export \
  --tenant <tenant_id> \
  --since <epoch_ms> \
  --until <epoch_ms> \
  --include-merkle-proofs \
  --verify \
  --out ./audit-evidence

# Re-validate a previously exported JSON-LD file, offline.
corelink audit verify ./audit-evidence/<export-file>

# Re-verify the streaming NDJSON envelope straight off the export route.
corelink audit verify-ndjson \
  --url "https://corelink-api.humangr.com/v1/audit/<tenant_id>/export?from=<epoch_ms>&to=<epoch_ms>" \
  --bearer corelink_<env>_…
```

`--verify` is fail-CLOSED: every proof is re-validated before anything is
written. `verify-ndjson` exits `0` on full chain integrity and exits
`65` (sysexits `DATAERR`) when the server signals a chain break through
the `x-corelink-audit-export-aborted` HTTP trailer. To verify a file you
already hold, use `--ndjson <FILE>` together with
`--chain-head-anchor <HEX>` (the anchor value the server published at
export time) instead of `--url`.

See [audit chain](../../explanation/security/audit-chain.mdx) for the
verification walkthrough.

## Query 4 — tail recent events

For a quick look rather than an evidence bundle:

```bash
corelink audit tail \
  --tenant <tenant_id> \
  --filter event_type=<type> \
  --limit 50
```

`tail` is a windowed pull from the live export route (not a live follow).
The default window is the trailing hour and the default limit is 50
events. `--filter` takes one `key=value` predicate; the accepted keys are
`event_type`, `subject`, `source`, `region`, `tenant_id`,
`sequence_number` and `id`.

## Common forensic patterns

### "Did anyone bypass the dual-approval gate?"

Short answer: **they cannot**. The gate is fail-CLOSED and every denied
outcome is itself audited. If you see `corelink.admin.op.executed` with
`op_type` in the destructive set, an approver identity is present and an
HMAC signature was verified server-side. If you suspect tampering, run
the export with proofs (Query 3) to confirm the event is in the canonical
log head.

### "Who was Admin on 2026-04-22 at 18:31 UTC?"

The audit chain is your point-in-time source of truth. Export the window
up to that timestamp (Query 3), filter to the membership event types you
identified in Query 1, and replay the state — the team roster only
reflects the current snapshot.

### "An ex-employee claims they were never granted Admin."

Export the window covering the grant and keep the Merkle proofs
(Query 3). Dual-approval events carry both the actor and the dual
approver as a `user_id` + `email_hash` pair, plus an HMAC signature over
the canonical audit bytes, and the CloudEvent `source` is
`/corelink/admin/<region>` — so the record is non-repudiable and
region-attributed without ever storing a raw email.

## Retention

Audit retention defaults to 7 years on the Enterprise tier (aligned with
SOC 2 Type II). After tenant offboarding, customer-identifying fields are
pseudonymized but the chain entries themselves persist for the regulatory
window. See
[audit chain](../../explanation/security/audit-chain.mdx) for the
retention contract.
