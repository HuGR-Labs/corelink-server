# Leave CoreLink — closing your tenant

This guide covers what happens when you want to stop using CoreLink. It is
split into two parts because, today, only one of them is self-service:

1. **Exporting your data** — a real CLI command you can run right now.
2. **Closing the tenant** — currently a support-handled process. There is
   no dashboard button and no public API for this yet.

:::caution Tenant cancellation is not self-service yet
`POST /v1/tenant/{tenant_id}/offboard` does not exist. The 5-state
cancellation lifecycle (grace period → read-only → suspended →
cryptographic erasure) that would drive it is a real design — it ships as
an in-memory, pure-logic state machine in the `corelink-ops` crate — but it
is **not wired to any HTTP route, dashboard button, or database-backed
state**. There is no `X-Corelink-MFA-Step-Up` header, no self-service
revert, and no automatic timeline. **To close your tenant, email
[support@humangr.com](mailto:support@humangr.com)** with your tenant ID and
we will process it manually.
:::

:::note Individual data-subject rights are a different flow
If you are a **natural person** whose data we process and you want to
exercise your individual rights under LGPD Art. 18 / GDPR Art. 15-22 / CCPA
§1798.105, use the DSR self-service surface at `/privacy/dsr`, not this
guide. This guide is about **whole-tenant commercial offboarding**.
:::

For the legal posture (refund mechanics, MSA §10, DPA v1.0.0 §11), see the
[Terms of Service](/legal/terms) — §3 (fees and refunds) and §10 (term and
termination) — and our [Trust page](/trust/data-handling).

## Step 1 — Export what you can, before you ask us to close the account

The CLI ships a real export command today:

```bash
corelink tenant export \
  --tenant-id $TENANT_ID \
  --output ./corelink-export-$(date +%Y%m%d).json
```

**What this actually produces:** a single content-addressed **JSON**
manifest built from the two real server surfaces that exist for this
(`GET /v1/audit/:tenant/export` and `GET /v1/cas/:tenant`):

- Your full audit-chain slice, embedded as NDJSON, SHA-256-addressed.
- Your CAS blob **index** — every digest and size stored under your
  tenant — SHA-256-addressed.
- A bundle-level hash covering both components, for offline integrity
  verification.

**What it does not contain:** the CAS blob **bytes** themselves, an RBAC
roster, or a DPA acceptance receipt. There is no server-side bulk-export
endpoint that streams those today — the CLI cannot produce an archive it
has no route to build. If you need the raw bytes, fetch each blob
individually, before your tenant is closed:

```bash
corelink cas get <digest> -o ./blobs/<digest>
```

Verify the manifest's integrity any time after saving it:

```bash
corelink tenant verify-export --archive ./corelink-export-YYYYMMDD.json
```

This re-derives and checks every component hash plus the bundle hash
against the file's own contents. It proves the file was not corrupted or
tampered with after you saved it — it does **not** certify that the
manifest is a complete copy of everything CoreLink holds for your tenant,
because today it isn't one.

Because blob bytes, the RBAC roster, and the DPA receipt have no bulk
export path, **run this export (and fetch any blobs you need) before you
ask support to close your tenant** — once a tenant is closed there is no
documented self-service way to retrieve blobs afterward.

## Step 2 — Ask support to close the tenant

Email [support@humangr.com](mailto:support@humangr.com) with your tenant
ID and confirm you want to cancel. Because this is a manual process today
(not the automated grace-period / read-only / suspend / erase pipeline
described in the code's internal design), the exact timeline, any
read-only window, and the retention/erasure evidence you'll receive are
things support will confirm with you directly — ask them up front so you
know what to expect before your export window closes.
