# Batch operations

## When to use this guide

You need to push or pull many blobs from a shell script (for example, CI bootstrap)
and want maximum throughput without exceeding rate limits.

## Bulk upload with `xargs -P`

```bash
find ./outputs -type f -print0 \
  | xargs -0 -n1 -P 32 corelink put --output json \
  | jq -r '.digest' > digests.txt
```

`-P 32` is a safe default; server allows up to `256` per PAT.

## Bulk download

```bash
while read -r digest; do
  corelink get "$digest" -o "blobs/$digest"
done < digests.txt
```

For parallel downloads:

```bash
cat digests.txt \
  | xargs -n1 -P 32 -I {} corelink get {} -o "blobs/{}"
```

## Rate-limit handling

The CLI has exactly four exit codes (`0`/`1`/`2`/`65` — see
[Troubleshooting](./07-troubleshooting.mdx)); a rate limit is not
distinguished from any other failure — it exits `1` like every other
command error, with the reason on stderr. A retry loop can't branch on the
exit code alone; check stderr (or re-run unconditionally with a cap):

```bash
attempt=0
until corelink put "$file" 2>err.log; do
  attempt=$((attempt+1))
  if [[ $attempt -ge 5 ]]; then
    cat err.log >&2
    exit 1                          # give up, surface the last error
  fi
  sleep $((2 ** attempt))           # 2s, 4s, 8s, 16s — retries every failure,
                                     # not just rate limits, since the CLI
                                     # doesn't expose which kind occurred
done
```

In real scripts use one of the SDKs, whose HTTP exception types
(`CoreLinkRequestError.status_code == 429` in Python, an HTTP status check
in Go/JS) let you retry rate limits specifically instead of retrying every
failure.

## Pre-dedupe with `b3sum`

```bash
declare -A seen
while IFS= read -r file; do
  digest=$(b3sum "$file" | awk '{print $1}')
  [[ -n "${seen[$digest]:-}" ]] && continue
  seen[$digest]=1
  corelink put "$file" --digest "$digest"
done < files.txt
```

Cuts upload count by 60-90% on typical build outputs.
