# Action Cache via the CLI

## When to use this guide

You are debugging a build system's cache behaviour and need to confirm
whether a specific `Action` digest has an entry in CoreLink's Action Cache.
The CLI does **not** expose AC writes — those happen only through REAPI
clients (Bazel, Buck2, Pants, or one of the language SDKs).

For programmatic AC writes use:
- [Python AC](../sdk-python/04-action-cache)
- [Go AC](../sdk-go/04-action-cache)
- [JS/TS AC](../sdk-js/04-action-cache)

## Lookup via `stat`

```bash
corelink stat <action-digest>
```

If the digest belongs to an `ActionResult` payload, the output flags it:

```text
digest:    0123...cdef
size:      4096 bytes
kind:      action_result
exit_code: 0
stdout:    fedc...3210
ttl_left:  29d 14h
```

## JSON output

```bash
corelink stat <action-digest> --output json
```

```json
{
  "ok": true,
  "subcommand": "stat",
  "digest": "0123...cdef",
  "size_bytes": 4096,
  "kind": "action_result",
  "action_result": {
    "exit_code": 0,
    "stdout_digest": "fedc...3210",
    "ttl_seconds_remaining": 2551200
  }
}
```

## Listing recent entries

```bash
corelink ls --tenant acme-corp --prefix ab --limit 50 --output json
```

`--prefix` is a **client-side** filter applied to the returned page: it
keeps only blobs whose BLAKE3 `hash` starts with the given hex prefix (here,
`ab`). It is not sent to the server and does not scope by namespace — entries
are content-addressed hashes, so a human label like `ac/` would match
nothing. Use it to narrow a page to a specific hash range.

## Forcing a miss

To validate that a downstream tool falls back correctly, evict an entry via
the admin API (CLI does not expose AC writes or deletes):

```bash
curl -X DELETE \
  -H "Authorization: Bearer $CORELINK_PAT" \
  "https://corelink-api.humangr.com/v1/tenants/acme-corp/ac/<digest>"
```

See [admin API reference](../../reference/cli/index) for the full
endpoint catalogue.
