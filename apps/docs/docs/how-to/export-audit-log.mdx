# Export your CoreLink audit log

## When to use this guide

You're preparing evidence for one of:

- **SOC 2** Common Criteria **CC4.1** ("information used by the entity to support the functioning of internal control"), **CC7.2** (system monitoring + audit log integrity), or **CC8.1** (change-management audit trail).
- **GDPR Art. 15** (subject access), **Art. 20** (data portability), or a supervisory-authority **Art. 31** information request.
- **LGPD Art. 9** (subject access) or **Art. 18** (portability).
- An internal forensic investigation, regulator notice, or DPA-required disclosure.

CoreLink's audit chain is BLAKE3-linked, retained 7 years on R2 with Object Lock Governance Mode, and verified daily by a SEV-0 cron (see runbook `RB-AUDIT-CHAIN-001` — internal). This guide shows how to extract a tamper-proof slice of that chain for any compliance use.

## Prerequisites

- CoreLink CLI installed (`corelink version` ≥ this WI).
- Authenticated as your tenant ([01-authenticate](./sdk-cli/01-authenticate.mdx)).
- The tenant id you want to export (pseudonymous UUIDv7; the same id shown in the admin console).

## Minimal command

```bash
corelink audit export \
  --tenant 01939d8f-9c2e-7000-8000-000000000001 \
  --since 1714521600000 \
  --until 1717200000000 \
  --format json-ld \
  --include-merkle-proofs \
  --verify \
  --output ./evidence/
```

The exporter writes a content-addressed file:

```text
evidence/corelink-audit-01939d8f-1714521600000-1717200000000-7f3a...c4.jsonld
```

The 32-character hex segment is the BLAKE3-256 of the file contents — paste it into the Drata evidence ticket so a reviewer can confirm the file was not modified after upload.

## Flags

| Flag | What it does | When to set it |
|---|---|---|
| `--tenant <UUID>` | Per-tenant chain partition key. | Always — exports are tenant-scoped. |
| `--since <MS>` | Lower bound, Unix epoch ms. **Inclusive.** | Match the audit window your regulator asks for. |
| `--until <MS>` | Upper bound, Unix epoch ms. **Exclusive.** | One day past the last event you care about. |
| `--format <FORMAT>` | One of `json-ld` (default), `csv`, `parquet`. | See [Choosing a format](#choosing-a-format). |
| `--output <DIR>` | Output directory. File name is content-addressed. | Default is `.` (current dir). |
| `--include-merkle-proofs` | Embed an inclusion proof per event. | **Always for compliance evidence.** Required by `corelink audit verify`. |
| `--verify` | Re-validate every proof BEFORE writing. | **Always for compliance evidence.** Fail-CLOSED per CTRL-AUDIT-001. |

## Choosing a format

| Format | Best for | Trade-off |
|---|---|---|
| `json-ld` | SOC 2 evidence, regulator submission, machine-verifiable proof. Carries CloudEvents 1.0 envelope + full Merkle inclusion proof per row. | ~3x size of CSV; not spreadsheet-friendly. |
| `csv` | Compliance reviewer wants a spreadsheet. 10 canonical columns: `sequence_number, time_ms, tenant_id, region, subject, event_type, id, source, prev_hash, link_hash`. | Drops the Merkle sibling list (chain integrity still recomputable from `prev_hash` + `link_hash`, but offline `audit verify` needs the JSON-LD). |
| `parquet` | Long-term analytics + querying via Spark / DuckDB / Athena. Schema-attached JSON container; the audit-export-worker converts to true Apache Parquet on ingestion. | JSON intermediate today — pure Parquet emit lands with WI-S-09-EXPORT-WORKER. |

For SOC 2 / GDPR / LGPD evidence, **always pick `json-ld` with `--include-merkle-proofs --verify`**. The other formats are optional companions.

## Verifying an export offline

Customers, auditors, or regulators can re-verify any JSON-LD export without contacting CoreLink:

```bash
corelink audit verify ./evidence/corelink-audit-01939d8f-...-7f3a...c4.jsonld
```

The CLI:

1. Recomputes BLAKE3 of the file contents — that hash MUST match the prefix in the filename.
2. Recomputes the BLAKE3 chain link at every event position: `BLAKE3(prev_hash || JCS(event))`.
3. Walks each event's sibling list forward — every sibling's `prev_hash` MUST equal the previous sibling's `link_hash`.
4. The final sibling's `link_hash` MUST equal the manifest's `chain_head_at_export`.

If any step fails, the command exits non-zero with a `chain break` error pointing at the first divergent sequence. That's your forensic anchor — share it with `compliance@hugr.com` (we'll match it against the daily-verifier's checkpoint store).

## What gets exported

Each row carries the canonical CloudEvents 1.0 attribute set + CoreLink extensions:

```json
{
  "@type": "CoreLinkAuditEvent",
  "event": {
    "specversion": "1.0",
    "type": "dev.hugr.corelink.cas.put.v1",
    "source": "corelink/region/iad",
    "subject": "cas:put",
    "id": "01939d90-...",
    "time_ms": 1714521605000,
    "datacontenttype": "application/json",
    "tenant_id": "01939d8f-9c2e-7000-8000-000000000001",
    "region": "iad",
    "sequence_number": 42,
    "prev_hash": "7f3a8c2e...",
    "data": { ... }
  },
  "proof": {
    "prev_hash": "7f3a8c2e...",
    "link_hash": "c1d4e5...",
    "siblings": [
      { "sequence": 43, "link_hash": "..." },
      { "sequence": 44, "link_hash": "..." }
    ]
  }
}
```

**PII redaction:** the `data` payload is the post-redaction view (per `CTRL-PRIV-001`). Email addresses, IPs, and bearer tokens never enter the audit chain — the export inherits that property by construction.

## Troubleshooting

**Export hangs at "verify".** The `--verify` pass is O(events²) for the sibling walk; a 1M-event window takes ~30s on commodity hardware. For very large windows, split into monthly chunks and concatenate the JSON-LD `events` arrays — chain head continuity is enforced via the manifest.

**Verify reports "chain break".** Stop — that's a SEV-0 signal. Open a support ticket at [`support@hugr.com`](mailto:support@hugr.com) **with the export file attached**. Internal triage runbook: `RB-AUDIT-EXPORT-INTEGRITY`.

**"production server-side endpoint not yet wired".** Today the CLI requires `--fixture` for offline / regression mode while the CF Worker `GET /v1/audit/export/window` impl lands. Production wiring goes live in the audit-export-worker rollout — see `ROADMAP-TO-GA.md` §4 R-4.
