# Quickstart — sign up to first cache hit in 10 minutes

**Goal:** sign up, install the CLI, verify connectivity with `corelink doctor`,
wire your Bazel repo, and watch cache HITs land on the second build.
**Total budget: ≤ 10 minutes for an experienced engineer.**

Some `corelink` CLI subcommands shown here (`doctor`, and the config helpers)
ship in an upcoming CLI release — the docs reflect the planned UX ahead of the
binary. The `.bazelrc` remote-cache configuration in Step 4 works today against
the live REAPI v2 endpoint and needs no CLI.

:::tip No credit card required
A starter account is free up to 10 GB. The sign-up wizard provisions
your tenant, region, and a starter PAT server-side — no billing step.
:::

---

## Before you start

- **Bazel 7+** installed and on `PATH`
- A browser for sign-up (Clerk-backed, Google / GitHub / email accepted)
- macOS, Linux, or Windows (WSL2 recommended for Windows)

---

## Step 1 — Sign up <span style={{color:"var(--ifm-color-emphasis-600)"}}>(~1 min)</span>

1. Open **[https://humangr.com/corelink](https://humangr.com/corelink)** in your browser.
2. Complete the 2-step signup wizard (pick your primary region — `ord` is
   US-Central and a safe default for most teams).
3. The wizard drops you on the **`/welcome`** page where your starter PAT
   is displayed **exactly once**. Copy it now before closing the tab.
   It looks like: `corelink_pat_xxx…xxx`

:::warning Copy your PAT from /welcome — it is shown once
If you close the tab without copying, regenerate via **Settings → Access
tokens → Regenerate**. Never paste a real PAT into shared docs, Slack,
or source code. Store it in a secret manager (`direnv`, `1password`,
`op`) or your CI provider's secret store.
:::

---

## Step 2 — Install the CLI <span style={{color:"var(--ifm-color-emphasis-600)"}}>(~1 min)</span>

Run the one-liner install script. Pass the PAT you copied in Step 1 and
your chosen region.

```bash
curl -fsSL https://corelink-get.humangr.com | sh -s -- \
  --token=corelink_pat_xxx…xxx \
  --region=ord
```

The script:
1. Detects your platform (macOS arm64/amd64, Linux amd64/arm64).
2. Downloads the statically-linked `corelink` binary to `/usr/local/bin`
   (falls back to `~/.local/bin` if `/usr/local/bin` is not writable).
3. Writes `~/.config/corelink/config.toml` with your PAT and tenant ID.
4. Runs `corelink ping` against the closest CAS region and prints the RTT.

Expected output:

```text
corelink-get: detected darwin/arm64
corelink-get: downloading corelink 0.1.0 ...
corelink-get: installed /usr/local/bin/corelink
corelink-get: writing ~/.config/corelink/config.toml
corelink ping: ok (region=cf-ord, rtt=22ms, tenant=acme-prod)
```

If `corelink ping` prints `ok`, you're good. Jump straight to Step 3.

## Step 3 — `corelink doctor` <span style={{color:"var(--ifm-color-emphasis-600)"}}>(~30 s)</span>

`corelink doctor` runs 8 connectivity and auth checks in sequence and
tells you exactly what is wrong if anything fails:

```bash
corelink doctor
```

Healthy output:

```text
[1/8] config file found              ✓  ~/.config/corelink/config.toml
[2/8] PAT format valid               ✓  prefix=corelink_pat, length=ok
[3/8] PAT not expired                ✓  ttl=365d (tenant=acme-prod)
[4/8] DNS resolution                 ✓  corelink-api.humangr.com → <IP>
[5/8] TLS handshake                  ✓  TLSv1.3, 0-RTT=off
[6/8] API ping (HTTP/2)              ✓  200 OK (rtt=18ms, region=cf-ord)
[7/8] gRPC channel (REAPI v2)        ✓  capabilities handshake ok
[8/8] tenant write permission        ✓  can upload 1-byte probe blob
8/8 checks PASS
```

If any check shows `✗`, the output includes a remediation hint. The
most common failures are listed in the [Troubleshooting](#troubleshooting)
section below.

:::note WP-2.1 / CLI release note
`corelink doctor` ships in the next CLI release. If your installed
binary predates that release, run `corelink ping` as a lighter
substitute (checks items 4–6 only).
:::

## Step 4 — Wire your `.bazelrc` <span style={{color:"var(--ifm-color-emphasis-600)"}}>(~30 s)</span>

`cd` into the root of your Bazel repository and add the CoreLink REAPI v2
remote-cache lines to your `.bazelrc` (see the committed reference config at
[`apps/examples/bazel/.bazelrc`](https://github.com/HumanGuardrail/corelink-server/blob/main/apps/examples/bazel/.bazelrc)):

```ini
build --remote_cache=https://corelink-api.humangr.com/bazel/v2
build --remote_instance_name=${CORELINK_TENANT}
build --remote_header=Authorization=Bearer ${CORELINK_PAT}
build --remote_upload_local_results=true
```

Export your PAT and tenant UUID in the same shell (or your CI secret store):

```bash
export CORELINK_PAT="corelink_pat_XXXXXXXXXXXX"
export CORELINK_TENANT="acme-prod"
```

:::warning Native `bazel --remote_cache` support: in progress
CoreLink's wired Bazel surface is the **REAPI v2 ByteStream** scheme at
`/bazel/v2/<tenant>` and requires a REAPI/ByteStream-compatible client. A stock
plain-HTTP `--remote_cache` alias (`/cas/<hash>`) is being built and is not yet
live — it currently returns 404. See the
[Bazel integration guide](../integrations/bazel) for details.
:::

:::tip Commit .bazelrc, keep the PAT out of git
Add `.bazelrc` to git so teammates share the config. Keep `CORELINK_PAT` in your
environment or a secret manager — never commit it.
:::

## Step 5 — First build (cold cache) <span style={{color:"var(--ifm-color-emphasis-600)"}}>(~3 min)</span>

Run your Bazel build for the first time. This populates the remote cache.

```bash
bazel build //...
```

You will see Bazel's normal build output. Nothing special happens yet —
this is the **cold** run that uploads your build artifacts.

---

## Step 6 — Second build (cache HITs) <span style={{color:"var(--ifm-color-emphasis-600)"}}>(~1 min)</span>

Run the same build a second time (or have a teammate clone and build on
a fresh machine):

```bash
bazel build //...
```

This time Bazel fetches from the CoreLink cache instead of rebuilding.
You will see `(cache hit)` annotations in the build output:

```text
INFO: 42 processes: 38 remote cache hit, 4 internal.
```

That `remote cache hit` count is the **activation event** — your first
successful CoreLink cache hit. The [CoreLink dashboard](https://humangr.com/corelink)
surfaces this as `first_cache_hit` on your tenant timeline.

:::note Why build twice?
The first build populates the cache (MISS → UPLOAD). The second build
reads from it (HIT → DOWNLOAD). This two-run pattern is intentional —
the cache is most valuable for your CI pipeline's second run and for
teammates who build the same commit.
:::

## Troubleshooting

Common failure modes and their fixes:

### Regional mismatch — high latency or `UNAVAILABLE` gRPC errors

**Symptom:** `corelink doctor` step 6 shows RTT > 200 ms, or `bazel build` logs `UNAVAILABLE: connection closed`.

**Fix:** your `.bazelrc` is pointing to the wrong region endpoint. Run
`corelink doctor` and note the `region=` in the API ping output. Then:

```bash
corelink config set defaults.region <correct-region>
```

Available regions: `ord` (US-Central), `iad` (US-East), `lhr` (EU-West),
`nrt` (AP-Northeast), `syd` (AP-Southeast).

### Token not set — `UNAUTHENTICATED` on every Bazel action

**Symptom:** Bazel logs `UNAUTHENTICATED` on remote-cache actions.

**Fix:** The `CORELINK_PAT` env var is not exported. Verify:

```bash
echo $CORELINK_PAT
# should print: corelink_pat_xxx…xxx
```

If empty, either re-export it or ensure it is written to
`~/.config/corelink/config.toml` (the one-liner installer does this
automatically):

```bash
corelink config set auth.pat "corelink_pat_xxx…xxx"
```

### `.bazelrc` duplicate-line warning

**Symptom:** Bazel prints `WARNING: Duplicate rc option: --remote_cache`.

**Fix:** `corelink bazel-init` was run twice without `--force`, or your
`.bazelrc` already contained remote-cache lines. Remove the duplicates:

```bash
# Preview what would be removed:
grep -n "remote_cache\|remote_header\|remote_upload" .bazelrc

# Remove duplicate lines manually, keeping one copy of each.
```

Re-run `corelink doctor` to confirm the auth and connectivity checks
still pass after the edit.

### `corelink doctor` check 8 fails — `PERMISSION_DENIED` on probe blob

**Symptom:** `[8/8] tenant write permission  ✗  PERMISSION_DENIED`.

**Fix:** Your PAT is read-only or belongs to a different tenant. Confirm:

```bash
corelink config get defaults.tenant_id
# should match the tenant shown in the dashboard
```

If the tenant ID is wrong, update it:

```bash
corelink config set defaults.tenant_id <your-tenant-id>
```

If you see `PERMISSION_DENIED` even with the correct tenant, regenerate
your PAT from **Settings → Access tokens** with `write` scope.
