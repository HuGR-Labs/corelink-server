# Verify cache hit ratio

The tutorial is complete only when you can prove the cache is working. This page collects three independent checks.

## A. Bazel BES / Buck2 logs

Bazel:

```bash
bazel build //:hello 2>&1 | grep -E "remote cache hit|disk cache hit|processes:"
# INFO: 12 processes: 11 remote cache hit, 1 internal.
```

Buck2:

```bash
buck2 build //:hello --show-output 2>&1 | grep -iE "cache hits"
```

A 100% green build that prints **0 processes** is the strongest single signal — Bazel/Buck2 short-circuited every action through the cache.

## B. CLI microbenchmark

Run the built-in `corelink bench` (writes a deterministic 16 KiB blob 50× then reads it 50×):

```bash
corelink bench --put 50 --get 50
# put p50=8.2ms  p95=13.1ms  err=0/50
# get p50=2.1ms  p95= 4.8ms  err=0/50 hit_ratio=100%
```

`hit_ratio=100%` on the read pass confirms the second-and-later requests are served from the cache.

## C. Admin UI dashboard

1. Open `https://humangr.com/corelink/orgs/<your-org>/observability`.
2. Pick **Cache hit ratio (5m, by tenant)**.
3. Trigger a fresh build (`bazel clean && bazel build //...`).
4. The series should jump to ~100% after the first warm pass.

The hit ratio Grafana panel is documented in `dashboards/cache_hit_ratio.json`; alert thresholds live in `infra/alerts/cache_hit_ratio.yaml`.

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `hit_ratio=0%` on second build | local disk cache served the request, never touched remote | `bazel clean` and set `build --noremote_accept_cached=false` to force remote read |
| `UNAUTHENTICATED` errors | PAT expired or wrong env | Re-run `corelink doctor --check-auth`, regenerate PAT |
| `COR_CAS_DIGEST_MISMATCH` | bytes corrupted in transit | `client_verify` rejected the blob — file an issue, do not disable verify |
| Slow `p95 > 50ms` | your tenant's region is far from your CI runners | **Not a client-side setting.** Requests are routed to your tenant's `primary_region`, fixed when the tenant is provisioned; the edge looks it up server-side and strips any client-supplied region, so no URL or `.bazelrc` flag can override it. If your tenant is in the wrong region, contact support@humangr.com — moving it is a data-residency change, not a config change. |
