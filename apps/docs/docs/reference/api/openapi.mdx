# REST API — OpenAPI 3.1

CoreLink exposes two API surfaces:

- **REAPI v2 (gRPC)** — high-throughput CAS / AC / ByteStream / Capabilities.
  Documented under [REAPI v2 reference](../reapi/index).
- **REST (this page)** — customer onboarding, privacy (DSR + consent + DPA),
  Stripe billing webhook, admin operations, and ops endpoints.

The canonical contract is
[`openapi/corelink-v1.yaml`](https://github.com/humangr-labs/corelink-server/blob/main/openapi/corelink-v1.yaml)
in the server monorepo. The static asset shipped with this docs site
mirrors that file byte-for-byte and is gated by the
`openapi-validate.yml` workflow on every PR.

## Authentication

| Scheme | Where | Used for |
| --- | --- | --- |
| `BearerPAT` | `Authorization: Bearer <PAT>` | Programmatic API access (default). |
| `ClerkSessionCookie` | `__session` cookie | Browser-driven onboarding flow. |
| `StripeSignature` | `Stripe-Signature` header | The Stripe webhook ingestion route only. |

Every admin mutation also requires an `X-Admin-Operation-Reason` header
captured into the audit envelope.

## Stability contract

The `v1` prefix is **public and semver-compatible**. Breaking changes
require a new path prefix (`/v2/...`); the CI gate
(`openapi-validate.yml`) runs `oasdiff breaking` against the base
branch on every pull request and fails unless a `breaking-api-ok`
label is applied with reviewer sign-off.
