# `corelink get`

Download a blob by digest. The CLI always performs client-side BLAKE3
verification (CTRL-CAS-002); there is no `--no-verify` flag.

## Synopsis

```bash
corelink get <DIGEST> [-o <FILE>] [--output <FORMAT>]
```

## Arguments

| Arg | Required | Description |
|---|---|---|
| `<DIGEST>` | yes | 64-character BLAKE3 hex digest. |

## Flags

| Flag | Required | Default | Description |
|---|---|---|---|
| `-o`, `--out` | no | stdout | Destination file. Verification happens before any bytes are written, so a verify failure never leaves a partial file — nothing is written at all. |
| `--output` | no | `text` | `text` or `json`. JSON is emitted on stderr; bytes go to stdout/`-o`. |

## Examples

To a file:

```bash
corelink get 0123...cdef -o ./restored.bin
```

To stdout (binary):

```bash
corelink get 0123...cdef > ./restored.bin
```

JSON status (bytes still go to `-o`):

```bash
corelink get 0123...cdef -o ./out.bin --output json
```

## JSON schema

```json
{
  "ok": true,
  "subcommand": "get",
  "digest": "0123...cdef",
  "size_bytes": 1048576,
  "verify_ms": 23
}
```

## Exit codes

The CLI has exactly four exit codes, shared by every subcommand:

| Code | Meaning |
|---|---|
| `0` | Downloaded + verified. |
| `1` | Any failure — network, auth, not found, verify mismatch. Read the `error: ...` message on stderr for which. |
| `2` | Argument error. |
| `65` | Reserved for `corelink audit verify-ndjson --url` mid-stream abort only — not used by `get`. |
