# Architecture overview

**Understanding-oriented.** This page explains *why* CoreLink is built
the way it is. For *how* to use it, see [Como fazer](/how-to/); for the
*API surface*, see [Referência](/reference/).

CoreLink is a **multi-tenant, content-addressable cache and
storage-governance platform** built on Cloudflare (Workers, Durable
Objects, Containers, R2, and D1). Every object is keyed by the SHA-256
of its bytes, which is the single design decision that the rest of the
system follows from — it is summarised below and expanded in the topics
that follow.

- **Content addressing** makes integrity verification free (the key
  *is* the checksum) and deduplication automatic (identical bytes
  collapse to one stored object), while keeping tenants isolated by key
  namespace rather than by a per-tenant encryption boundary.
- **Cloudflare-native placement** keeps reads and writes at the edge: a
  Durable Object fronts each tenant's cache coordination, R2 holds the
  bytes with zero egress fees, and the heavier execution surface runs in
  a Container.
- **Governance is first-class**, not bolted on: storage quotas, tier
  entitlements, audit chaining, and data-subject-request erasure are
  modelled in the same data plane as the cache itself.

## Topics this page will cover

1. **Why content-addressable?** Hash-keyed storage gives us trivial
   dedup, free integrity verification, and tenant isolation by key
   namespace rather than by encryption boundary.
2. **How dedup works.** Chunking strategy (rolling hash + fixed-size
   fallback), chunk-level reference counting, and tenant-isolated GC.
3. **Multi-region read-path.** R2 region pinning, fail-open vs
   fail-closed semantics, and the consistency model.
4. **BYOK envelope model.** Per-tenant DEK wrapped by customer KEK in
   their KMS — CoreLink never sees plaintext keys.
