# Download a blob

## When to use this guide

You have a BLAKE3 digest and want to materialize the bytes on disk or pipe
them into another command. The CLI verifies the digest client-side by
default (CTRL-CAS-002).

## Prerequisites

- A known BLAKE3 digest.
- Authentication configured.

## To a file

```bash
corelink get 0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef \
  -o ./restored.tar
```

If verification fails, the CLI exits `1` with an
`error: Client verify FAILED: ...` message. The download is fully buffered
in memory before verification, so nothing is ever written to `-o` for a
failed verify — there is no partial file to clean up.

## To stdout

```bash
corelink get <digest> > ./restored.tar
```

stdout is binary; do not redirect to a tty.

## Verification

The CLI downloads the full response body, then hashes it and compares the
result to the requested digest before writing anything to disk or stdout.
A mismatch always results in:

- Exit code `1`.
- `error: Client verify FAILED: expected blake3:<requested>, got blake3:<actual>. ...` on stderr.
- No output file created (verification happens before the write, not after).

## JSON output

```bash
corelink get <digest> -o ./out.bin --output json
```

```json
{
  "ok": true,
  "subcommand": "get",
  "digest": "0123...cdef",
  "size_bytes": 1048576,
  "verify_ms": 23
}
```

## Opting out of verification

The CLI does **not** expose a `--no-verify` flag; opt-out is only available
to SDK callers running benchmarks (and emits a warning log). For ad-hoc
performance measurement use `corelink bench`.

## Exit codes

The CLI has exactly four exit codes, shared by every subcommand:

| Code | Meaning |
|---|---|
| `0` | Downloaded + verified |
| `1` | Any failure — network, auth, not found, verify mismatch. Read the `error: ...` message on stderr for which. |
| `2` | Argument/flag error, or the `--pat` flag was rejected (CTRL-CRED-001) |
| `65` | Reserved for `corelink audit verify-ndjson --url` mid-stream abort only — not used by `get` |
