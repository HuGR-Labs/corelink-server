# Invite a team member

## When to use this guide

You're an `Owner` or `Admin` on a CoreLink tenant and you want to add a
teammate. This guide walks through Clerk SSO setup, the invite flow, and
which role to pick.

## Prerequisites

- You are signed in as `Owner` or `Admin` on the target tenant.
- The invitee has (or can create) a Clerk-backed identity at the same SSO
  domain your tenant uses.
- You have decided which role to assign (see decision tree below).

## Pick the right role

| Their job                                                      | Role to assign   |
|----------------------------------------------------------------|------------------|
| Engineer who reads/writes the cache from CI or local dev       | `Developer`      |
| Tech lead / SRE who needs to mint tokens or read audit log     | `Admin`          |
| Co-founder / Head of Engineering who also owns billing         | `Owner`          |
| External auditor or read-only dashboard consumer               | `Viewer`         |

When in doubt, pick the **least-privileged** role that lets them do their
job. You can always promote later. Demotion is also one click.

> **A note on `Owner`:** Only assign `Owner` if the person should see the
> invoice and be able to act as the second approver for destructive
> operations. Most engineering hires should start as `Admin` or
> `Developer`.

## Step 1 — Confirm Clerk SSO is configured

CoreLink delegates authentication to Clerk. Before inviting, make sure:

1. Your Clerk application is wired to CoreLink (one-time tenant setup —
   done at signup; if you skipped this, contact support).
2. Your invitee's email domain is on your Clerk allowlist (if you use
   domain-restricted sign-up).
3. MFA is enforced for `Owner` and `Admin` roles. **The dual-approval gate
   requires MFA freshness ≤ 30 minutes** for any approver
   (`MFA_MAX_AGE_MS` in
   `crates/corelink-dual-approval/src/gate.rs`). If MFA isn't enabled for
   the user, they can sign in but they cannot approve destructive ops.

## Etapa 2 — Enviar o convite

A gestão de equipe fica no painel, em
[https://humangr.com/corelink/en/customer/team](https://humangr.com/corelink/en/customer/team):

1. Abra a página **Team**.
2. Em **Invite a teammate**, informe o e-mail da pessoa convidada.
3. Escolha o papel em **Role** (veja a tabela acima).
4. Clique em **Send invite**.

Nos bastidores:

- O assento é registrado na hora como uma linha `team_member` com status
  `invited` — é isso que a lista **Pending invitations** mostra.
- Só é armazenado um hash pseudonimizado do e-mail (sem espaços nas
  pontas e em minúsculas); o endereço em texto puro nunca é persistido.
- Uma linha de auditoria visível ao cliente, com tipo de evento
  `team.invited`, é gravada *antes* da linha do assento — assim um convite
  nunca é efetivado sem o registro de auditoria correspondente. O detalhe
  dela cita apenas o papel, nunca o endereço.

### Automatizando pela API HTTP

**Não existe comando `corelink` na CLI para gestão de equipe** — os dois
caminhos suportados são o painel acima e a API HTTP abaixo. A API aceita
tanto um PAT do CoreLink quanto a sua sessão autenticada do Clerk, então
dá para automatizar convites na CI com um PAT:

```bash
curl -X POST https://corelink-api.humangr.com/v1/customer/team/invite \
  -H "Authorization: Bearer $CORELINK_PAT" \
  -H "Content-Type: application/json" \
  -d '{"email":"teammate@example.com","role":"Developer"}'
```

Convidar (e remover) um membro é **exclusivo de owner/admin** — um token
`Developer` ou `Viewer` recebe `403` aqui, por qualquer um dos caminhos.

## Etapa 3 — A pessoa convidada aceita o convite

1. Ela entra no CoreLink — ou se cadastra e configura o MFA, se for a
   primeira vez — usando **o mesmo endereço de e-mail que você convidou**.
2. O Clerk redireciona de volta para o CoreLink.
3. O CoreLink localiza o assento pendente pelo hash do e-mail, vincula-o
   ao `user_id` real dela e muda o status de `invited` para `active`. O
   papel escolhido no convite é preservado.

A partir daí ela aparece em **Members**, e não mais em
**Pending invitations**.

## Etapa 4 — Conferir o papel

Na página **Team**, a tabela **Members** lista todo mundo que tem acesso e
o papel de cada pessoa; quem foi convidado mas ainda não entrou aparece em
**Pending invitations**.

Para conferir o mesmo por script:

```bash
curl https://corelink-api.humangr.com/v1/customer/team \
  -H "Authorization: Bearer $CORELINK_PAT"
```

A resposta traz um array `members`; cada item tem o `user_id`, o `role`, o
`joined_at` e o `status` do membro (`invited` até a pessoa entrar, depois
`active`). Existe também um campo `email`, mas ele volta como um
marcador — veja a nota abaixo.

> **O CoreLink nunca armazena o e-mail em texto puro.** O convite persiste
> apenas um hash pseudonimizado do endereço (sem espaços nas pontas e em
> minúsculas, `CTRL-PRIV-001`), e é esse hash que serve de chave para
> localizar o convite quando a pessoa entra. As linhas de auditoria seguem
> a mesma regra (`INV-AUDIT-NO-RAW-PII`): o registro `team.invited` guarda
> o papel, não o endereço.

## Etapa 5 — Emitir o primeiro PAT (Developer ou acima)

Usuários `Developer`, `Admin` e `Owner` podem emitir os próprios PATs na
página **API keys** do painel
(`https://humangr.com/corelink/en/customer/keys`); `Viewer` não pode.

Se você preferir emitir por conta própria um token de conta de serviço
para a CI, use a API de chaves — de novo, não há CLI para isso:

```bash
curl -X POST https://corelink-api.humangr.com/v1/customer/keys \
  -H "Authorization: Bearer $CORELINK_PAT" \
  -H "Content-Type: application/json" \
  -d '{"name":"ci-service-account","scopes":["cache:r","cache:w","cache:find-missing"]}'
```

O corpo da requisição é apenas um nome e uma lista de escopos — não existe
campo para emitir um token *em nome de outra pessoa*, então um token de
conta de serviço pertence ao tenant, não a quem você convidou. Veja a
[referência de permissões](/reference/rbac/permissions) para todos os
escopos que você pode conceder.

O segredo do token é exibido **uma única vez**. Entregue-o à pessoa
convidada pelo seu gerenciador de segredos (1Password, Doppler, o cofre de
segredos da sua CI); ele é irrecuperável depois desta etapa. Um token pode
ser revogado a qualquer momento com
`POST /v1/customer/keys/{pat_id}/revoke`.

## Armadilhas comuns

1. **"Ela entrou, mas continua em Pending invitations."** O assento só
   muda para `active` quando o endereço informado pelo Clerk coincide com
   o endereço convidado, depois de normalizado (sem espaços nas pontas e
   em minúsculas). Um login com outro endereço — um alias, uma conta
   pessoal — não mexe no assento convidado. Convide o endereço que ela
   realmente usa para entrar.
2. **"Meu convite voltou com 403."** Três verificações acontecem, nesta
   ordem: um convite com o papel `Owner` é sempre rejeitado (um tenant tem
   exatamente um owner, quem o criou); quem chama precisa ser `Owner` ou
   `Admin`; e só o `Owner` pode convidar um papel privilegiado (`Admin`).
3. **"A pessoa convidada diz que não consegue aprovar uma operação
   destrutiva."** Verifique: (a) se ela é `Admin` ou `Owner`; (b) se o MFA
   está habilitado na conta dela; (c) se o último desafio de MFA foi nos
   últimos 30 minutos (`MFA_MAX_AGE_MS`).
