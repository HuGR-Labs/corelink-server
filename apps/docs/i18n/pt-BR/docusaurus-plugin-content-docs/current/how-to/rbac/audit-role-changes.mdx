# Auditar mudanças de papel

## Quando usar este guia

Você precisa responder perguntas como:

- "Quem promoveu a Alice de Developer para Admin, e quando?"
- "Mostre todas as concessões do papel Owner neste tenant nos últimos 90 dias."
- "O gate de dupla aprovação disparou no rollback que fizemos na terça passada?"

Este guia mostra como consultar a cadeia de auditoria do CoreLink em
busca de mudanças de papel e de eventos de dupla aprovação.

> A gestão de time e de papéis em si é **apenas painel + API HTTP** —
> não existe CLI para isso. Gerencie membros em
> `https://humangr.com/corelink/en/customer/team`, ou pelas rotas
> `GET /v1/customer/team`, `POST /v1/customer/team/invite`
> (`{email, role}`) e `DELETE /v1/customer/team/{user_id}` (convidar e
> remover são exclusivos de owner/admin). Ler a trilha de auditoria — o
> assunto deste guia — é o que fazem as rotas `/v1/audit/*` e o comando
> `corelink audit`.

## Pré-requisitos

- Você possui o escopo `admin:audit`.
- Um PAT com esse escopo
  (`Authorization: Bearer corelink_<env>_…`), ou uma sessão Clerk no
  painel. Emita e liste PATs com `POST /v1/customer/keys`
  (`{name, scopes[]}`) e `GET /v1/customer/keys`; revogue com
  `POST /v1/customer/keys/{pat_id}/revoke`.
- URL base da API: `https://corelink-api.humangr.com`.

## A cadeia de auditoria em um parágrafo

Toda mutação administrativa ou de plano de dados é gravada em um log
append-only estruturado como uma árvore de Merkle RFC 6962. Os eventos
relevantes para papéis vivem em dois fluxos:

1. `admin_op_log` — o log em tabela de toda operação protegida por dupla
   aprovação, com `outcome` ∈ `{approved, denied_missing, denied_sig,
   denied_caller_eq, denied_collusion, denied_mfa_stale,
   denied_approver_not_admin, denied_nonce_replay, denied_clock_skew}`
   (`crates/corelink-dual-approval/src/types.rs::ApprovalOutcome`).

2. A cadeia de auditoria CloudEvent — o log mais amplo. Os dois tipos de
   evento fixados em constantes do código-fonte são
   `corelink.admin.op.executed` e `corelink.admin.op.denied`
   (`crates/corelink-dual-approval/src/audit.rs`). Mutações de membros e
   de papéis caem no mesmo fluxo do tenant, mas este guia não imprime as
   strings de `type` delas: descubra os valores exatos que seu tenant
   emite com a Consulta 1 abaixo e então filtre por eles.

Ambos são lidos pelas rotas HTTP `/v1/audit/*` e pelo CLI
`corelink audit`. O
[explicativo da cadeia de auditoria](../../explanation/security/audit-chain.mdx)
cobre o mecanismo subjacente (provas de Merkle, retenção etc).

## Consulta 1 — quais tipos de evento ocorreram na janela

`GET /v1/audit/analytics/event-count` agrega as linhas de auditoria do
tenant por `type` de CloudEvents no intervalo `[from, to)` (em
**milissegundos** de epoch Unix), com um filtro opcional `event_type` de
correspondência exata:

```bash
curl -sS \
  -H "Authorization: Bearer corelink_<env>_…" \
  "https://corelink-api.humangr.com/v1/audit/analytics/event-count?from=<epoch_ms>&to=<epoch_ms>"
```

A resposta traz um array `buckets` — uma entrada por `event_type`
distinto observado na janela, cada entrada associando esse `event_type`
à sua contagem (`count`) de linhas. Rode primeiro sem filtro para
descobrir as strings de tipo exatas que seu tenant emite e, depois,
repita com `&event_type=<type>` para isolar uma delas.

> E-mails aparecem apenas como hashes (`email_hash`), conforme
> `INV-AUDIT-NO-RAW-PII`. Para voltar a uma pessoa, cruze com a página do
> time (`https://humangr.com/corelink/en/customer/team`) enquanto o vínculo
> ainda estiver ativo.

## Consulta 2 — quando ocorreram

`GET /v1/audit/analytics/timeline` distribui a mesma janela em baldes ao
longo do tempo:

```bash
curl -sS \
  -H "Authorization: Bearer corelink_<env>_…" \
  "https://corelink-api.humangr.com/v1/audit/analytics/timeline?from=<epoch_ms>&to=<epoch_ms>&granularity=3600000"
```

`granularity` é a largura do balde em milissegundos e tem padrão
`3600000` (1 h). A rota rejeita a requisição com `400 Bad Request`
quando `(to - from) / granularity` passa de 1000 baldes, ou quando
`granularity` é maior que 24 h.

## Consulta 3 — extrair os próprios eventos, com provas de Merkle

Para evidência de auditoria de alto risco (SOC 2, jurídico, auditoria de
cliente), exporte a janela e verifique a cadeia. A superfície HTTP
transmite NDJSON — uma linha `{event, proof}` por linha de auditoria mais
uma linha final de manifesto — e publica a âncora de cabeça de cadeia no
cabeçalho de resposta
`X-CoreLink-Audit-Export-Chain-Head-Anchor`:

```http
GET /v1/audit/{tenant}/export?from=<epoch_ms>&to=<epoch_ms>
Authorization: Bearer corelink_<env>_…
```

O CLI usa a mesma rota. `corelink audit` é o único verbo de auditoria que
o CLI oferece:

```bash
# Export the window, embedding + re-validating Merkle inclusion proofs.
corelink audit export \
  --tenant <tenant_id> \
  --since <epoch_ms> \
  --until <epoch_ms> \
  --include-merkle-proofs \
  --verify \
  --out ./audit-evidence

# Re-validate a previously exported JSON-LD file, offline.
corelink audit verify ./audit-evidence/<export-file>

# Re-verify the streaming NDJSON envelope straight off the export route.
corelink audit verify-ndjson \
  --url "https://corelink-api.humangr.com/v1/audit/<tenant_id>/export?from=<epoch_ms>&to=<epoch_ms>" \
  --bearer corelink_<env>_…
```

`--verify` é fail-CLOSED: toda prova é revalidada antes de qualquer
escrita. `verify-ndjson` sai com `0` quando a integridade da cadeia é
total e sai com `65` (`DATAERR` do sysexits) quando o servidor sinaliza
uma quebra de cadeia pelo trailer HTTP
`x-corelink-audit-export-aborted`. Para verificar um arquivo que você já
tem, use `--ndjson <FILE>` junto de `--chain-head-anchor <HEX>` (o valor
da âncora publicado pelo servidor no momento do export) em vez de
`--url`.

Veja a [cadeia de auditoria](../../explanation/security/audit-chain.mdx)
para o passo a passo de verificação.

## Consulta 4 — acompanhar eventos recentes

Para uma olhada rápida, em vez de um pacote de evidências:

```bash
corelink audit tail \
  --tenant <tenant_id> \
  --filter event_type=<type> \
  --limit 50
```

`tail` é uma leitura por janela da rota de export ao vivo (não é um
follow contínuo). A janela padrão é a última hora e o limite padrão é de
50 eventos. `--filter` aceita um predicado `key=value`; as chaves
aceitas são `event_type`, `subject`, `source`, `region`, `tenant_id`,
`sequence_number` e `id`.

## Padrões forenses comuns

### "Alguém burlou o gate de dupla aprovação?"

Resposta curta: **não é possível**. O gate é fail-CLOSED e todo desfecho
negado é ele próprio auditado. Se você vir `corelink.admin.op.executed`
com `op_type` no conjunto destrutivo, há uma identidade de aprovador
presente e uma assinatura HMAC foi verificada no servidor. Se suspeitar
de adulteração, rode o export com provas (Consulta 3) para confirmar que
o evento está na cabeça canônica do log.

### "Quem era Admin em 22/04/2026 às 18:31 UTC?"

A cadeia de auditoria é sua fonte de verdade ponto-a-ponto no tempo.
Exporte a janela até aquele instante (Consulta 3), filtre pelos tipos de
evento de membro que você identificou na Consulta 1 e reproduza o estado
— a lista do time reflete apenas o retrato atual.

### "Um ex-funcionário alega que nunca recebeu Admin."

Exporte a janela que cobre a concessão e guarde as provas de Merkle
(Consulta 3). Eventos de dupla aprovação carregam tanto o ator quanto o
aprovador duplo como um par `user_id` + `email_hash`, além de uma
assinatura HMAC sobre os bytes canônicos de auditoria, e o `source` do
CloudEvent é `/corelink/admin/<region>` — de modo que o registro é
inegável e atribuído a uma região sem jamais armazenar um e-mail em
texto claro.

## Retenção

A retenção de auditoria tem padrão de 7 anos no tier Enterprise
(alinhado ao SOC 2 Type II). Após o offboarding do tenant, os campos que
identificam o cliente são pseudonimizados, mas as entradas da cadeia
persistem durante a janela regulatória. Veja a
[cadeia de auditoria](../../explanation/security/audit-chain.mdx) para o
contrato de retenção.
