# Rollenänderungen auditieren

## Wann Sie diese Anleitung brauchen

Sie müssen Fragen dieser Art beantworten:

- „Wer hat Alice von Developer zu Admin befördert, und wann?"
- „Zeige jede Vergabe der Owner-Rolle in diesem Tenant in den letzten 90 Tagen."
- „Hat das Vier-Augen-Gate beim Rollback vom letzten Dienstag ausgelöst?"

Diese Anleitung zeigt, wie Sie die CoreLink-Audit-Kette nach
Rollenänderungen und Vier-Augen-Ereignissen abfragen.

> Die Team- und Rollenverwaltung selbst läuft **ausschließlich über das
> Dashboard und die HTTP-API** — dafür gibt es keine CLI. Verwalten Sie
> Mitglieder unter `https://humangr.com/corelink/customer/team` oder über
> `GET /v1/customer/team`, `POST /v1/customer/team/invite`
> (`{email, role}`) und `DELETE /v1/customer/team/{user_id}` (Einladen
> und Entfernen sind Owner/Admin vorbehalten). Das Lesen des Audit-Trails
> — das Thema dieser Anleitung — leisten die `/v1/audit/*`-Routen und der
> Befehl `corelink audit`.

## Voraussetzungen

- Sie besitzen den Scope `admin:audit`.
- Ein PAT mit diesem Scope
  (`Authorization: Bearer corelink_<env>_…`) oder eine Clerk-Session im
  Dashboard. PATs erzeugen und auflisten Sie mit
  `POST /v1/customer/keys` (`{name, scopes[]}`) und
  `GET /v1/customer/keys`; widerrufen mit
  `POST /v1/customer/keys/{pat_id}/revoke`.
- API-Basis-URL: `https://corelink-api.humangr.com`.

## Die Audit-Kette in einem Absatz

Jede administrative Mutation und jede Mutation der Datenebene wird in ein
Append-only-Log geschrieben, das als RFC-6962-Merkle-Baum strukturiert
ist. Die rollenrelevanten Ereignisse liegen in zwei Strömen:

1. `admin_op_log` — das tabellengestützte Log jeder per Vier-Augen-Prinzip
   abgesicherten Operation, mit `outcome` ∈ `{approved, denied_missing,
   denied_sig, denied_caller_eq, denied_collusion, denied_mfa_stale,
   denied_approver_not_admin, denied_nonce_replay, denied_clock_skew}`
   (`crates/corelink-dual-approval/src/types.rs::ApprovalOutcome`).

2. Die CloudEvent-Audit-Kette — das breitere Log. Die beiden Ereignistypen,
   die an Quellcode-Konstanten gebunden sind, lauten
   `corelink.admin.op.executed` und `corelink.admin.op.denied`
   (`crates/corelink-dual-approval/src/audit.rs`). Mitglieds- und
   Rollenmutationen landen im selben Tenant-Strom, doch diese Anleitung
   nennt deren `type`-Zeichenketten nicht: Ermitteln Sie die exakten
   Werte, die Ihr Tenant ausgibt, mit Abfrage 1 weiter unten, und filtern
   Sie dann darauf.

Beide werden über die HTTP-Routen `/v1/audit/*` und die CLI
`corelink audit` gelesen. Die
[Erläuterung zur Audit-Kette](../../explanation/security/audit-chain.mdx)
beschreibt den zugrunde liegenden Mechanismus (Merkle-Beweise, Aufbewahrung usw.).

## Abfrage 1 — welche Ereignistypen im Zeitfenster auftraten

`GET /v1/audit/analytics/event-count` aggregiert die Audit-Zeilen des
Tenants nach dem CloudEvents-`type` über `[from, to)` (Unix-Epoch in
**Millisekunden**), mit optionalem, exakt passendem `event_type`-Filter:

```bash
curl -sS \
  -H "Authorization: Bearer corelink_<env>_…" \
  "https://corelink-api.humangr.com/v1/audit/analytics/event-count?from=<epoch_ms>&to=<epoch_ms>"
```

Die Antwort enthält ein `buckets`-Array — ein Eintrag je im Fenster
beobachtetem `event_type`, wobei jeder Eintrag diesen `event_type` mit
seiner Zeilenzahl (`count`) verbindet. Führen Sie die Abfrage zuerst ohne
Filter aus, um die exakten Typ-Zeichenketten Ihres Tenants zu erfahren,
und wiederholen Sie sie dann mit `&event_type=<type>`, um einen davon zu
isolieren.

> E-Mail-Adressen erscheinen gemäß `INV-AUDIT-NO-RAW-PII` nur als Hashes
> (`email_hash`). Um wieder auf eine Person zu schließen, gleichen Sie mit
> der Team-Seite (`https://humangr.com/corelink/customer/team`) ab,
> solange die Mitgliedschaft noch aktiv ist.

## Abfrage 2 — wann sie auftraten

`GET /v1/audit/analytics/timeline` verteilt dasselbe Fenster zeitlich auf
Buckets:

```bash
curl -sS \
  -H "Authorization: Bearer corelink_<env>_…" \
  "https://corelink-api.humangr.com/v1/audit/analytics/timeline?from=<epoch_ms>&to=<epoch_ms>&granularity=3600000"
```

`granularity` ist die Bucket-Breite in Millisekunden und steht
standardmäßig auf `3600000` (1 h). Die Route weist eine Anfrage mit
`400 Bad Request` ab, wenn `(to - from) / granularity` 1000 Buckets
überschreitet oder wenn `granularity` über 24 h liegt.

## Abfrage 3 — die Ereignisse selbst holen, mit Merkle-Beweisen

Für Audit-Nachweise mit hohem Einsatz (SOC 2, Recht, Kundenaudit)
exportieren Sie das Fenster und verifizieren die Kette. Die HTTP-Fläche
streamt NDJSON — eine `{event, proof}`-Zeile je Audit-Zeile plus eine
abschließende Manifest-Zeile — und veröffentlicht den Chain-Head-Anchor
im Antwort-Header `X-CoreLink-Audit-Export-Chain-Head-Anchor`:

```http
GET /v1/audit/{tenant}/export?from=<epoch_ms>&to=<epoch_ms>
Authorization: Bearer corelink_<env>_…
```

Die CLI nutzt dieselbe Route. `corelink audit` ist das einzige
Audit-Verb, das die CLI mitbringt:

```bash
# Export the window, embedding + re-validating Merkle inclusion proofs.
corelink audit export \
  --tenant <tenant_id> \
  --since <epoch_ms> \
  --until <epoch_ms> \
  --include-merkle-proofs \
  --verify \
  --out ./audit-evidence

# Re-validate a previously exported JSON-LD file, offline.
corelink audit verify ./audit-evidence/<export-file>

# Re-verify the streaming NDJSON envelope straight off the export route.
corelink audit verify-ndjson \
  --url "https://corelink-api.humangr.com/v1/audit/<tenant_id>/export?from=<epoch_ms>&to=<epoch_ms>" \
  --bearer corelink_<env>_…
```

`--verify` ist fail-CLOSED: Jeder Beweis wird neu validiert, bevor
irgendetwas geschrieben wird. `verify-ndjson` endet mit `0` bei
vollständiger Kettenintegrität und mit `65` (sysexits `DATAERR`), wenn
der Server über den HTTP-Trailer `x-corelink-audit-export-aborted` einen
Kettenbruch meldet. Um eine bereits vorliegende Datei zu prüfen,
verwenden Sie `--ndjson <FILE>` zusammen mit `--chain-head-anchor <HEX>`
(dem Anchor-Wert, den der Server beim Export veröffentlicht hat) statt
`--url`.

Siehe [Audit-Kette](../../explanation/security/audit-chain.mdx) für die
Verifikations-Schritt-für-Schritt-Anleitung.

## Abfrage 4 — aktuelle Ereignisse verfolgen

Für einen schnellen Blick statt eines Nachweispakets:

```bash
corelink audit tail \
  --tenant <tenant_id> \
  --filter event_type=<type> \
  --limit 50
```

`tail` ist ein fensterbasierter Abruf der Live-Export-Route (kein
laufendes Follow). Das Standardfenster ist die letzte Stunde, das
Standardlimit 50 Ereignisse. `--filter` nimmt ein `key=value`-Prädikat
entgegen; zulässige Schlüssel sind `event_type`, `subject`, `source`,
`region`, `tenant_id`, `sequence_number` und `id`.

## Häufige forensische Muster

### „Hat jemand das Vier-Augen-Gate umgangen?"

Kurze Antwort: **das ist nicht möglich**. Das Gate ist fail-CLOSED, und
jedes abgelehnte Ergebnis wird selbst auditiert. Sehen Sie
`corelink.admin.op.executed` mit einem `op_type` aus der destruktiven
Menge, dann liegt eine Genehmiger-Identität vor und eine HMAC-Signatur
wurde serverseitig verifiziert. Bei Manipulationsverdacht führen Sie den
Export mit Beweisen aus (Abfrage 3), um zu bestätigen, dass das Ereignis
im kanonischen Log-Head steht.

### „Wer war am 22.04.2026 um 18:31 UTC Admin?"

Die Audit-Kette ist Ihre Wahrheitsquelle für einen Zeitpunkt.
Exportieren Sie das Fenster bis zu diesem Zeitstempel (Abfrage 3),
filtern Sie auf die Mitglieds-Ereignistypen, die Sie in Abfrage 1
ermittelt haben, und spielen Sie den Zustand nach — die Team-Liste zeigt
nur die aktuelle Momentaufnahme.

### „Ein Ex-Mitarbeiter bestreitet, jemals Admin bekommen zu haben."

Exportieren Sie das Fenster, das die Vergabe abdeckt, und bewahren Sie
die Merkle-Beweise auf (Abfrage 3). Vier-Augen-Ereignisse führen sowohl
den Akteur als auch den zweiten Genehmiger als Paar aus `user_id` und
`email_hash`, dazu eine HMAC-Signatur über die kanonischen Audit-Bytes;
die CloudEvent-`source` lautet `/corelink/admin/<region>` — der Eintrag
ist damit unbestreitbar und regional zugeordnet, ohne je eine
Klartext-E-Mail zu speichern.

## Aufbewahrung

Die Audit-Aufbewahrung beträgt im Enterprise-Tier standardmäßig 7 Jahre
(abgestimmt auf SOC 2 Type II). Nach dem Offboarding eines Tenants werden
kundenidentifizierende Felder pseudonymisiert, die Ketteneinträge selbst
bleiben jedoch für den regulatorischen Zeitraum bestehen. Siehe
[Audit-Kette](../../explanation/security/audit-chain.mdx) für den
Aufbewahrungsvertrag.
