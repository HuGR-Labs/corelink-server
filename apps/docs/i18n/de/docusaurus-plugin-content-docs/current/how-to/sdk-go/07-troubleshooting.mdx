# Troubleshooting

## When to use this guide

A `corelink-go` call returned an error. `corelink-go` is intentionally
minimal: `Client` exposes only `Put` / `Get` / `Stat` / `Close` /
`IsClientVerifyEnabled`, and every error is a plain `error` value (message
string), not a typed error hierarchy. There is no `Doctor`, `Whoami`,
streaming reader, or structured logging in this SDK today.

If you want the 8-check `doctor` diagnostic or a CLI-driven identity check,
use the [`corelink` CLI](../../reference/cli/doctor.mdx) or the
[Python](../sdk-python/07-troubleshooting.mdx) /
[JS](../sdk-js/07-troubleshooting.mdx) SDKs, which have richer surfaces.

## Errors you'll actually see

`errors.New` / `fmt.Errorf` messages, matched by substring — there is no
`error_code` field or typed error to switch on:

| Message contains | Cause | Fix |
|---|---|---|
| `PAT must not be empty` | `Config.PAT` was empty at `NewClient` | Set `CORELINK_PAT` and read it into `Config.PAT` yourself — `NewClient` does not read env vars for you. |
| `TenantID must not be empty` | `Config.TenantID` was empty at `NewClient` | Pass a non-empty `TenantID`. |
| `failed to construct client (invalid PAT or TenantID encoding)` | The cgo constructor rejected the PAT or tenant ID bytes | Check the PAT was copied in full (`corelink_<env>_<token_id>.<random_secret>.<hmac_sig>`), no truncation. |
| `put failed (rc=%d)` | Non-zero return from the native `Put` call | Check network/auth first (a valid PAT and tenant on a failing `Get`/`Stat` narrows it down). |
| `invalid digest length %d (expected 64)` | Digest passed to `Get`/`Stat` isn't 64 hex chars | Recompute — CoreLink digests are BLAKE3, not SHA-256. |
| `COR_CAS_DIGEST_MISMATCH: digest mismatch for %s` | Client-verify (default-on, CTRL-CAS-002) caught a BLAKE3 mismatch on `Get` | Possible corruption in transit; retry. Persistent → open a support ticket. |
| `COR_CAS_VERIFY_DISABLED` | `Get` called with client-verify explicitly disabled | Expected if you set `ClientVerify: false, ClientVerifyExplicitFalse: true` — not an error condition unless you didn't mean to disable it. |
| `get verify failed (rc=%d)` | Non-zero, non-mismatch return from the native verify call | Check network/auth; retry. |

## Confirm the client is talking to the server at all

There's no `Whoami` — the first real signal is a successful `Put`/`Get`:

```go
digest, err := client.Put(ctx, []byte("healthcheck"))
if err != nil {
    log.Fatalf("client not working: %v", err)
}
log.Println("ok, wrote", digest)
```

## Filing a bug

Include the exact error message (`err.Error()`), your `corelink-go`
version (`go.mod` / `go list -m github.com/HumanGuardrail/corelink-go/v1`),
and whether you built against a matching `libcorelink_go`
(`cargo build --release -p corelink-go`) — a version skew between the Go
module and the linked Rust cdylib is a common source of opaque `rc=%d`
failures. Never include your PAT.
