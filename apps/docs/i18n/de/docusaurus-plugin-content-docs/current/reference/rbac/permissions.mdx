# Permissions reference

The full canonical permission catalog. Two layers:

1. **PAT scopes** — the 7 bits in the `PatScopes` u64 bitset, recorded on
   a PAT at mint time.
2. **Admin op types** — the 7 destructive/non-destructive operation
   variants carried in the body of `POST /v1/admin/mutate`, with the
   dual-approval gate where applicable.

:::warning[The bitset is a mint-time record, not the enforcement input]
No served route reads the `PatScopes` bitset. Every request is authorized
from the **`x-corelink-scope` header**, a space/comma-separated token
string the Worker sets and the container parses with
`crates/corelink-container/src/scope.rs`. `PatScopes::has()` appears only
inside test modules (`routes/internal_pat.rs:1025-1058`); there is no
production call site.

The tokens the predicates actually match are `read-only`, `read-write`,
`cas:r`, `cas:rw`, `cas:w`, `find-missing`, `billing`, `admin` and
`owner` (`scope.rs:60-64` defines the grammar; matching is exact-token,
never substring). Where a bit below has no matching predicate, it grants
nothing at request time — those are called out per scope.
:::

> The wire-form scope strings are stable; bit positions are stable for
> the lifetime of the u64 (ADR-0026 covers the u128 migration path when
> we exceed 64 scopes). Reserved bits 5..=9 and 12..=63 are masked off by
> `PatScopes::from_u64`. Bits 5..=9 previously held six granular
> `admin:*` scopes that no enforcement point ever read; they were removed
> in B-080 — see the warning below.

## PAT scopes (7 canonical bits)

### `cache:r` — Read CAS blobs + AC results

- **Bit position:** 0 (`SCOPE_CACHE_R = 1 << 0`).
- **Wire tokens that satisfy it:** `read-only`, `read-write`, `cas:r`,
  `cas:rw`, `cas:w`, `admin` (`scope.rs:73-80`, `requires_cache_read`).
- **Enforced on:**
  - `GET /v1/cas/{tenant}/{hash}` (`routes/cas.rs:87,707`).
  - `GET /v1/ac/{tenant}/{action_digest}` (`routes/ac.rs:96,449`).
  - `GET /v1/cas/{tenant}` and `GET /v1/ac/{tenant}` (listings;
    `cas.rs:49`, `ac.rs:59`).

### `cache:w` — Write CAS blobs + AC results

- **Bit position:** 1 (`SCOPE_CACHE_W`).
- **Wire tokens that satisfy it:** `read-write`, `cas:w`, `cas:rw`,
  `admin` (`scope.rs:93-95`, `requires_cache_write`). `read-only` does
  not.
- **Enforced on:**
  - `PUT /v1/cas/{tenant}/{hash}` (`routes/cas.rs:707-710`).
  - `PUT /v1/ac/{tenant}/{action_digest}` (`routes/ac.rs:449-452`).

### `cache:find-missing` — Execute FindMissingBlobs

- **Bit position:** 2 (`SCOPE_CACHE_FIND`).
- **Wire tokens that satisfy it:** the explicit `find-missing` /
  `cache:find-missing` least-privilege token, plus any read grant — read
  is a superset of an existence probe (`scope.rs:107`,
  `requires_find_missing`; ADR-0071).
- **Enforced on:** the REAPI `FindMissingBlobs` operation. A
  find-missing-only PAT probes existence and can download nothing.

### `cache:delete` — Admin blob deletion

- **Bit position:** 3 (`SCOPE_CACHE_DELETE`).
- **Granted to roles by default:** none. No mint path emits this bit —
  the self-serve classifier only ever sets `SCOPE_CACHE_FIND`,
  `SCOPE_CACHE_RW` or `SCOPE_CACHE_R` (`customer_d1.rs:1267-1273`), and
  the internal mint's admin bundle does not include it
  (`routes/internal_pat.rs:134-140`).
- **Status:** **this bit is not an enforcement input.** Deletion *is*
  served — `DELETE /v1/cas/{tenant}/{hash}` (`cas.rs:709`, handler at
  `cas.rs:1556`) and `DELETE /v1/ac/{tenant}/{action_digest}`
  (`ac.rs:451`, handler at `ac.rs:679`) both exist — but they are gated
  on the **cache-write** capability, not on `cache:delete`:
  `cas.rs:1584` and the AC mirror both call `scope.can_write()`. A
  runner-job credential is refused outright before that check
  (`cas.rs:1576-1582`), and a cross-tenant path is refused before any
  storage access (`cas.rs:1565`).
- Holding `cache:delete` therefore grants nothing; holding `cas:rw`
  already permits deletion. The name is carried in an explicit
  declared-exception ledger
  (`crates/corelink-container/tests/scope_catalog_closure.rs`) so the gap
  stays visible rather than silent.

### `admin` — Owner-grade superset

- **Bit position:** 4 (`SCOPE_ADMIN`).
- **Granted to roles by default:** `Owner`. Never self-serve-grantable:
  the mint classifier refuses `admin` / `owner` from the customer
  surface, so an `admin` PAT can only come from the internal mint.
- **Grants:** cache read + write, plus the billing / account-PII surface
  (`GET /v1/customer/billing*`, `GET /v1/customer/audit`), which the
  container gates with `requires_billing_admin` (`billing`, `admin` or
  `owner`).

:::warning[There are no granular `admin:*` scopes]
Six granular admin scopes — `admin:tenant-read`, `admin:tenant-write`,
`admin:tokens`, `admin:billing`, `admin:audit`, `admin:users` — were
listed here as bits 4..=9. **They were never implemented and are now
removed** (B-080). They could not be minted (neither the self-serve
classifier nor the internal mint ever accepted them individually), could
not be stored (`pat.scope` is
`TEXT CHECK (scope IN ('read-write','read-only','admin'))` — there is no
bitset column), and no enforcement point ever read them. A token bearing
one received exactly the privilege of a token without it.

**Do not build a least-privilege plan on those names.** Bits 5..=9 are
retired and fold back into the reserved range. The admin capability that
*is* enforced is the single `admin` scope above, plus the `billing`
capability the Worker forwards for an owner/admin dashboard session.
Reintroducing granular admin scopes is a security-surface expansion and
is subject to `auth_model.md` §3.4 (ADR + security review) in full.
:::

### `execute:action` — Phase 2 executor reports action start

- **Bit position:** 10 (`SCOPE_EXECUTE_ACTION`).
- **Granted to roles by default:** none (Phase 2 worker identity only).
- **Gates endpoints:**
  - `POST /v2/execution/action/start` *(planned for Phase 2)*.

### `report:result` — Phase 2 executor reports result

- **Bit position:** 11 (`SCOPE_REPORT_RESULT`).
- **Granted to roles by default:** none (Phase 2 worker identity only).
- **Gates endpoints:**
  - `POST /v2/execution/result` *(planned for Phase 2)*.

### Reserved bits 5..=9 and 12..=63

Masked off by `PatScopes::from_u64` so a row carrying an unknown bit
silently degrades to zero on a current-generation reader (per ADR-0026)
— fail-closed, never a privilege. Bits 5..=9 held the six retired
`admin:*` scopes (B-080) and are reserved again; 12..=63 have always
been reserved for future scopes.

## Admin operation types (7 variants)

Submitted to `POST /v1/admin/mutate`; the second signature goes to
`POST /v1/admin/approve` (`routes/admin.rs:124,129,695,696`). Destructive
variants require `X-Dual-Approver`, `X-Approver-Signature`,
`X-Approver-Nonce`, `X-Request-Ts-Ms` headers and run through the 7-step
gate.

### Destructive (dual-approval required)

| Op type                  | Spec WI    | What it does                                  |
|--------------------------|------------|-----------------------------------------------|
| `ConfigRollback`         | WI-S13-001 | Roll back a tenant config to a prior version. |
| `RetentionPolicyReduce`  | (S-11)     | Shorten a retention TTL.                      |
| `FeatureFlagDisable`     | (S-12)     | Disable a feature flag globally or per-tenant.|
| `SecretRotationStart`    | WI-S13-003 | Kick off a secret / DEK rotation.             |
| `TenantTombstone`        | (S-11)     | Tombstone a tenant (erasure pipeline entry).  |

### Non-destructive (audited; approver optional but recommended)

| Op type                   | What it does                                    |
|---------------------------|-------------------------------------------------|
| `FeatureFlagToggleSafe`   | Toggle a flag in the safe direction (enable / rollout %↑). |
| `RateLimitAdjustUp`       | Increase a rate-limit bucket (conservative).    |

See `crates/corelink-dual-approval/src/types.rs::AdminOpType::is_destructive`
for the canonical classifier.

## Approval outcomes

Every gate evaluation writes one of these strings to `admin_op_log.outcome`
(CHECK constraint enforces the set):

| Outcome string                | Meaning                                                  |
|-------------------------------|----------------------------------------------------------|
| `approved`                    | All 7 checks passed; op executed.                        |
| `denied_missing`              | `X-Dual-Approver` header missing on a destructive op.    |
| `denied_sig`                  | HMAC signature invalid.                                  |
| `denied_caller_eq`            | Caller == approver (separation of duties).               |
| `denied_collusion`            | Same approver co-signed within the 3-cycle window.       |
| `denied_mfa_stale`            | Caller MFA assertion > 30 min old.                       |
| `denied_approver_not_admin`   | Approver does not hold an active `Owner`/`Admin` role.   |
| `denied_nonce_replay`         | Nonce already seen.                                      |
| `denied_clock_skew`           | `ts_ms` differs from server now > 60s.                   |

`admin_op_log` is written by `crates/corelink-dual-approval`. **There is
no route that reads it back** — the table name appears nowhere outside
that crate's `types.rs`, `audit.rs` and `collusion.rs`. Approval history
is not retrievable over the API today.

They are listed here because earlier revisions of this page named an
admin API that was never served; these are the endpoint names to use.

### Audit surface

| Route | Gate | Source |
|---|---|---|
| `GET /v1/audit/{tenant}/export` | `requires_audit_read` | `routes/audit_export/types.rs:20`, gate at `handler.rs:111` |
| `GET /v1/audit/analytics/event-count` | `requires_audit_read` | `routes/audit_analytics/types.rs:15`, gate at `handler_event_count.rs:62` |
| `GET /v1/audit/analytics/timeline` | `requires_audit_read` | `routes/audit_analytics/types.rs:18`, gate at `handler_timeline.rs:60` |

The RFC 6962 inclusion proof has **no route of its own**: each exported
row is verified inline and the result is emitted as part of the export
stream (`routes/audit_export/stream.rs:251`).

**Two different gates guard "audit".** `GET /v1/customer/audit` — the
dashboard log — is gated on `requires_billing_admin` (`scope.rs:229`),
which accepts only `billing`, `admin` or `owner`. The export and
analytics routes are gated on `requires_audit_read` (`scope.rs:251`),
which accepts any read-capable token. A `read-only` credential is
therefore **refused (403)** by the first and **accepted** by the other
three. See the [permission matrix](../../explanation/rbac/permission-matrix.mdx).
