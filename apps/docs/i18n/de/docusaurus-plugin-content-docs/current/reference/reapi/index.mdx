# REAPI v2 reference

CoreLink implementiert eine mandantenfähige, wire-kompatible Teilmenge von
[`bazelbuild/remote-apis @ v2.12.0`](https://github.com/bazelbuild/remote-apis/tree/v2.12.0).
Bazel 6+ und jeder andere REAPI-v2-Client, der **HTTP/REST** spricht,
verbinden sich **ohne Codeänderungen** — nur der Cache-Endpoint und der PAT
unterscheiden sich. CoreLink stellt keinen gRPC-Ingress bereit; REAPI-Clients,
die ausschließlich gRPC sprechen (Buck2, Pants, NativeLink), können sich
daher nicht verbinden.

## Authentifizierung

Jeder RPC trägt einen PAT im `Authorization: Bearer <pat>`-Metadaten-Header.
Das kanonische Token-Format ist:

```
corelink_<env>_<token_id>.<random_secret>.<hmac_sig>
```

Der auf dieser Website durchgängig verwendete Platzhalter —
`corelink_pat_0123456789ABCDEF.AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA.BBBBBBBBBBBBBBBBBBBBBA` — ist beabsichtigt und darf in Produktion
niemals auftauchen.

## Automatisch generierte Service-Seiten

Die Seiten unter diesem Abschnitt werden aus den vendored `.proto`-Dateien
von `pnpm docs:gen` neu generiert. CI verifiziert bei jedem PR, dass
zwischen Proto und gerendertem MDX kein Drift besteht
(`pnpm docs:gen:check`).

Durchsuchen Sie den generierten Index für alle Services im aktuellen Build.

## Manuelle Codebeispiele

Für jeden Service liegen handgeschriebene Beispiele in vier Sprachen unter
`_examples/<Service>/`:

- **Python** (`corelink-py`)
- **Go** (`corelink-go`)
- **Node / TypeScript** (`@corelink/client`)
- **CLI** (`corelink`)

Die Beispiele decken die häufigsten Abläufe ab: PAT-Auth,
`BatchUpdateBlobs`, `BatchReadBlobs`, `FindMissingBlobs`,
`Capabilities.GetCapabilities`, `ByteStream.Read`, `ByteStream.Write` und
Health-Probing.

## Fehlermodell

CoreLink bildet jeden REAPI-v2-Statuscode auf eine stabile
`error_taxonomy`-Kennung ab (`COR_CAS_*`, `COR_AUTH_*`, `COR_QUOTA_*`).
Siehe [Fehlertaxonomie](../../tutorial/06-verify-cache-hit.mdx#troubleshooting)
für die häufigsten Fälle.
