# Cache-Trefferquote überprüfen

Das Tutorial ist erst abgeschlossen, wenn Sie nachweisen können, dass der Cache
funktioniert. Diese Seite fasst drei unabhängige Prüfungen zusammen.

## A. Bazel-BES- / Buck2-Logs

Bazel:

```bash
bazel build //:hello 2>&1 | grep -E "remote cache hit|disk cache hit|processes:"
# INFO: 12 processes: 11 remote cache hit, 1 internal.
```

Buck2:

```bash
buck2 build //:hello --show-output 2>&1 | grep -iE "cache hits"
```

Eine zu 100 % grüne Build, die **0 processes** ausgibt, ist das stärkste einzelne
Signal — Bazel/Buck2 hat jede Aktion über den Cache kurzgeschlossen.

## B. CLI-Mikrobenchmark

Führen Sie das integrierte `corelink bench` aus (schreibt einen deterministischen
16-KiB-Blob 50× und liest ihn dann 50×):

```bash
corelink bench --put 50 --get 50
# put p50=8.2ms  p95=13.1ms  err=0/50
# get p50=2.1ms  p95= 4.8ms  err=0/50 hit_ratio=100%
```

`hit_ratio=100%` im Lesedurchlauf bestätigt, dass die Anfragen ab der zweiten aus
dem Cache bedient werden.

## C. Admin-UI-Dashboard

1. Öffnen Sie `https://humangr.com/corelink/orgs/<your-org>/observability`.
2. Wählen Sie **Cache hit ratio (5m, by tenant)**.
3. Lösen Sie eine neue Build aus (`bazel clean && bazel build //...`).
4. Die Reihe sollte nach dem ersten warmen Durchlauf auf ~100 % springen.

Das Grafana-Panel für die Trefferquote ist in `dashboards/cache_hit_ratio.json`
dokumentiert; die Alarmschwellen liegen in `infra/alerts/cache_hit_ratio.yaml`.

## Fehlerbehebung

| Symptom | Wahrscheinliche Ursache | Behebung |
| --- | --- | --- |
| `hit_ratio=0%` bei der zweiten Build | der lokale Festplatten-Cache hat die Anfrage bedient, den Remote nie berührt | `bazel clean` und `build --noremote_accept_cached=false` setzen, um einen Remote-Lesevorgang zu erzwingen |
| `UNAUTHENTICATED`-Fehler | PAT abgelaufen oder falsche Umgebung | `corelink doctor --check-auth` erneut ausführen, PAT neu generieren |
| `COR_CAS_DIGEST_MISMATCH` | Bytes während der Übertragung beschädigt | `client_verify` hat den Blob abgelehnt — melden Sie ein Issue, deaktivieren Sie die Prüfung nicht |
| Langsam `p95 > 50ms` | die Region Ihres Mandanten liegt weit von Ihren CI-Runnern entfernt | **Keine clientseitige Einstellung.** Anfragen werden an die `primary_region` Ihres Mandanten geleitet, die bei der Bereitstellung festgelegt wird; die Edge liest sie serverseitig aus und verwirft jede vom Client mitgegebene Region — keine URL und kein `.bazelrc`-Flag kann das überschreiben. Liegt Ihr Mandant in der falschen Region, wenden Sie sich an support@humangr.com — eine Verlagerung ist eine Änderung der Datenresidenz, keine Konfigurationsänderung. |
