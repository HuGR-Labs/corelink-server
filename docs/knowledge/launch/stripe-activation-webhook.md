# Stripe activation webhook — the money-path activation half

CoreLink's money-path implementation includes a signup-worker handler for Stripe deliveries. It verifies the raw signed body, makes the billing writes idempotent, and handles cache and runner subscription events. The repository also mounts a container webhook when its secret and durable D1 are available; source code establishes these implementations and their guards, while endpoint configuration and deployment selection require operational evidence outside this repository (`crates/corelink-container/src/main.rs:680-684`, `crates/corelink-container/src/main.rs:820-840`).

# Role

`handleStripeWebhook` verifies, parses, awaits its required billing writes, claims the delivery, and then emits analytics. The implementation uses `verifyStripeSignature` for the raw-body signature and replay check, `claimWebhookEvent` for the idempotency claim, and `activatePaidTierSelection` for the cache activation write (`apps/signup-worker/src/webhooks/stripe_signature.ts:18-76`, `apps/signup-worker/src/webhooks/stripe_persistence_billing.ts:45-60`, `apps/signup-worker/src/webhooks/stripe_persistence_billing.ts:253-286`). Its cache price map resolves configured `STRIPE_PRICE_ID_{TIER}` values back to CoreLink tiers (`apps/signup-worker/src/webhooks/stripe_contract.ts:68-91`).

This handler now ALSO owns the RUNNER entitlement lifecycle — a SECOND, separate axis from the cache tier. A runner subscription is its own Stripe subscription (disjoint price env set `STRIPE_PRICE_ID_RUNNER_*`), so the cache-path helpers all resolve null for it and the cache activation is a clean no-op. The runner arms instead seed/revoke `runners_entitlement` (migrations 0070/0072) via a dedicated `runner_billing` map (migration 0087), which keys the runner Stripe subscription id → tenant so it never clobbers the one-row-per-tenant `tenant_billing` cache row and a tenant can hold BOTH a cache and a runner subscription. On `checkout.session.completed` a `metadata[tier]=runner_*` maps the runner subscription into `runner_billing` and returns without any cache activation (`apps/signup-worker/src/webhooks/stripe.ts:234-280`); on `customer.subscription.created`/`updated` (the first events carrying the runner PRICE) `runnerEntitlementFromSubscriptionPrice` seeds the entitlement on a granting status and revokes it otherwise (`apps/signup-worker/src/webhooks/stripe_contract.ts:225-253`, seed/revoke dispatch at `apps/signup-worker/src/webhooks/stripe.ts:528-592`); and `invoice.payment_failed` (`apps/signup-worker/src/webhooks/stripe.ts:739-756`) / `customer.subscription.deleted` (`apps/signup-worker/src/webhooks/stripe.ts:802-820`) unconditionally revoke through `runner_billing` (an inherent no-op for a cache subscription).

# How it works

- **Signature verify before any side effect.** `verifyStripeSignature` parses the `Stripe-Signature` header (`t=<ts>,v1=<hex>…`), computes `HMAC-SHA256(secret, ` + "`${timestamp}.${rawBody}`" + `)`, and compares against each `v1` candidate — over the RAW body, never the re-serialized JSON, so no canonicalization drift can invalidate the HMAC (`apps/signup-worker/src/webhooks/stripe_signature.ts:18-76`).
- **Replay guard (±tolerance).** The signed timestamp must be within `MAX_TIMESTAMP_AGE_MS` (5 minutes) of now, else the delivery is rejected as a replay — a captured-and-resent body past the window fails closed (`apps/signup-worker/src/webhooks/stripe_signature.ts:56-56`).
- **Constant-time-ish compare.** The expected hex is diffed against each candidate by XOR-accumulating every char into `diff` and only accepting when `diff === 0`, so a partial-prefix match leaks no early-exit timing oracle (`apps/signup-worker/src/webhooks/stripe_signature.ts:81-81`).
- **Idempotency claim.** The billing persistence helper inserts the Stripe event id with `INSERT OR IGNORE`; the handler uses the claim result when deciding whether to emit analytics (`apps/signup-worker/src/webhooks/stripe_persistence_billing.ts:39-61`, `apps/signup-worker/src/webhooks/stripe.ts:905-930`).
- **The activation write is owner-bound.** `upsertBillingPaid` first proves the Checkout session, tenant, tier, customer, and pending correlation agree; its conflict arm may only replay the same paid subscription or replace a non-paid row, never clobber a different paid subscription. `activatePaidTierSelection` repeats the exact billing-owner proof at the tier mutation. The container's partial UNIQUE index covers both paid `active` and payable `pending_checkout` rows, while the Stripe idempotency key is `checkout:<axis>:<tenant>` (`axis` is `cache` or `runner`; the D1 correlation ledger remains the durable request identity). A mirrored pending page blocks a second payable checkout on its axis; a fresh pre-mirror reservation is a bounded crash-recovery case, so the retry rebinds its tenant+tier ledger row and receives the same Stripe session instead of a 24-hour lockout. Webhook completion/expiry can recover the orphan from tenant+tier metadata plus Stripe creation time, with cross-tenant and stale-session predicates. `checkout.session.expired` releases only that pending correlation (`apps/signup-worker/src/webhooks/billing_checkout.ts:23-23`, `crates/corelink-container/src/routes/tier_select_store.rs:70-70`, `crates/corelink-stripe-real/src/client.rs:857-857`, `migrations/d1/0111_b076_payable_subscription_ownership.sql:1`).
- **Cache-tier revocation is scoped to the SPECIFIC subscription (H1).** The three terminal events that revoke the canonical gate — `customer.subscription.updated` → non-granting (`apps/signup-worker/src/webhooks/stripe_signature.ts:75-75`), terminal `invoice.payment_failed` (`apps/signup-worker/src/webhooks/stripe.ts:736-740`), and `customer.subscription.deleted` (`apps/signup-worker/src/webhooks/stripe.ts:801-804`) — all call `deactivateTierSelectionBySubscription`, which flips `tier_selections.subscription_state` to `inactive` ONLY for the tenant resolved THROUGH `tenant_billing` (the one-row-per-tenant CACHE billing map) by the event's `stripe_subscription_id` (`apps/signup-worker/src/webhooks/stripe_persistence_billing.ts:346-374`). Revocation is NEVER keyed by `stripe_customer_id`: checkout reuses ONE Stripe customer per tenant across the cache AND runner subscriptions, so a customer-keyed revoke would flip the tenant's active cache-tier row on an unrelated runner-subscription terminal event. A runner subscription id is never in `tenant_billing` (runner subs live in `runner_billing`), so a runner-sub terminal event is a clean no-op on the cache row.
- **Price→tier reverse map (cache axis).** `tierFromSubscriptionPrice` reads `items.data[0].price.id` (or legacy `plan.id`) and matches it against the `STRIPE_PRICE_ID_{TIER}` env vars — the SAME vars the checkout backend used to pick the price — returning null (never a guess) when no tier matches, so an in-Stripe plan swap maps back to the right CoreLink tier (`apps/signup-worker/src/webhooks/stripe_contract.ts:68-91`).
- **Runner seed/revoke (separate axis).** The runner mirror is `runnerEntitlementFromSubscriptionPrice`, which reverse-maps the subscription's price against the DISJOINT `STRIPE_PRICE_ID_RUNNER_*` env set (scanning every `items.data[*].price.id` plus legacy `plan.id`); a hit seeds `runners_entitlement` on a granting status and revokes it otherwise via `revokeRunnersEntitlementBySubscription`, both resolving tenant THROUGH `runner_billing` (subscription id → tenant), all idempotent so a redelivery converges. The seed is now RACE-FREE: when the subscription metadata carries the tenant id the entitlement is written DIRECTLY by tenant via `upsertRunnersEntitlementByTenant` (`apps/signup-worker/src/webhooks/stripe_persistence_runner.ts:1-251`) — and the webhook's causal write queue executes the `runner_billing` mapping before any subscription-correlated entitlement seed — then falls back to the correlated variant only on the no-metadata path (`apps/signup-worker/src/webhooks/stripe.ts:562-585`). Because the runner and cache price env sets are disjoint, at most one of the two paths ever has work to do on a given subscription (`apps/signup-worker/src/webhooks/stripe_contract.ts:225-253`, `apps/signup-worker/src/webhooks/stripe_contract.ts:90-90`).

# Invariants

- A delivery with a bad or absent signature, or a timestamp outside the 5-minute window, produces NO side effect — verification returns false before parse, and the handler 400s `invalid_signature` (`apps/signup-worker/src/webhooks/stripe_signature.ts:56-56`).
- The signature compare never exits early on a mismatching byte — equal-length candidates are XOR-folded and only `diff === 0` accepts (`apps/signup-worker/src/webhooks/stripe_signature.ts:81-81`).
- The non-idempotent analytics emit fires exactly once: the claim is `INSERT OR IGNORE` on the `event_id` PK and a redelivery hits `changes === 0` (`apps/signup-worker/src/webhooks/stripe_persistence_billing.ts:45-60`).
- Activation is idempotent and non-regressing: the `ON CONFLICT DO UPDATE … WHERE subscription_state <> 'active' OR tier = 'free'` guard means a redelivered/out-of-order completion cannot downgrade or re-timestamp an already-active PAID row, while still allowing a paid activation to overwrite the free seed row every tenant starts on (`apps/signup-worker/src/webhooks/stripe_persistence_billing.ts:253-286`).
- A terminal event revokes ONLY the cache tier tied to its own subscription: `deactivateTierSelectionBySubscription` resolves the tenant through `tenant_billing` by `stripe_subscription_id`, so a runner-subscription cancel/failure (whose id is absent from `tenant_billing`) is a no-op on the cache row while the tenant's cache subscription stays `active`; there is no customer-keyed revocation path that could flip an unrelated active row (`apps/signup-worker/src/webhooks/stripe.ts:346-346`).
- An unrecognized Stripe price maps to NO cache tier change — `tierFromSubscriptionPrice` returns null rather than guessing a SKU (`apps/signup-worker/src/webhooks/stripe_contract.ts:80`).
- The runner axis never touches the cache tables and vice-versa: a runner price is in a DISJOINT env set from the cache price map, so `tierFromSubscriptionPrice` returns null for a runner price (and `runnerEntitlementFromSubscriptionPrice` returns null for a cache price), and the runner entitlement is written ONLY to `runner_billing`/`runners_entitlement` (migrations 0087/0070), never `tenant_billing`/`tier_selections`. A tenant can therefore hold both a cache AND a runner subscription (`apps/signup-worker/src/webhooks/stripe_contract.ts:225-253`).
- Runner terminal-event handling updates the runner billing status and reconciles a runner entitlement only when the event has a matching runner price (`apps/signup-worker/src/webhooks/stripe.ts:741-787`, `apps/signup-worker/src/webhooks/stripe.ts:835-847`).

# Gotchas

- **Repository evidence has a deployment boundary.** The source tree contains a signup-worker handler and a conditionally mounted container webhook; it does not identify the configured Stripe endpoint or establish which handler receives a deployed delivery (`apps/signup-worker/src/webhooks/stripe.ts:168-189`, `crates/corelink-container/src/main.rs:820-840`).
- **The cache price map is configuration-dependent.** A cache subscription price that is absent from the configured `STRIPE_PRICE_ID_{TIER}` values produces no tier match; operators must validate deployed price configuration separately (`apps/signup-worker/src/webhooks/stripe_contract.ts:68-91`).
- **`checkout.session.completed` cannot price-cross-check.** The session payload carries no price-shaped data and the handler makes no Stripe API calls, so the price↔tier mismatch assert runs only on the subsequent `customer.subscription.created`/`updated` event, where the price IS in the payload — this is the SAME reason a runner entitlement can only be seeded on the subscription event (checkout sessions carry no price), while the checkout branch only maps `metadata[tier]` (no price) into activation or `runner_billing` (`apps/signup-worker/src/webhooks/stripe.ts:286-286`).
- **`current_period_end_ms` is null at activation.** The session object does not carry it; it is backfilled by the `customer.subscription.created` event Stripe fires immediately after, so do not read it right after the activation write (`apps/signup-worker/src/webhooks/stripe.ts:347-350`).
- **A missing `BILLING_DB` binding fails CLOSED.** Without the D1 binding the handler returns 503 (not a silent 200) so Stripe retries — a paid checkout is never acked with zero entitlement writes; the runner writes ride the same `requiredWrites` await/500-on-failure durability contract (`apps/signup-worker/src/webhooks/stripe.ts:171-177`).
- **The dispatched event allowlist is data-driven.** `HANDLED_EVENT_TYPES` is built from `handled-stripe-events.json`; source code establishes the runtime input but cannot prove a dashboard endpoint has been reconciled (`apps/signup-worker/src/webhooks/stripe.ts:7-11`, `apps/signup-worker/src/webhooks/stripe.ts:165-165`).
