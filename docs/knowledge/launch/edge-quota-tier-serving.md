# Edge quota & tier serving

This is the read-side counterpart to the [money path](/launch/money-path.md): once Stripe activation has written a tenant's subscription row, *this* module is what decides which tier quota the tenant is actually SERVED on every cache request. It runs in the Worker edge, AFTER PAT auth and BEFORE the request is forwarded to the Durable Object, and it answers two questions — "what tier is this tenant?" and "are they within their storage and monthly-request caps?". Getting the tier-resolution filter exactly right is launch-critical: the same row the checkout backend writes at click-time (before any payment) must NOT be served as paid until Stripe confirms the charge. The container's CAS/quota FSM is the deeper net on mutations; this concept is the cheap edge decision that protects revenue integrity and availability at the same time. See the sibling concepts [tier model](/launch/tier-model.md) (the ceilings sold) and [money path](/launch/money-path.md) (the checkout + activation seam that populates the row read here).

# Role

`quota.ts` owns three things at the Worker edge: (1) **tier resolution** — `getTierForTenant` maps a `tenant_id` to its effective `Tier` from D1; (2) **storage enforcement** — `checkStorageQuota` compares `SUM(bytes_used)` against the tier's byte ceiling; (3) **request enforcement** — `checkRequestQuota` atomically increments a monthly counter and compares it to the tier's request ceiling. The per-tier ceilings themselves are the frozen `QUOTAS` table transcribed from the signed launch rate card. All three are positioned at the edge so a doomed or over-cap request is rejected before it costs the container plane anything; the Durable Object re-enforces the hard CAS boundary on every mutation.

# How it works

- The `QUOTAS` table is the single source of per-tier ceilings — `free` = 10 GB / 500 K req/mo up through `max` = 2 TB / 80 M req/mo. It has 9 rows: `org` is a pro-equivalent ALIAS (identical 500 GB / 20 M caps to `pro`), so the table carries one more row than the 8 distinct ceilings. The `MAX_SAFE_INTEGER` "no cap" sentinel is per-AXIS, not per-tier: `team` uncaps only its REQUEST axis but is storage-capped at a FINITE **1 TB** (`1_099_511_627_776`, `worker/src/lib/quota.ts:88`); ONLY `enterprise` is unlimited on BOTH axes (`worker/src/lib/quota.ts:85-93`).
- **The launch-blocker filter:** tier resolution reads the canonical subscription row with `SELECT tier FROM tier_selections WHERE tenant_id = ?1 AND subscription_state = 'active'` — the `= 'active'` predicate is what refuses to serve a paid tier on a `pending_checkout` (written at click-time, before payment) or `inactive` row (`worker/src/lib/quota.ts:152`).
- A confirmed, valid `active` row short-circuits and returns that tier with `d1Error: false` (`worker/src/lib/quota.ts:169`).
- When no active subscription is found, resolution falls through to the tenant column `SELECT tier FROM tenant WHERE tenant_id = ?1` (migration 0057, `DEFAULT 'free'`). The resolver captures whether the step-1 query saw an active-subscription row (`hasActiveSubscription = tierSel !== null`, `worker/src/lib/quota.ts:166`) and — as a billing-integrity fail-safe (M14) — FLOORS a paid `tenant.tier` value to `'free'` unless that active-subscription signal is present (`worker/src/lib/quota.ts:195-196`); only a `free` value (or a paid value backed by an active row) is returned verbatim (`worker/src/lib/quota.ts:198`). The fallback therefore can NEVER serve a paid ceiling without a confirmed active subscription, even if a rogue writer set `tenant.tier` to a paid class. The floored `'free'` carries `d1Error: tierSelError` (`worker/src/lib/quota.ts:196`): a floor reached after the step-1 query THREW is outage-derived (fails OPEN downstream, F21), not a confirmed `free`.
- If BOTH D1 reads fail, the resolver returns the hard-coded `free` fallback but flags `d1Error = tierSelError && tenantTierError` so callers can tell a confirmed `free` from an outage-derived one (`worker/src/lib/quota.ts:205-206`).
- Storage enforcement reads `SELECT SUM(bytes_used) AS total_bytes FROM tenant_storage_state WHERE tenant_id = ?1` and compares it to the tier ceiling, returning `ok:true` while `totalBytes < storageBytesMax` (`worker/src/lib/quota.ts:380`, `worker/src/lib/quota.ts:413`).
- A tier whose STORAGE ceiling is `MAX_SAFE_INTEGER` skips the storage SUM entirely — there is nothing to check (`worker/src/lib/quota.ts:351`). Today that is ONLY `enterprise`; `team` has a finite 1 TB storage ceiling (`worker/src/lib/quota.ts:88`) and is NOT skipped, so its storage is enforced like any capped tier (the request-axis `MAX_SAFE_INTEGER` is a separate sentinel that uncaps the monthly-request gate).
- Request enforcement is a single ATOMIC `INSERT … ON CONFLICT(tenant_id, year_month) DO UPDATE SET request_count = request_count + 1 … RETURNING request_count`, so concurrent isolates cannot race a read-modify-write (`worker/src/lib/quota.ts:606`).
- **The storage SUM and request-count are no longer UNCONDITIONALLY synchronous on a warm READ.** Behind the `EDGE_ASYNC_METER` flag (unset/off ⇒ the exact synchronous `runQuotaBatch` path is the default), a metered, tier-CONFIRMED, NON-mutating request whose tenant is provably far under its request cap is served off two read-side edge caches. **B2 request-count** (`quota_request_cache.ts`) arms ONLY with proven headroom — a tenant within `burstMargin(cap)` of its cap takes the synchronous path (`worker/src/lib/quota_request_cache.ts:284`) — then serves now and increments via `ctx.waitUntil` off the hot path (`worker/src/lib/quota_request_cache.ts:318`, `worker/src/lib/quota_request_cache.ts:326`), refreshing the KV count from the authoritative `RETURNING` value rather than a blind local `+1` (`worker/src/lib/quota_request_cache.ts:320`); the margin is sized to dominate the KV staleness window so the cap boundary stays exact (`worker/src/lib/quota_request_cache.ts:94`). **B1 storage** (`quota_storage_cache.ts`) caches the `SUM(bytes_used)` bytes (never the verdict) and recomputes the cheap cap comparison live against the resolved tier (`worker/src/lib/quota_storage_cache.ts:299`, `worker/src/lib/quota_storage_cache.ts:304`); only a CONFIRMED SUM is cached — a `d1Error` is never pinned (`worker/src/lib/quota_storage_cache.ts:242`) — and because a READ cannot grow storage a ≤60 s-stale byte count is safe and only ever wrong in the customer-favorable direction. Every OTHER case — a WRITE verb, a fan-out/kill-switched request, an unconfirmed (`d1Error`) tier, a KV miss, or a near-cap tenant — falls back to the EXACT `runQuotaBatch` path below, byte-identical (`worker/src/lib/quota_request_cache.ts:284`).

# Invariants

- Paid serving requires a confirmed active subscription on BOTH resolution arms: (1) an `active` `tier_selections` row (subscription-gated — the launch-blocker filter, `worker/src/lib/quota.ts:152`), or (2) the `tenant.tier` fallback, which returns a paid class ONLY when an active-subscription row was observed on the same lookup — otherwise a paid `tenant.tier` value is floored to `'free'` (M14 fail-safe, `worker/src/lib/quota.ts:195-196`). An abandoned checkout (`pending_checkout`/`inactive`) is served `free` on both arms.
- The per-tier ceilings served at the edge are exactly the frozen `QUOTAS` rate-card values — no AXIS is silently uncapped except where the value is the explicit `MAX_SAFE_INTEGER` sentinel: `team` uncaps only its request axis (storage stays a finite 1 TB, `worker/src/lib/quota.ts:88`) and only `enterprise` is uncapped on both axes (`worker/src/lib/quota.ts:85-93`).
- The monthly request count is incremented atomically in one round trip (`INSERT … ON CONFLICT … RETURNING`), so two concurrent requests cannot both read the same pre-increment value (`worker/src/lib/quota.ts:606`).
- **The two UNCACHED statements share ONE round trip.** `runQuotaBatch` submits the monthly-counter UPSERT and the storage `SUM(bytes_used)` as a single `db.batch()` (`worker/src/lib/quota.ts:697-761`), which is how the Worker edge issues them on the DEFAULT synchronous path (and the `EDGE_ASYNC_METER` fallback for writes / near-cap / KV-miss / `d1Error`, `worker/src/lib/quota_request_cache.ts:284`); the standalone `checkStorageQuota` / `incrementMonthlyRequestCount` remain for callers that need only one half, and both paths build their SQL from the SAME statement builders (`worker/src/lib/quota.ts:377-383`, `worker/src/lib/quota.ts:599-609`) so a batched read and a serial read can never enforce different things. The merge was driven by measurement, not taste: warm against live prod (n=30, 2026-08-04) the UPSERT cost 152/158/163 ms and the SUM 120/126/130 ms, together the ENTIRE 277/284/302 ms `wdb` phase, and neither reads the other's result.
- **The counter is NOT deferred, and that is a decision with a reason.** Its post-increment value IS the 429 (`requestCapResultForCount`), the same table backs the container's OCI request-cap gate (`crates/corelink-container/src/request_count.rs`) and the `/v1/customer/usage` figure, and the UPSERT is ADDITIVE — a retried deferred flush over-counts and wrongly 429s a paying tenant, a dropped one under-counts past a contracted cap. `ctx.waitUntil` guarantees neither, so on the DEFAULT path the increment stays synchronous (`worker/src/lib/quota.ts:599-609`, `worker/src/lib/quota.ts:620`). The opt-in `EDGE_ASYNC_METER` fast path DOES move the increment to `ctx.waitUntil` (`worker/src/lib/quota_request_cache.ts:318`), but ONLY for a tenant proven more than `burstMargin` below its cap (`worker/src/lib/quota_request_cache.ts:284`), so a dropped async write is a bounded UNDER-count — the direction this counter's fail-open posture already tolerates — never an over-count that would wrongly 429 a paying tenant, and the KV count is refreshed from the D1 `RETURNING` value, never a blind local `+1` (`worker/src/lib/quota_request_cache.ts:320`). A durable deferral (per-tenant DO counter + alarm-driven flush) is possible and is NOT what ships here.
- **Batch = transaction.** A D1 batch fault rolls BOTH statements back, so a fault now leaves the request uncounted where the serial pair could have committed the increment before the SUM failed. That is an UNDER-count — the direction this counter's fail-open posture already produces when the UPSERT itself throws (`counted:false`, `worker/src/lib/quota.ts:729-739`) — and never an over-count.
- Tier resolution and storage enforcement share ONE failure posture: an unconfirmed (`d1Error`) tier never seeds a cap header (`storageQuotaHeaderValue` returns `null`) (`worker/src/lib/quota.ts:263`).

# Gotchas

- **F21 fail-OPEN symmetry — disclosed honestly.** If BOTH tier queries error, `getTierForTenant` returns `{ tier: 'free', d1Error: true }` (`worker/src/lib/quota.ts:205-206`); `checkStorageQuota` then SKIPS the storage SUM and returns `ok:true` for READ-style requests rather than enforce a possibly-wrong `free` cap (`worker/src/lib/quota.ts:344`). This is deliberate: combining an error-derived `free` tier with a successful storage query would 429 a paid tenant who legitimately stores > 10 GiB. The cost of the symmetry is real, though — during a *total* tier-lookup outage a tenant who IS over their real cap is not blocked at the edge on reads. The bound is that this is fail-open only; MUTATING (PUT/POST) requests fail CLOSED with a short Retry-After (`worker/src/lib/quota.ts:398-402`), and the Durable Object's CAS quota FSM remains the deeper net on every write.
- **M14 — the `tenant.tier` fallback is now subscription-guarded.** Fallback arm (2) previously returned whatever valid `Tier` the `tenant.tier` column held with NO `subscription_state = 'active'` re-check, safe only by the migration-0057 `'free'` default. It is now fail-safe: a paid `tenant.tier` value is floored to `'free'` unless an active `tier_selections` row was observed on the same lookup (`isPaidTier(fallbackTier) && !hasActiveSubscription` → `'free'`, `worker/src/lib/quota.ts:195-196`). A rogue or future writer that set `tenant.tier = 'pro'` directly (bypassing `tier_selections`) is therefore served `free`, not paid — closing the billing-integrity seam without altering the authoritative active-subscription arm (`worker/src/lib/quota.ts:152`). The floor return propagates `d1Error: tierSelError` (`worker/src/lib/quota.ts:196`) so an outage-driven floor (step-1 threw) fails OPEN downstream rather than enforcing a possibly-wrong `free` cap — the same F21 posture as the both-queries-failed path.
- The monthly request gate is the *aggregate* monthly cap, NOT the container's per-second token-bucket rate limit — a slow-but-steady tenant can stay under req/s yet exceed the contracted monthly allowance, which is exactly the gap this edge check closes (`worker/src/lib/quota.ts:526`).
- `storageQuotaHeaderValue` emits `"0"` for a genuinely-unlimited tier and `null` (do-not-inject) for an unconfirmed `d1Error` tier — `"0"` is the container's unlimited sentinel and is NOT the same as absence; conflating them re-opens the legacy "fresh tenant uncapped" hole (`worker/src/lib/quota.ts:263`).
