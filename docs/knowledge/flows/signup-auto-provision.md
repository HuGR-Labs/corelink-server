# Signup auto-provision + account-deletion erasure (Clerk webhook)

This is the live edge entry point where a Clerk identity event becomes (or un-becomes) a CoreLink tenant. The `signup-worker` Cloudflare Worker receives Clerk's `user.created` and `user.deleted` webhooks (delivered by Svix), verifies the Svix signature, and then drives two opposite obligations: `user.created` auto-provisions a tenant + a read-write PAT so a stranger can start using the cache, and `user.deleted` enqueues a GDPR right-to-erasure request. Both are auth-state mutations with outsized blast radius, so the whole path is engineered to fail CLOSED — a missing secret or unbound queue returns a 500 that Svix retries, never a silent success. This concept covers the deletion/erasure trigger and the worker wiring; the provisioning happy-path detail and the container-side pilot reservation are in the sibling [signup -> tenant onboarding flow](/launch/signup-onboarding.md), and the Stripe activation that follows is [the Stripe activation webhook](/launch/stripe-activation-webhook.md).

# Role

The webhook is the pre-tenant boundary: it turns a Clerk-authenticated identity into a provisioned tenant (`user.created`), or honors that identity's right-to-be-forgotten by enqueuing erasure (`user.deleted`). It sits in the `signup-worker` worker, distinct from the main API worker, and is the sole place a Clerk lifecycle event crosses into CoreLink's tenant/PAT/D1 state. Because it provisions and erases, it must be idempotent under Svix redelivery and must never silently drop either obligation.

# How it works

- The worker `route()` dispatches `POST /webhooks/clerk` to `handleClerkWebhook`, `POST /webhooks/stripe` to the Stripe handler, `POST /internal/v1/runner/provision-installation` to the runner provisioning primitive, the `GET /install/github/*` trio to the runner GitHub-App install flow, and `/health` to a liveness JSON; anything else is 404 (`apps/signup-worker/src/index.ts:43-67`).
- `handleClerkWebhook` requires `POST`, reads the `svix-id`/`svix-timestamp`/`svix-signature` headers, and rejects a missing header set with 400 before any work (`apps/signup-worker/src/webhooks/clerk.ts:447-459`).
- Svix verification HMAC-SHA256s `${svix-id}.${svix-timestamp}.${body}` and constant-time compares each `v1,<sig>` candidate; an anti-replay window rejects a `svix-timestamp` outside ±300s before any HMAC work; failure is 401 (`apps/signup-worker/src/webhooks/clerk.ts:217-242`, `apps/signup-worker/src/webhooks/clerk.ts:461-470`).
- After verify, the body is parsed and `user.deleted` routes to `handleUserDeleted`, `user.created` falls through to provisioning, and any other event type is a 200 `ignored` no-op (`apps/signup-worker/src/webhooks/clerk.ts:480-495`).
- `user.created` provisioning is gated FAIL-LOUD on the PAT-mint auth key: the pre-flight resolves the DEDICATED `CORELINK_PAT_MINT_AUTH_KEY` first and falls back to the shared `CORELINK_INTERNAL_AUTH_KEY` only when the dedicated key is unset (the container's `/_internal/pat/mint` gate requires the dedicated key with no shared fallback once provisioned — DD-HIGH WP1); an unset, blank, or sub-32-character resolved key returns 500 with ZERO side effects (before the first tenant write) so a Svix redelivery cleanly re-provisions once the secret is set (`apps/signup-worker/src/webhooks/clerk.ts:574-587`). `issuePat` performs the SAME dedicated-first resolution and 32-character floor, throws (rather than minting a stub) on an invalid key, and sends the resolved key as `x-corelink-internal-auth` to the mint endpoint (`apps/signup-worker/src/webhooks/clerk.ts:807-823`, `apps/signup-worker/src/webhooks/clerk.ts:828-835`).
- The webhook validates known Clerk lifecycle IDs (`user_` plus a bounded opaque suffix) before dispatching `user.created` or `user.deleted`; malformed or missing IDs return `400 invalid_clerk_user_id` before any lookup, DSR derivation, or D1 write (`apps/signup-worker/src/webhooks/clerk_erasure.ts:23-26`, `apps/signup-worker/src/webhooks/clerk.ts:480-487`).
- Provisioning has two durable idempotency boundaries: the unique `tenant.clerk_user_id` row and a five-minute `clerk_provisioning_lock` lease claimed atomically before PAT minting. A concurrent delivery that cannot claim the lease returns `409 provisioning_in_progress` (or idempotent success after the winner's live PAT exists); a crashed owner is reclaimable after lease expiry. This closes the race where both deliveries observed the same tenant before either PAT insert (`migrations/d1/0113_clerk_provisioning_lock.sql`, `apps/signup-worker/src/webhooks/clerk_erasure.ts:39-70`, `apps/signup-worker/src/webhooks/clerk.ts:590-627`).
- Colo mapping preserves `afr` as an explicit unprovisioned macro (for example `JNB`, `CPT`, `LOS`, `NBO`); it is rejected before `createTenant`, never silently relabelled as `enam` (`apps/signup-worker/src/webhooks/clerk_identity.ts:86-97`, `apps/signup-worker/src/webhooks/clerk.ts:322-332`).
- `deterministicDsrId` derives a stable v5-shaped UUID from `SHA-256("corelink-dsr-v1:" + clerkUserId)`, so the same deleted account always maps to ONE `dsr_id` and the erasure orchestrator (which dedups per `(dsr_id, backend)`) is idempotent across redeliveries (`apps/signup-worker/src/webhooks/clerk_erasure.ts:75-91`, `apps/signup-worker/src/webhooks/clerk_erasure.ts:162-173`).
- `handleUserDeleted` short-circuits to a 200 `erasure_enqueued:false` no-op when the event carries no user id (`reason:"no_user_id"`) or when no provisioned tenant maps to the Clerk user (`reason:"no_tenant"`) — nothing exists to erase (`apps/signup-worker/src/webhooks/clerk_erasure.ts:228-242`, `apps/signup-worker/src/webhooks/clerk_erasure.ts:262-265`).
- The tenant is resolved by `SELECT tenant_id FROM tenant WHERE clerk_user_id = ?1`; a D1 read error returns 500 (not a no-op) so Svix retries rather than dropping the deletion (`apps/signup-worker/src/webhooks/clerk_erasure.ts:244-259`).
- When a tenant DOES exist but `DSR_QUEUE` is unbound, the handler logs and returns 500 `dsr_queue_unconfigured` — it refuses to ack a deletion it cannot honor (`apps/signup-worker/src/webhooks/clerk_erasure.ts:267-276`).
- On the happy path it builds the `dsr.queued.v1` message (deterministic `dsr_id` + erasure salt + resolved legal-hold), writes an `INSERT OR IGNORE` `dsr_requested` SLA anchor, `DSR_QUEUE.send(msg)`s it, and returns 200 `erasure_enqueued:true` — logging only the pseudonymous `dsr_id`/`tenant_id`, never the salt (`apps/signup-worker/src/webhooks/clerk_erasure.ts:278-285`, `apps/signup-worker/src/webhooks/clerk_erasure.ts:287-341`).
- **The tenant + PAT D1 writes are race-safe and self-serve-active.** `insertTenant` writes the new row `INSERT OR IGNORE` with `tenant_state` hard-coded to `'active'` (self-serve bypasses the DPA-pending pilot flow), and `insertPat` writes `shown_once_consumed = 1` so the one-time reveal endpoint cannot re-surface a plaintext the PLG `/welcome` session already delivered; both are `INSERT OR IGNORE` so a double Svix delivery is a no-op (`apps/signup-worker/src/lib/d1.ts:76-95`, `apps/signup-worker/src/lib/d1.ts:108-130`).
- **After the tenant is created, provisioning writes the `tenant_org_map` (`clerk_org_id → tenant_id`) identity-map row (A1 auto-provision).** In `autoProvisionFromClerkEvent`, immediately after `createTenant` (step 1b), the handler-supplied `writeOrgMap` callback calls `insertTenantOrgMap` — an `INSERT OR IGNORE` on `tenant_org_map` keyed on the Clerk `org_id` if the event carries one, else the user `sub` (`orgMapKeyFor`) — so `POST /internal/v1/auth/resolve-tenant` can map the githugr-scoped principal to its tenant instead of 404-ing `org_not_mapped` and locking the user out. This write is LOAD-BEARING, not best-effort: `insertTenantOrgMap` deliberately does NOT swallow, so a throw propagates out of provisioning → the webhook returns non-2xx and Svix retries (idempotent via the `clerk_org_id` PRIMARY KEY) (`apps/signup-worker/src/webhooks/clerk.ts:343-353`, `apps/signup-worker/src/webhooks/clerk.ts:636-645`, `apps/signup-worker/src/lib/d1.ts:151-162`).
- **Provisioning then seeds the free-tier entitlement row-family so the tenant is FULLY provisioned — not just tenant+org_map+pat.** After `configureTenant`/`region_assigned` and BEFORE `issuePat` (step 2b), the handler-supplied `seedEntitlements` callback calls `seedTenantEntitlements`, which `INSERT OR IGNORE`s two rows: `tier_selections('free','active')` (so billing reads `active`, with the non-NULL `subscription_started_at_ms` the 0039 `subscription_started_when_active` CHECK requires) and `tenant_quota` (the $1,000,000/mo ADR-0068 backstop). Without these the tenant reports billing `inactive` and the quota gate reads empty → a degraded dashboard; the shape is replicated by hand from the login-time provisioner `worker/src/lib/githugr_provision.ts` (the two workers are separate deploy units, so they CONVERGE on the same row-family rather than importing). ⚠️ It deliberately seeds NO `runners_entitlement` row (2026-08-02): Runners is a SEPARATE PAID axis and migration 0070's contract is that the ABSENCE of the row is the zero, so the row it used to write here — added to give the runner cap gate 'a real entitlement' to read — was in fact GRANTING billable compute to every free signup. Like `writeOrgMap` this is LOAD-BEARING + fail-CLOSED (a throw propagates → webhook non-2xx → Svix retries) and CONFIG_DB-gated; running BEFORE `issuePat` means the handler's tenant+live-PAT idempotency guard implies these rows already exist (`apps/signup-worker/src/webhooks/clerk.ts:366-381`, `apps/signup-worker/src/webhooks/clerk.ts:647-660`, `apps/signup-worker/src/lib/d1.ts:247-273`).
- **The signup-worker also hosts the cf-multitenant runner-CI provisioning primitive.** `POST /internal/v1/runner/provision-installation` → `handleInstallationProvision` is an internal-auth-gated endpoint that is DEDICATED-REQUIRED: the ONLY credential it accepts is `CORELINK_RUNNER_PROVISION_AUTH_KEY` at or above `MIN_INTERNAL_AUTH_KEY_LEN` (32) chars, which it constant-time-compares the Bearer against. The shared `CORELINK_INTERNAL_AUTH_KEY` is NOT a fallback and is not even a member of the route's env type, so a later edit cannot reach for it without re-declaring the dependency. Both UNSET and SET-but-sub-floor fail CLOSED. The phase-1 fallback was removed once the dedicated key was bound because, while it existed, the isolation held only for as long as a secret stayed bound — unbinding it would silently re-widen the endpoint to the broad shared secret instead of failing. The two failure modes are deliberately distinct: **no resolvable key is 503** (a fault of OURS, retryable) while a **wrong credential is 401** (a fault of the CALLER); a 403 would tell callers to drop the job (`apps/signup-worker/src/webhooks/github_provision.ts:166-203`, `apps/signup-worker/src/webhooks/github_provision.ts:268-277`). Given an ALREADY-authenticated `{installation_id, tenant_id, repositories[]}`, `INSERT OR IGNORE`s the GitHub-installation→tenant identity row into `tenant_gh_installation_map` (migration 0084) and seeds one `runner_repo_allowlist` row per repo (migration 0085) — the read model the runner-mint authz chokepoint resolves against. The actual D1 batch is no longer inline in the handler: it was extracted into the shared `writeInstallationProvision(db, {installationId, tenantId, repos, nowMs})` (idempotent, `.batch`-transactional where the binding supports it, else sequential), and the handler now DELEGATES to it under its fail-closed `try/catch` (`apps/signup-worker/src/webhooks/github_provision.ts:214-241`, delegated at `apps/signup-worker/src/webhooks/github_provision.ts:313`). That extraction is deliberate: the SAME write path is reused by the identity-gated install-flow callback (the sibling [runner GitHub-App install flow](/flows/runner-github-install.md)), so the fabric-called (Option-A) and self-owned-callback (Option-B) provisioning triggers can never diverge on how the map+allowlist is persisted. It is NOT lazy-provision: it never auto-creates a tenant; the caller owns the authenticated identity→tenant binding (`apps/signup-worker/src/index.ts:51-53`).
    - **B-073 team-seat acceptance is an explicit, verified, one-time capability flow.** The container generates 256 bits of OS randomness, returns the opaque lower-case hex token once, and stores only its SHA-256 digest in `team_member.invitation_token_hash` (migration 0108). The edge `POST /v1/customer/team/accept` rejects unknown fields and client tenant ids, fetches Clerk's primary address from the Backend API, requires `verification.status === "verified"`, dual-reads salted/legacy email pseudonyms, enforces the half-open 14-day window, and performs the audit insert plus conditional `invited → active` update in one D1 batch. The target tenant is selected solely from the token-bound row; a second use, wrong address, expired/future row, missing secret, malformed token, or batch mismatch fails closed (`crates/corelink-container/src/customer_d1_team_audit.rs:318`, `worker/src/lib/team_invitation.ts`, `worker/src/index_special_routes.ts:340-410`). The old signup webhook hash-only auto-accept path is removed (`apps/signup-worker/src/webhooks/clerk.ts`).
    - **B-073 signup helper and in-memory parity.** The legacy signup helper now rejects absent/malformed tokens and applies the same SQL expiry window with five aligned binds (`?1` token digest, `?2/?3` email candidates, `?4/?5` lower/upper time bounds); its fake D1 test models those actual SQLite predicates, including exact-boundary and future-dated mutations (`apps/signup-worker/src/lib/d1.ts:334-374`, `apps/signup-worker/tests/invite-expiry.test.ts`). The InMemory customer handler also returns a mandatory 64-character lower-case hex token, so contract fixtures cannot teach clients that invitation capability is nullable (`crates/corelink-handler-customer/src/handler.rs:674-728`, `crates/corelink-handler-customer/tests/handler_customer.rs:368-386`).
- **The PAT plaintext is classified into PRIVATE metadata, the tenant claims into PUBLIC.** `updateClerkUserMetadata` PATCHes Clerk `public_metadata` with only `{tenant_id, region}` (the legit session-JWT claims) and routes the one-time `pat_plaintext` into `private_metadata` (backend-only, never in the JWT, never readable by `useUser()`) — the secret-classification boundary that keeps the credential out of the client-visible session (`apps/signup-worker/src/lib/clerk-metadata.ts:67-86`, `apps/signup-worker/src/lib/clerk-metadata.ts:82-85`).

# Invariants

- An erasure obligation is NEVER silently dropped: every failure mode after a tenant is resolved (unbound queue, salt-derivation failure, D1 lookup error) returns 500 so Svix redelivers, instead of a misleading 200 (`apps/signup-worker/src/webhooks/clerk_erasure.ts:244-276`, `apps/signup-worker/src/webhooks/clerk_erasure.ts:297-308`, `apps/signup-worker/src/webhooks/clerk_erasure.ts:253-259`).
- The `dsr_id` is deterministic per Clerk user, so a Svix redelivery of the same `user.deleted` enqueues an idempotent message and the `dsr_requested` anchor is an `INSERT OR IGNORE` no-op — erasure never double-runs (`apps/signup-worker/src/webhooks/clerk_erasure.ts:75-91`, `apps/signup-worker/src/webhooks/clerk_erasure.ts:309-323`).
- The erasure salt is derived `HMAC-SHA256(ERASURE_SALT_KEY, dsr_id)`; when the key is absent in a `prod` environment `deriveErasureSalt` THROWS, the caller returns 500, and the predictable non-secret SHA-256 fallback can never reach production (`apps/signup-worker/src/webhooks/clerk_erasure.ts:93-135`).
- Provisioning is fail-CLOSED on its mint secret: `handleClerkWebhook` 500s before writing a tenant row when the resolved mint auth key (`CORELINK_PAT_MINT_AUTH_KEY ?? CORELINK_INTERNAL_AUTH_KEY` — dedicated-first, shared fallback) is unset, blank, or below the 32-character floor, so a half-provisioned PAT-less tenant is never committed (`apps/signup-worker/src/webhooks/clerk.ts:574-587`).
- Secret-bearing PII never reaches Sentry telemetry: `beforeSend`/`beforeSendTransaction` run `scrubSentryEvent` (`apps/signup-worker/src/sentry-scrub.ts`), which default-DENYs sensitive object KEYS (`authorization`/`cookie`/`svix-signature`/`stripe-signature`/`token`/`secret`/`email`, and more) to `[REDACTED]` AND substring-redacts secret/PII SHAPES (CoreLink PATs, bearer/basic auth, Stripe `sk_`/`whsec_` keys, emails) inside message/exception bodies + `extra`/`contexts` values — not just header keys (the WP4 hardening over the old header-key-only filter) — before any event leaves the Worker (`apps/signup-worker/src/index.ts:253-258`).
- The DSR erasure queue consumer captures + rethrows on a thrown error so the Cloudflare queue runtime redelivers the whole batch; the single `queue()` handler dispatches on `batch.queue` (main erasure queue vs `corelink-dsr-erasure-dlq`), and redelivery is safe because the erasure orchestrator is idempotent (`apps/signup-worker/src/index.ts:105-122`).
- The PAT plaintext NEVER enters a client-readable surface: `updateClerkUserMetadata` writes it ONLY to Clerk `private_metadata` (backend-only) and the legit `{tenant_id, region}` claims to `public_metadata`, so the secret is never embedded in the session JWT nor exposed via `useUser()` (`apps/signup-worker/src/lib/clerk-metadata.ts:82-85`).
- A double Svix delivery of the same `user.created` can never create a second tenant or a second PAT: both `insertTenant` and `insertPat` are `INSERT OR IGNORE`, so the second writer is silently dropped (`apps/signup-worker/src/lib/d1.ts:82-85`, `apps/signup-worker/src/lib/d1.ts:114-117`).
- A team-seat flip is bound to the token digest, candidate email hashes, tenant and invitation id, and cannot be double-applied: the atomic D1 batch inserts `team.accepted` and conditionally updates exactly one invited row (`worker/src/lib/team_invitation.ts:82-151`).
- A pending invitation is redeemable only inside the half-open 14-day window (`invited_at_ms > nowMs - TEAM_INVITATION_TTL_MS AND invited_at_ms <= nowMs`) and only for a verified Clerk primary address. Legacy rows without a token digest are intentionally not redeemable and must be re-issued (`migrations/d1/0108_team_member_invitation_security.sql:1-16`).

# Gotchas

- The webhook's `request.cf.colo` is SVIX's sender PoP, NOT the end-user's geo, so residency is deliberately NOT derived from it; webhook-provisioned tenants default to the launch-served region (enam, via `regionFromColo`'s null default) — deriving residency from the Svix PoP was an observed SAM-trap (a US signup Svix-routed via a South-American PoP would be assigned `sam`, which is recognised but NOT provisionable, and REJECTED) (`apps/signup-worker/src/webhooks/clerk.ts:496-513`).
- Idempotency on `user.created` keys on a tenant row AND a still-live PAT — a tenant row alone is treated as a half-failed prior attempt and falls through to re-issue the PAT, never acked as done (`apps/signup-worker/src/webhooks/clerk.ts:515-554`).
- `legal_hold` is resolved from D1 (`tenant_legal_hold` existence) and carried into the message; the read posture on a query error is `false` (erase proceeds) — deliberately, so a not-yet-provisioned hold table cannot silently no-op every deletion (`apps/signup-worker/src/webhooks/clerk_erasure.ts:177-225`, resolved at the enqueue site `apps/signup-worker/src/webhooks/clerk_erasure.ts:278-296`).
