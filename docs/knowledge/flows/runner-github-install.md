# Runner GitHub-App install → tenant-map provisioning flow

This is the edge path that turns "a tenant wants CoreLink Runners to run their CI" into the two control-plane read models the runner-CI fabric consults: `tenant_gh_installation_map` (installation → tenant) and `runner_repo_allowlist` (per-tenant `owner/repo`). It spans the admin-ui (the tenant-bound state mint) and the `signup-worker` (verify + provision), and is engineered around ONE hard constraint: the raw GitHub `installation` payload carries an `installation.id` + repos but **no CoreLink identity**, so binding a tenant off it alone would be exactly the lazy-provisioning the runner-provisioning primitive (DP3) forbids. The identity must instead come FROM the install flow — a Clerk-authed tenant clicks "Install", CoreLink mints an HMAC-signed `state = tenant_id`, and the setup callback verifies that signature to recover the authenticated tenant. The **mint** happens in the admin-ui (the tenant's authenticated surface); the **verify + provision** happen in the signup-worker. Files: `github_install_state.ts` (the worker's signed-state verify + its `signInstallState` mint half), `github_install_callback.ts` (the `setup_url` callback that provisions), `github_app_manifest.ts` (the one-click App-creation flow), and in the admin-ui `lib/install-state.ts` + `app/api/install/github/route.ts` (the "Install" button's server-side mint entry point — a byte-identical HMAC mirror of the worker's, since the two deployables cannot share a module). All three route off the same `signup-worker` entry point that hosts the Clerk/Stripe webhooks and the internal provisioning primitive; the actual map+allowlist write is the shared `writeInstallationProvision` in `github_provision.ts` (see the sibling [signup auto-provision flow](/flows/signup-auto-provision.md), which owns the internal-auth `POST /internal/v1/runner/provision-installation` variant of the same write).

# Role

This flow is the **Option-B (self-owned) runner install path**: the signup-worker owns the whole install→provision handshake end-to-end, rather than delegating the identity binding to an external fabric caller. It is the runner counterpart of the Clerk `user.created` auto-provision — where that turns an identity event into a tenant + PAT, this turns an authenticated install click into an installation→tenant map + repo allowlist. Its authority boundary is precisely the signed `state`: that HMAC is the ONLY thing that authenticates which tenant an installation belongs to, so the whole flow's isolation guarantee rests on that signature being unforgeable and expiry-bounded.

# How it works

- **The install routes hang off the signup-worker `route()` table.** `GET /install/github/app/new` → `handleAppManifestForm`, `GET /install/github/app/created` → `handleAppManifestCallback`, and `GET /install/github/callback` → `handleInstallGithubCallback` are dispatched alongside the Clerk/Stripe webhooks and the internal provisioning primitive, all method-gated to `GET` (`apps/signup-worker/src/index.ts:53-61`, route table `apps/signup-worker/src/index.ts:42-66`).
- **The mint entry point is the admin-ui "Install" button, tenant-bound SERVER-SIDE.** `GET /api/install/github` resolves the canonical CoreLink `tenant_id` from the Clerk session claim (`publicMetadata.tenant_id` or the flattened `tenant_id` — NEVER the client, and NEVER `org_id`/`user_id`, which are Clerk ids not the tenant the entitlement is keyed by), mints the state via `signInstallState`, and 302-redirects into GitHub's App-install page; it 401s without a tenant and fails closed 503 until `INSTALL_STATE_SIGNING_KEY` + `GITHUB_APP_SLUG` are bound (`apps/admin-ui/src/app/api/install/github/route.ts:72-94`, tenant resolve `apps/admin-ui/src/app/api/install/github/route.ts:45-58`). The admin-ui `signInstallState` (`apps/admin-ui/src/lib/install-state.ts:49-58`) is a byte-for-byte mirror of the worker's mint (below); a cross-deployable test pins the two to the same HMAC so drift breaks CI.
- **The install `state` is an HMAC-signed tenant binding, NOT a bearer of secrets.** `signInstallState` emits `<tenant_id>.<exp_ms>.<hex HMAC-SHA256(key,"<tenant_id>.<exp_ms>")>`, HMACing the tenant id AND the expiry together so neither can be tampered without invalidating the signature; the expiry (default 10 min) bounds replay (`apps/signup-worker/src/webhooks/github_install_state.ts:53-63`, TTL `apps/signup-worker/src/webhooks/github_install_state.ts:22`).
- **State verification is constant-time and fail-closed.** `verifyInstallState` splits into exactly 3 parts, recomputes the HMAC and constant-time-compares it BEFORE the expiry check (so a bad-signature and an expired-but-valid-signature take the same path shape), and returns the bound `{tenantId}` only on a good, unexpired signature — otherwise `null`, leaking no distinction to the caller (`apps/signup-worker/src/webhooks/github_install_state.ts:70-90`; the constant-time hex compare `apps/signup-worker/src/webhooks/github_install_state.ts:40-47`).
- **The callback treats the signed state as the SOLE identity source.** `handleInstallGithubCallback` reads `installation_id` + `state` from the query, calls `verifyInstallState`, and 403s on a bad/expired state — it NEVER binds a tenant off the raw `installation_id` (`apps/signup-worker/src/webhooks/github_install_callback.ts:244-256`).
- **Installation OWNERSHIP is proven before binding (the public-flip PREVENTION gate).** After the state authenticates the tenant, when the App's OAuth credentials (`GITHUB_APP_CLIENT_ID` + `GITHUB_APP_CLIENT_SECRET`, from "Request user authorization (OAuth) during installation") are bound, the callback REQUIRES the install-time OAuth `code`, exchanges it for a **user** access token (`exchangeOAuthCode`), and requires the presented `installation_id` to appear in that user's own `GET /user/installations` (`userControlsInstallation`) — a user can only list an installation they administer, so a tenant can no longer bind an installation they do not control. Ordered fail-CLOSED: creds bound but no code / bad exchange / not-controlled ⇒ `403`, BEFORE any App-JWT mint or D1 write; when the creds are UNBOUND the check is skipped (the `public:false` org-only dogfood path, where only org members can install) (`apps/signup-worker/src/webhooks/github_install_callback.ts:271-311`, OAuth exchange `apps/signup-worker/src/webhooks/github_install_callback.ts:163-182`, ownership check `apps/signup-worker/src/webhooks/github_install_callback.ts:193-213`). A STRUCTURAL guard ties the skip to the public state so the two can never diverge: when the new `GITHUB_APP_PUBLIC` env flag is set (`"true"`/`"1"`) the ownership proof is MANDATORY — a public App with UNBOUND OAuth creds is a hard `403` (`install ownership proof required: app is public but oauth creds are unbound`) before any App-JWT mint or D1 write, so it is impossible to ship a public App without the proof; only the non-public dogfood keeps the skip (`apps/signup-worker/src/webhooks/github_install_callback.ts:283-290`).
- **After identity, the callback mints an App JWT → installation token → repo list.** `mintAppJwt` signs an RS256 App JWT (`iss`=app id, ~9-minute window, 60s backdated `iat` for clock skew) from the PKCS#8 private key; `installationToken` exchanges it for an installation access token; `installationRepos` pages `/installation/repositories` into `owner/repo` full names (`apps/signup-worker/src/webhooks/github_install_callback.ts:313-324`, JWT mint `apps/signup-worker/src/webhooks/github_install_callback.ts:92-116`, repo list `apps/signup-worker/src/webhooks/github_install_callback.ts:136-153`). A `null` installation-token exchange and any GitHub API throw are logged (installation-id only — no token/state material) before the callback fails closed, so a token/JWT misconfig surfaces in a `wrangler tail` instead of a silent `done(false)` (`apps/signup-worker/src/webhooks/github_install_callback.ts:319-329`).
- **Provisioning reuses the SAME shared idempotent write as the internal primitive.** On success the callback calls `writeInstallationProvision(db, {installationId, tenantId, repos, nowMs})` — the exact `.batch`-transactional (or sequential-fallback) `INSERT OR IGNORE` into `tenant_gh_installation_map` + `runner_repo_allowlist` that `handleInstallationProvision` delegates to — so the Option-A (fabric-called) and Option-B (self-owned callback) triggers can never diverge on the persisted shape. The persist boundary is bracketed with `persisting` / `persist OK` / `persist FAILED` logs so a live install that returns 200 while writing nothing is diagnosable (`apps/signup-worker/src/webhooks/github_install_callback.ts:339-350`, shared writer `apps/signup-worker/src/webhooks/github_provision.ts:88-115`).
- **After the write, the callback detects a cross-tenant binding conflict.** The map `installation_id` is a PK written `INSERT OR IGNORE` (first-writer-wins), and the signed `state` proves only the tenant — NOT that this tenant controls the presented `installation_id`. So the callback re-reads the bound row and refuses to report success if the installation is already owned by a DIFFERENT tenant (best-effort — only a confirmed cross-tenant row fails; a read fault never blocks a legitimate provision) (`apps/signup-worker/src/webhooks/github_install_callback.ts:361-386`). With the OAuth ownership proof now running BEFORE the write (above), this post-write conflict guard is defense-in-depth rather than the sole protection.
- **The callback ends in a browser redirect (or a plain response) carrying a result flag.** `done` 302-redirects back to `${ADMIN_UI_PUBLIC_URL}/settings/runners?runner_install=ok|error&reason=…` when the admin-ui base is bound, else returns a plain `200`/`502` — always `cache-control: no-store` (`apps/signup-worker/src/webhooks/github_install_callback.ts:215-226`).
- **The App itself is created via the one-click app-manifest flow (there is no REST endpoint to create an App).** `handleAppManifestForm` serves an auto-submitting HTML form that POSTs a pre-filled `manifest` JSON to `github.com/organizations/<ORG>/settings/apps/new`; the manifest freezes the registration shape — `setup_url` → `/install/github/callback` (this flow's identity-gated callback), `hook_attributes.url` → `/webhooks/github`, `public:false` (org-only dogfood), the `actions:read`/`metadata:read` permissions, and — for `default_events` — ONLY the subscribable `workflow_job` (granted by `actions:read`). The `installation`/`installation_repositories` App-lifecycle events are delivered to the webhook automatically and MUST NOT be listed in the manifest — GitHub rejects the registration ("Default events are not supported by permissions") if you do (`apps/signup-worker/src/webhooks/github_app_manifest.ts:117-150`, manifest builder `apps/signup-worker/src/webhooks/github_app_manifest.ts:69-112`).
- **The manifest callback exchanges the temporary `code` for permanent App credentials and displays them ONCE.** `handleAppManifestCallback` POSTs `/app-manifests/{code}/conversions`, receives `{id, pem, webhook_secret, client_id, slug}` (the private-key PEM is returned by GitHub exactly once), and renders a `noindex` + `no-store` one-time hand-off page listing the secrets the operator must set (`GITHUB_APP_ID`/`GITHUB_APP_PRIVATE_KEY`/`GITHUB_APP_WEBHOOK_SECRET`) — a Worker cannot set its own secrets, so this manual copy is the hand-off (`apps/signup-worker/src/webhooks/github_app_manifest.ts:164-239`, conversion exchange `apps/signup-worker/src/webhooks/github_app_manifest.ts:185-209`).

# Invariants

- **No tenant is ever bound off the raw installation id.** The only authenticated tenant source is the signed `state`; `handleInstallGithubCallback` 403s when `verifyInstallState` returns `null`, so a forged/replayed/expired install can never provision a map row under someone else's tenant (`apps/signup-worker/src/webhooks/github_install_callback.ts:251-256`, verify `apps/signup-worker/src/webhooks/github_install_state.ts:70-90`).
- **The state signature is unforgeable and non-malleable.** The HMAC covers `<tenant_id>.<exp_ms>` together, so an attacker cannot lift a valid signature onto a different tenant id or push out the expiry; verification recomputes over the SAME payload and constant-time-compares (`apps/signup-worker/src/webhooks/github_install_state.ts:60-62`, `apps/signup-worker/src/webhooks/github_install_state.ts:85-88`).
- **The install callback is INERT until fully configured — never partial-provisions.** With any of `GITHUB_APP_ID` / `GITHUB_APP_PRIVATE_KEY` / `INSTALL_STATE_SIGNING_KEY` / `CONFIG_DB` unbound it returns `503` before doing any work, so a half-configured env cannot verify state against a missing key nor persist against a missing DB (`apps/signup-worker/src/webhooks/github_install_callback.ts:235-242`).
- **Provisioning is fail-closed on the persist step — and no longer silently.** A throw from the shared `writeInstallationProvision` (D1 fault) is caught, LOGGED with the real error (the catch previously swallowed it, leaving the callback un-debuggable), and turned into a `runner_install=error` result — never a claimed success — and the write itself is `INSERT OR IGNORE` so a re-run of the same install is a harmless idempotent no-op (`apps/signup-worker/src/webhooks/github_install_callback.ts:339-360`, `apps/signup-worker/src/webhooks/github_provision.ts:92-114`).
- **The step-1 form is operator-gated; the step-3 callback is code-gated (GitHub can't carry the setup token).** `handleAppManifestForm` `503`s when `GITHUB_APP_SETUP_TOKEN` is unbound and `403`s (constant-time) on a wrong token, so only the operator can initiate registration (`apps/signup-worker/src/webhooks/github_app_manifest.ts:120-126`). But `handleAppManifestCallback` is GitHub's `redirect_url` — GitHub appends ONLY `?code=…`, never the setup token — so it gates on possession of the single-use, unguessable, ~1h-TTL `code` itself (`400` if absent), which IS the manifest-flow's designed auth boundary; gating it on the setup token would 403 every legitimate redirect (`apps/signup-worker/src/webhooks/github_app_manifest.ts:170-172`).

# Gotchas

- **ISOLATION — installation ownership is now PROVEN (was the HARD GATE on going public).** The signed `state` authenticates only the TENANT; the App-JWT→installation-token exchange proves nothing (a GitHub App can mint a token for ANY of its installations), so on its own the callback could bind another party's `installation_id` to a tenant (first-writer-wins), and `#633` could only DETECT an already-bound conflict, not PREVENT the initial mis-binding. This is now closed by the OAuth ownership proof above: with the App's OAuth creds bound, the caller must present an install-time `code` whose **user** token lists the presented `installation_id` in `GET /user/installations` — which a user gets only for an installation they administer — so a tenant can no longer bind an installation it does not control (`apps/signup-worker/src/webhooks/github_install_callback.ts:271-311`). This makes flipping the App **public** for real self-serve customers safe; the remaining go-public steps are purely operator config (enable OAuth-during-install + generate the client secret in App settings, bind `GITHUB_APP_CLIENT_ID`/`_SECRET`, toggle public). While the creds are UNBOUND the check is skipped, but that path is `public:false` org-only (only org members can install), so the dogfood is unaffected. The post-write cross-tenant conflict guard (above) remains as defense-in-depth. (Launch-audit HIGH — resolved; the reverse — binding YOUR repo to THEIR tenant — was already blocked since the allowlist is populated from the installation's real repos, `apps/signup-worker/src/webhooks/github_install_callback.ts:136-153`.)
- The App private key GitHub returns from the manifest conversion is **PKCS#1** PEM, but the Worker's WebCrypto `importKey("pkcs8", …)` needs **PKCS#8** — the one-time hand-off page explicitly tells the operator to run `openssl pkcs8 -topk8 -nocrypt` before setting `GITHUB_APP_PRIVATE_KEY` (`apps/signup-worker/src/webhooks/github_app_manifest.ts:226-228`, PKCS#8 decode at the callback `apps/signup-worker/src/webhooks/github_install_callback.ts:77-86`).
- The manifest sets `setup_on_update: true` so a NEW installation always re-hits the `setup_url` callback and re-provisions — the callback is designed to be idempotent for exactly this repeat-install case (`apps/signup-worker/src/webhooks/github_app_manifest.ts:79-80`).
- The manifest `code` is single-use with a ~1h TTL, and the private-key PEM is displayed exactly once — there is no re-fetch; losing the tab means re-running the whole manifest flow to mint a fresh App (`apps/signup-worker/src/webhooks/github_app_manifest.ts:170-186`).
