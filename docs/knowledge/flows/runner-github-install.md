# Runner GitHub-App install → tenant-map provisioning flow

This is the edge path that turns "a tenant wants CoreLink Runners to run their CI" into the two control-plane read models the runner-CI fabric consults: `tenant_gh_installation_map` (installation → tenant) and `runner_repo_allowlist` (per-tenant `owner/repo`). It spans the admin-ui (the tenant-bound state mint) and the `signup-worker` (verify + provision), and is engineered around ONE hard constraint: the raw GitHub `installation` payload carries an `installation.id` + repos but **no CoreLink identity**, so binding a tenant off it alone would be exactly the lazy-provisioning the runner-provisioning primitive (DP3) forbids. The identity must instead come FROM the install flow — a Clerk-authed tenant clicks "Install", CoreLink mints an HMAC-signed `state = tenant_id`, and the setup callback verifies that signature to recover the authenticated tenant. The **mint** happens in the admin-ui (the tenant's authenticated surface); the **verify + provision** happen in the signup-worker. Files: `github_install_state.ts` (the worker's signed-state verify + its `signInstallState` mint half), `github_install_callback.ts` (the `setup_url` callback that provisions), `github_app_manifest.ts` (the one-click App-creation flow), and in the admin-ui `lib/install-state.ts` + `app/api/install/github/route.ts` (the "Install" button's server-side mint entry point — a byte-identical HMAC mirror of the worker's, since the two deployables cannot share a module). All three route off the same `signup-worker` entry point that hosts the Clerk/Stripe webhooks and the internal provisioning primitive; the actual map+allowlist write is the shared `writeInstallationProvision` in `github_provision.ts` (see the sibling [signup auto-provision flow](/flows/signup-auto-provision.md), which owns the internal-auth `POST /internal/v1/runner/provision-installation` variant of the same write).

# Role

This flow is the **Option-B (self-owned) runner install path**: the signup-worker owns the whole install→provision handshake end-to-end, rather than delegating the identity binding to an external fabric caller. It is the runner counterpart of the Clerk `user.created` auto-provision — where that turns an identity event into a tenant + PAT, this turns an authenticated install click into an installation→tenant map + repo allowlist. Its authority boundary is precisely the signed `state`: that HMAC is the ONLY thing that authenticates which tenant an installation belongs to, so the whole flow's isolation guarantee rests on that signature being unforgeable and expiry-bounded.

# How it works

- **The install routes hang off the signup-worker `route()` table.** `GET /install/github/app/new` → `handleAppManifestForm`, `GET /install/github/app/created` → `handleAppManifestCallback`, and `GET /install/github/callback` → `handleInstallGithubCallback` are dispatched alongside the Clerk/Stripe webhooks and the internal provisioning primitive, all method-gated to `GET` (`apps/signup-worker/src/index.ts:53-61`, route table `apps/signup-worker/src/index.ts:42-66`).
- **The mint entry point is the admin-ui "Install" button, tenant-bound SERVER-SIDE.** `GET /api/install/github` resolves the canonical CoreLink `tenant_id` from the Clerk session claim (`publicMetadata.tenant_id` or the flattened `tenant_id` — NEVER the client, and NEVER `org_id`/`user_id`, which are Clerk ids not the tenant the entitlement is keyed by), mints the state via `signInstallState`, and 302-redirects into GitHub's App-install page; it 401s without a tenant and fails closed 503 until `INSTALL_STATE_SIGNING_KEY` + `GITHUB_APP_SLUG` are bound (`apps/admin-ui/src/app/api/install/github/route.ts:72-94`, tenant resolve `apps/admin-ui/src/app/api/install/github/route.ts:45-58`). The admin-ui `signInstallState` (`apps/admin-ui/src/lib/install-state.ts:49-58`) is a byte-for-byte mirror of the worker's mint (below); a cross-deployable test pins the two to the same HMAC so drift breaks CI.
- **The install `state` is an HMAC-signed tenant binding, NOT a bearer of secrets.** `signInstallState` emits `<tenant_id>.<exp_ms>.<hex HMAC-SHA256(key,"<tenant_id>.<exp_ms>")>`, HMACing the tenant id AND the expiry together so neither can be tampered without invalidating the signature; the expiry (default 10 min) bounds replay (`apps/signup-worker/src/webhooks/github_install_state.ts:53-63`, TTL `apps/signup-worker/src/webhooks/github_install_state.ts:22`).
- **State verification is constant-time and fail-closed.** `verifyInstallState` splits into exactly 3 parts, recomputes the HMAC and constant-time-compares it BEFORE the expiry check (so a bad-signature and an expired-but-valid-signature take the same path shape), and returns the bound `{tenantId}` only on a good, unexpired signature — otherwise `null`, leaking no distinction to the caller (`apps/signup-worker/src/webhooks/github_install_state.ts:70-90`; the constant-time hex compare `apps/signup-worker/src/webhooks/github_install_state.ts:40-47`).
- **The callback treats the signed state as the SOLE identity source.** `handleInstallGithubCallback` reads `installation_id` + `state` from the query, calls `verifyInstallState`, and 403s on a bad/expired state — it NEVER binds a tenant off the raw `installation_id` (`apps/signup-worker/src/webhooks/github_install_callback.ts:160-172`).
- **After identity, the callback mints an App JWT → installation token → repo list.** `mintAppJwt` signs an RS256 App JWT (`iss`=app id, ~9-minute window, 60s backdated `iat` for clock skew) from the PKCS#8 private key; `installationToken` exchanges it for an installation access token; `installationRepos` pages `/installation/repositories` into `owner/repo` full names (`apps/signup-worker/src/webhooks/github_install_callback.ts:174-185`, JWT mint `apps/signup-worker/src/webhooks/github_install_callback.ts:68-92`, repo list `apps/signup-worker/src/webhooks/github_install_callback.ts:111-129`).
- **Provisioning reuses the SAME shared idempotent write as the internal primitive.** On success the callback calls `writeInstallationProvision(db, {installationId, tenantId, repos, nowMs})` — the exact `.batch`-transactional (or sequential-fallback) `INSERT OR IGNORE` into `tenant_gh_installation_map` + `runner_repo_allowlist` that `handleInstallationProvision` delegates to — so the Option-A (fabric-called) and Option-B (self-owned callback) triggers can never diverge on the persisted shape (`apps/signup-worker/src/webhooks/github_install_callback.ts:187-197`, shared writer `apps/signup-worker/src/webhooks/github_provision.ts:88-115`).
- **The callback ends in a browser redirect (or a plain response) carrying a result flag.** `done` 302-redirects back to `${ADMIN_UI_PUBLIC_URL}/settings/runners?runner_install=ok|error&reason=…` when the admin-ui base is bound, else returns a plain `200`/`502` — always `cache-control: no-store` (`apps/signup-worker/src/webhooks/github_install_callback.ts:131-142`).
- **The App itself is created via the one-click app-manifest flow (there is no REST endpoint to create an App).** `handleAppManifestForm` serves an auto-submitting HTML form that POSTs a pre-filled `manifest` JSON to `github.com/organizations/<ORG>/settings/apps/new`; the manifest freezes the registration shape — `setup_url` → `/install/github/callback` (this flow's identity-gated callback), `hook_attributes.url` → `/webhooks/github`, `public:false` (org-only dogfood), the `actions:read`/`metadata:read` permissions, and — for `default_events` — ONLY the subscribable `workflow_job` (granted by `actions:read`). The `installation`/`installation_repositories` App-lifecycle events are delivered to the webhook automatically and MUST NOT be listed in the manifest — GitHub rejects the registration ("Default events are not supported by permissions") if you do (`apps/signup-worker/src/webhooks/github_app_manifest.ts:107-140`, manifest builder `apps/signup-worker/src/webhooks/github_app_manifest.ts:69-102`).
- **The manifest callback exchanges the temporary `code` for permanent App credentials and displays them ONCE.** `handleAppManifestCallback` POSTs `/app-manifests/{code}/conversions`, receives `{id, pem, webhook_secret, client_id, slug}` (the private-key PEM is returned by GitHub exactly once), and renders a `noindex` + `no-store` one-time hand-off page listing the secrets the operator must set (`GITHUB_APP_ID`/`GITHUB_APP_PRIVATE_KEY`/`GITHUB_APP_WEBHOOK_SECRET`) — a Worker cannot set its own secrets, so this manual copy is the hand-off (`apps/signup-worker/src/webhooks/github_app_manifest.ts:146-229`, conversion exchange `apps/signup-worker/src/webhooks/github_app_manifest.ts:175-199`).

# Invariants

- **No tenant is ever bound off the raw installation id.** The only authenticated tenant source is the signed `state`; `handleInstallGithubCallback` 403s when `verifyInstallState` returns `null`, so a forged/replayed/expired install can never provision a map row under someone else's tenant (`apps/signup-worker/src/webhooks/github_install_callback.ts:167-172`, verify `apps/signup-worker/src/webhooks/github_install_state.ts:70-90`).
- **The state signature is unforgeable and non-malleable.** The HMAC covers `<tenant_id>.<exp_ms>` together, so an attacker cannot lift a valid signature onto a different tenant id or push out the expiry; verification recomputes over the SAME payload and constant-time-compares (`apps/signup-worker/src/webhooks/github_install_state.ts:60-62`, `apps/signup-worker/src/webhooks/github_install_state.ts:85-88`).
- **The install callback is INERT until fully configured — never partial-provisions.** With any of `GITHUB_APP_ID` / `GITHUB_APP_PRIVATE_KEY` / `INSTALL_STATE_SIGNING_KEY` / `CONFIG_DB` unbound it returns `503` before doing any work, so a half-configured env cannot verify state against a missing key nor persist against a missing DB (`apps/signup-worker/src/webhooks/github_install_callback.ts:151-158`).
- **Provisioning is fail-closed on the persist step.** A throw from the shared `writeInstallationProvision` (D1 fault) is caught and turned into a `runner_install=error` result — never a claimed success — and the write itself is `INSERT OR IGNORE` so a re-run of the same install is a harmless idempotent no-op (`apps/signup-worker/src/webhooks/github_install_callback.ts:187-197`, `apps/signup-worker/src/webhooks/github_provision.ts:92-114`).
- **Both manifest routes are operator-gated, fail-closed.** `handleAppManifestForm` and `handleAppManifestCallback` `503` when `GITHUB_APP_SETUP_TOKEN` is unbound and `403` (constant-time compare) on a wrong token, so only the operator can register the App or read the one-time credential page (`apps/signup-worker/src/webhooks/github_app_manifest.ts:110-116`, `apps/signup-worker/src/webhooks/github_app_manifest.ts:152-158`).

# Gotchas

- The App private key GitHub returns from the manifest conversion is **PKCS#1** PEM, but the Worker's WebCrypto `importKey("pkcs8", …)` needs **PKCS#8** — the one-time hand-off page explicitly tells the operator to run `openssl pkcs8 -topk8 -nocrypt` before setting `GITHUB_APP_PRIVATE_KEY` (`apps/signup-worker/src/webhooks/github_app_manifest.ts:217-219`, PKCS#8 decode at the callback `apps/signup-worker/src/webhooks/github_install_callback.ts:53-62`).
- The manifest sets `setup_on_update: true` so a NEW installation always re-hits the `setup_url` callback and re-provisions — the callback is designed to be idempotent for exactly this repeat-install case (`apps/signup-worker/src/webhooks/github_app_manifest.ts:79-80`).
- The manifest `code` is single-use with a ~1h TTL, and the private-key PEM is displayed exactly once — there is no re-fetch; losing the tab means re-running the whole manifest flow to mint a fresh App (`apps/signup-worker/src/webhooks/github_app_manifest.ts:165-174`).
