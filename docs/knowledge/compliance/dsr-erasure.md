CoreLink is a multi-tenant content-addressable cache sold self-serve to SMBs, so it holds tenant PII and content and must honour data-subject erasure (GDPR Art.17 / LGPD Art.18). The pipeline has two halves: a pure-logic **self-service DSR endpoint** (`corelink-dsr`) that intakes a request, gates destructive arms behind step-up MFA, and issues a signed receipt; and the **live Wave-1 erasure engine** in the container (`routes/dsr.rs`) that actually deletes real bytes across the configured backends and is re-confirmed by a 24h verify sweep. A go-live security review found erasure "complete-by-construction for the live data planes (CAS + AC + D1 + Stripe)" with no launch-blocking finding (`docs/security/2026-06-23-secreview-gdpr-residency.md:12-18`). The pipeline is fail-CLOSED at the state-mutation seam: every state mutation is preceded by a durable audit row, and the `VerifiedComplete` decision is DUAL-gated — a backend counts as failed when `hash != canonical || !prior.outcome.is_successful()`, i.e. both a canonical-empty re-fingerprint AND the per-backend success tombstone are required (`crates/corelink-privacy-erasure-worker/src/orchestrator.rs:503`), and that tombstone is only written when the adapter's `erase(...)?` returned Ok (`crates/corelink-privacy-erasure-worker/src/orchestrator.rs:339`). **But honesty about what `VerifiedComplete` proves (red-team-confirmed):** only THREE of the live backends actually re-scan at verify time — D1 (`remaining_rows`), R2-CAS (`count_cas_remaining`), R2-AC (`count_ac_remaining`) LIST/COUNT real storage and return a non-canonical fingerprint if anything survives, so for those planes the re-fingerprint half of the gate is a genuine independent cross-check. **The Stripe adapter and the 8 not-shipped "not-applicable" backends return `Ok(CANONICAL_EMPTY_TENANT_HASH)` UNCONDITIONALLY, without querying the backend** (`crates/corelink-container/src/routes/dsr/adapter_stripe.rs:140-150` — a deferred no-op, ADR-S11-013; `crates/corelink-container/src/routes/dsr/adapter_not_applicable.rs:66-72`). For those backends the dual gate collapses to its erase-time-success half ALONE — the re-fingerprint can never fail. So `VerifiedComplete` attests "a verify sweep returned Complete," which is verify-time-PROVEN only for D1/CAS/AC; for Stripe it rests entirely on the single original `erase(...)` returning Ok. A Stripe pseudonymize that returned Ok but did not actually redact (a Stripe-side fault, a partial redaction, or post-erase re-population) would NEVER be caught by the sweep → `VerifiedComplete` + the Ed25519 attestation sign Complete while Stripe PII survives. This is a real, if narrow, sign-while-PII-may-survive exposure on the Stripe/not-applicable arms — `VerifiedComplete` is NOT independent proof of Stripe (or other-backend) erasure.

# Role

This control implements the data-subject right-to-erasure (and the sibling DSR rights: access, portability, rectification, restriction, objection). It is the compliance seam that converts a customer's "delete my account/data" demand — whether self-served or originated from a Clerk `user.deleted` webhook — into a verified, audited, attested deletion across CoreLink's storage backends, with outcome-confidential cross-tenant lookups (no existence oracle on the wire — but not timing-constant; see How it works) and a customer-held proof-of-submission receipt.

# How it works

- **Intake (self-service endpoint).** `InMemoryDsrEndpoint::submit` runs a serial pipeline per request: it first fires the `request_received` audit row BEFORE any state mutation, then an idempotency lookup, then the MFA gate, then receipt-issue + store-insert (`crates/corelink-dsr/src/endpoint.rs:299-418`).
- **MFA step-up on destructive arms only.** Erasure and Rectification require a non-empty step-up token; without one the orchestrator returns `MfaRequired` after a `mfa_step_up_required` audit, with no store insert; read/policy arms skip the gate (`crates/corelink-dsr/src/endpoint.rs:351-379`).
- **The MFA verifier contract.** `MfaStepUpVerifier::verify` is fail-CLOSED: `None` token → `Required`, empty bytes / bad binding → `Invalid`, expired → `Expired`; production wiring binds it to a 5-min WebAuthn step-up token scoped to `op_class = "dsr_destructive"` (`crates/corelink-dsr/src/mfa.rs:80-102`).
- **Idempotency by `(tenant_id, request_id)`.** A prior non-terminal ticket short-circuits to the original receipt + SLA deadline with no second audit/insert (the receipt+SLA reuse arm `crates/corelink-dsr/src/endpoint.rs:327-333`); a replay with a divergent `(data_subject_id, request_kind, jurisdiction)` tuple is a SEV-1 forensic anomaly surfaced as `DivergentPayload` in the store insert (`crates/corelink-dsr/src/store.rs:133-158`).
- **Receipt + SLA.** On accept, a JWT (RS256) receipt is issued by `DsrReceipt::new` with a 90-day anti-replay expiry cap (`crates/corelink-dsr/src/receipt.rs:136-149`, doc-contract `crates/corelink-dsr/src/lib.rs:127-131`) and an SLA deadline derived per jurisdiction (LGPD 15d / GDPR 30d / CCPA 45d) by the `pub const fn sla_for` enforcer (`crates/corelink-dsr/src/event.rs:403`, doc-contract `crates/corelink-dsr/src/lib.rs:116-119`).
- **Status poll is outcome-confidential (no existence oracle), not timing-constant.** `poll_status` returns the ticket status on a hit, but a miss OR a cross-tenant lookup both surface as `RequestRejected{IdentityVerificationFailed}` — never disclosing on the response *outcome* whether a `request_id` exists for another tenant (`crates/corelink-dsr/src/endpoint.rs:420-457`). It is NOT timing-constant, though: the two arms take structurally different code paths — the hit arm reads the ticket and emits a `StatusPolled` audit carrying the formatted status, while the miss/cross-tenant arm emits a `RequestRejected` audit (`crates/corelink-dsr/src/endpoint.rs:428-455`). Timing/side-channel observers are not in the threat model here — only the wire *response* is confidential.
- **Live erasure intake (container).** `POST /_internal/dsr/erase` deserialises the `dsr.queued.v1` message (forwarded by the signup-worker queue consumer for the Clerk `user.deleted` path), maps it to a canonical `ErasureRequest`, and drives the 12-backend orchestrator via `handle_erase` (`crates/corelink-container/src/routes/dsr.rs:429-451`).
- **Self-serve account-delete uses the same DSR message + anchor (LIVE).** A self-serve account delete routes through `routes/customer.rs::handle_account_delete` (`crates/corelink-container/src/routes/customer.rs:940`), which builds a `dsr.queued.v1` message and `INSERT OR IGNORE`s a `dsr_requested` anchor row, then hands erasure to the `DsrErasureSink` trait — production wires `dsr::InProcessErasureSink` (via `routes/customer.rs::account_deletion_from_env`), which drives the **same** in-process, D1-backed erasure worker the `/_internal/dsr/erase` consumer runs (the container has no CF Queue producer, so the "enqueue" is a synchronous same-worker drive, not an async queue). `None` in dev/CI → the route fails CLOSED 503; in prod the sink is wired (deployed 2026-06-26).
- **The 12 backends, honestly reconciled.** `build_d1_worker` wires REAL transports for the 4 live planes — D1 erase-set, R2 CAS, R2 AC, and Stripe pseudonymisation — and reconciles the other 8 (Neon/KV/Loki/audit/legal-hold/evidence, not shipped in prod) to `NotApplicable` with a documented reason each, a truthful GDPR record not a silent skip (`crates/corelink-container/src/routes/dsr.rs:189-244`).
- **CAS tombstone / per-hash erase.** `POST /_internal/cas/:tenant/:hash/erase` deletes the blob from R2 and writes a durable `cas_tombstone` (migration 0067) so subsequent reads return 410 Gone, never 404 or 200 (`crates/corelink-container/src/routes/cas_erase.rs:1-8`, `D1TombstoneStore::upsert` `crates/corelink-container/src/routes/cas_erase.rs:462-486`).
- **Bloom-gated tombstone reads.** `BloomTombstoneStore::is_tombstoned` answers a definitely-absent fast-path only against a bloom seeded from the authoritative D1 set, falling through to D1 on maybe-present or a just-reloaded epoch (`crates/corelink-container/src/routes/cas_erase.rs:830-850`).
- **24h verify sweep + attestation.** `POST /_internal/dsr/verify` re-fingerprints every backend via `verify_erasure`; on a fully `VerifiedComplete` decision it signs an Ed25519 erasure attestation and writes a D1 INDEX row for it (best-effort, fail-OPEN since the erasure is already done and audited) (`crates/corelink-container/src/routes/dsr.rs:503-514`; the `VerifiedComplete` sign gate `crates/corelink-container/src/routes/dsr.rs:503`, `attestation::sign_and_persist` call `crates/corelink-container/src/routes/dsr.rs:505`). The signature is **index-only — NOT durably persisted**: `sign_and_persist` writes only the `erasure_public_keys` + `erasure_attestations` D1 index rows; the R2 (7-year) persistence and the public verify endpoint are WI-S11-008 wiring not yet live (consistent with the sibling `compliance/erasure-attestation` correction). And the fail-OPEN is total: the verify HTTP response returns 200 `verified_complete` REGARDLESS of whether any attestation was produced (`crates/corelink-container/src/routes/dsr.rs:498-516`) — on any env where `ERASURE_ATTESTATION_SEED_HEX` is unset/malformed, `sign_and_persist` returns silently with NO row written (`crates/corelink-container/src/routes/dsr/attestation.rs:114-120`) yet the customer still gets the `verified_complete` label and ZERO signed artifact (see `compliance/erasure-attestation`).

# Invariants

- **Audit-before-mutation, fail-CLOSED.** Every decision arm fires its canonical audit row BEFORE the state-mutating step; an audit failure aborts the request and propagates `DsrError::Audit` with no mutation past that point (`crates/corelink-dsr/src/endpoint.rs:312-318`).
- **MFA mandatory for Erasure + Rectification, never for read/policy arms.** The gate is structural in the orchestrator pipeline (`crates/corelink-dsr/src/endpoint.rs:354-379`); the verifier impl rejects `None`/empty tokens (`crates/corelink-dsr/src/mfa.rs:146-154`); token expiry is in the trait contract (`crates/corelink-dsr/src/mfa.rs:80-102`).
- **Tenant isolation is structural.** The ticket store is keyed `(tenant_id, request_id)` leftmost, so cross-tenant reads are impossible by construction (`crates/corelink-dsr/src/store.rs:45`).
- **Erasure intake is legitimacy-gated (anti mass-erase).** Every erase binds to a D1-authenticated `dsr_requested` row; a forged body-asserted `tenant_id` with the shared internal key lands as `Rejected` → HTTP 422, no fan-out, no bytes deleted; a D1 fault also fails CLOSED (`crates/corelink-container/src/routes/dsr.rs:457-459`, legitimacy store `crates/corelink-container/src/routes/dsr.rs:180-184`).
- **The destructive route is mounted only with a ≥32-char dedicated key.** `build_state_from_env` prefers `CORELINK_ERASE_AUTH_KEY`, falls back to the shared internal key, and refuses to mount below the 32-char floor (`crates/corelink-container/src/routes/dsr.rs:316-332`); the check itself is constant-time, length-folded (`crates/corelink-container/src/routes/dsr.rs:126-143`).
- **"Complete" is verify-time-PROVEN only for D1/CAS/AC — NOT for Stripe or the not-applicable arms (red-team-confirmed).** The attestation is signed only on the `VerifiedComplete` arm (`crates/corelink-container/src/routes/dsr.rs:503`), which the orchestrator emits iff EVERY backend clears a DUAL gate: its re-fingerprint equals the canonical-empty sentinel AND its original erase succeeded — `hash != canonical || !prior.outcome.is_successful()` increments `failed_count`, and any non-zero `failed_count` downgrades the decision to `VerifiedPartial` → no signature (`crates/corelink-privacy-erasure-worker/src/orchestrator.rs:503`, `crates/corelink-privacy-erasure-worker/src/orchestrator.rs:512-521`). The `prior` success tombstone is only written when the adapter's `erase(...)?` returned Ok (`crates/corelink-privacy-erasure-worker/src/orchestrator.rs:339`); a failed OR missing backend erase leaves no prior tombstone → `failed_count++` → `VerifiedPartial` → no sign (`crates/corelink-privacy-erasure-worker/src/orchestrator.rs:449-477`). **Crucially, the re-fingerprint half of the gate is a REAL independent re-scan only for the three backends that actually LIST/COUNT storage at verify time** — D1 (`remaining_rows`), R2-CAS (`count_cas_remaining`), R2-AC (`count_ac_remaining`), each returning a non-canonical fingerprint when bytes survive. **The Stripe adapter and the 8 not-shipped backends return `Ok(CANONICAL_EMPTY_TENANT_HASH)` UNCONDITIONALLY without querying the backend** (`crates/corelink-container/src/routes/dsr/adapter_stripe.rs:140-150`, ADR-S11-013 deferred; `crates/corelink-container/src/routes/dsr/adapter_not_applicable.rs:66-72`) — for those arms the re-fingerprint can never fail, so the dual gate collapses to the single erase-time `prior.outcome` Ok. So PII surviving D1/CAS/AC DOES block `VerifiedComplete`; but a Stripe pseudonymize that returned Ok yet left PII (Stripe-side fault / partial redaction / post-erase re-population) is NEVER re-checked by the sweep → `VerifiedComplete` + the attestation sign Complete while Stripe PII survives. This IS a (narrow) sign-while-PII-may-survive path on the Stripe/not-applicable arms; the deeper per-customer `metadata.pii_redacted` re-query that would close it is deferred (ADR-S11-013). Do NOT read `VerifiedComplete` as independent proof of Stripe erasure.
- **A tombstoned hash never resurrects.** A read of a tombstoned digest returns 410 on the native CAS route — the read-side enforcer short-circuits `Ok(true) => return (StatusCode::GONE, "erased")` BEFORE the R2 GET (`crates/corelink-container/src/routes/cas.rs:665-676`, tombstone-WRITE side `crates/corelink-container/src/routes/cas_erase.rs:1-8`), a re-PUT is refused, and a gate transport fault fails CLOSED 503; the bloom is re-seeded from D1 on every reload to close the cross-writer false-negative window (`crates/corelink-container/src/routes/cas_erase.rs:797-825`).
- **The receipt caps customer-side replay at 90 days.** `DsrReceipt::is_expired` enforces the `submitted + 90d` cap independent of DB state (`crates/corelink-dsr/src/receipt.rs:153-154`).

# Gotchas

- The `corelink-dsr` crate is the **pure-logic skeleton** (trait + in-memory fakes) for the self-service DSR API; its production CF Worker / RS256-from-KMS / WebAuthn / Neon `dsr_tickets` wiring is deferred to WI-S11-008 (`crates/corelink-dsr/src/lib.rs:1-15`). The bytes-actually-deleted path that is LIVE today is the container `routes/dsr.rs` Wave-1 engine, not this crate's `InMemoryErasureWorker`.
- In the container, an unconfigured `StorageEnv` makes `build_d1_worker` return `None`; the erase route then falls back to an all-placeholder worker whose EMPTY legitimacy store rejects EVERY request — deliberately fail-CLOSED, never an allow-all on a route-mountable path (`crates/corelink-container/src/routes/dsr.rs:151-166`). A self-serve account-delete with no real worker fails CLOSED 503 rather than silently "succeeding".
- Attestation is fail-OPEN by design: a missing signature does NOT mean the erasure failed — the erasure is already complete and audited; the Ed25519 attestation is an extra evidence artifact (see the sibling `compliance/erasure-attestation` concept). Do not treat absence of an attestation as a deletion gap. But equally, do NOT treat a `verified_complete` response as proof a customer holds: the response is returned even when the attestation was fail-open-dropped, and even when signed there is no serving endpoint to fetch it — so the "proof" today is an unsigned, repudiable JSON label, not a downloadable receipt (see `compliance/erasure-attestation`).
- LATENT (not a live hole): the R2Cas adapter does not sweep the separate `corelink-chunk-*`/`corelink-manifest-*` multipart buckets, but the container has zero chunk-bucket write-sites today, so no tenant bytes land there. This MUST be fixed before the multipart path ships or chunked content would survive a "complete" erasure (`docs/security/2026-06-23-secreview-gdpr-residency.md:126-150`).
- The verify sweep zeroes the salt and sets `subject_id == tenant_id`: the per-DSR erasure salt is not retained post-erasure and `verify_erasure` re-fingerprints by tenant, so do not expect the salt to be reusable after the fact.
- **KNOWN TDK-rotation erase/verify blindspot (MED, red-team-confirmed).** Both the R2-CAS erase and its verify re-scan address objects by `derive_prefix(load_tdk(), tenant_id)` (erase `crates/corelink-container/src/routes/dsr/adapter_r2_cas.rs:172-177`, verify `crates/corelink-container/src/routes/dsr/adapter_r2_cas.rs:200-206`). If `R2_TDK_HEX` rotates between a tenant's WRITE and its erase, BOTH the delete and the verify count look under the NEW-TDK prefix — so the erase deletes 0 objects, the verify counts 0 remaining → `CANONICAL_EMPTY_TENANT_HASH` → `VerifiedComplete`, while the tenant's blobs survive untouched under the OLD-TDK prefix. Erase and verify share the identical mis-derivation, so the second check cannot catch the first (the file flags the same failure mode for the not-yet-swept multipart buckets at `crates/corelink-container/src/routes/dsr/adapter_r2_cas.rs:91-99`). TDK rotation must therefore re-prefix or re-derive historical tenant data before it can be considered safe for the erase path.
