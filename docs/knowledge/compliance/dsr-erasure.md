CoreLink is a multi-tenant content-addressable cache sold self-serve to SMBs, so it holds tenant PII and content and must honour data-subject erasure (GDPR Art.17 / LGPD Art.18). The pipeline has two halves: a pure-logic **self-service DSR endpoint** (`corelink-dsr`) that intakes a request, gates destructive arms behind step-up MFA, and issues a signed receipt; and the **live Wave-1 erasure engine** in the container (`routes/dsr.rs`) that actually deletes real bytes across the configured backends and is re-confirmed by a 24h verify sweep. A go-live security review found erasure "complete-by-construction for the live data planes (CAS + AC + D1 + Stripe)" with no launch-blocking finding (`docs/security/2026-06-23-secreview-gdpr-residency.md:12-18`). The whole pipeline is regulatory-grade fail-CLOSED: every state mutation is preceded by a durable audit row, and an erasure is never attested complete while subject bytes survive.

# Role

This control implements the data-subject right-to-erasure (and the sibling DSR rights: access, portability, rectification, restriction, objection). It is the compliance seam that converts a customer's "delete my account/data" demand — whether self-served or originated from a Clerk `user.deleted` webhook — into a verified, audited, attested deletion across CoreLink's storage backends, with constant-time cross-tenant confidentiality and a customer-held proof-of-submission receipt.

# How it works

- **Intake (self-service endpoint).** `InMemoryDsrEndpoint::submit` runs a serial pipeline per request: it first fires the `request_received` audit row BEFORE any state mutation, then an idempotency lookup, then the MFA gate, then receipt-issue + store-insert (`crates/corelink-dsr/src/endpoint.rs:299-418`).
- **MFA step-up on destructive arms only.** Erasure and Rectification require a non-empty step-up token; without one the orchestrator returns `MfaRequired` after a `mfa_step_up_required` audit, with no store insert; read/policy arms skip the gate (`crates/corelink-dsr/src/endpoint.rs:351-379`).
- **The MFA verifier contract.** `MfaStepUpVerifier::verify` is fail-CLOSED: `None` token → `Required`, empty bytes / bad binding → `Invalid`, expired → `Expired`; production wiring binds it to a 5-min WebAuthn step-up token scoped to `op_class = "dsr_destructive"` (`crates/corelink-dsr/src/mfa.rs:80-102`).
- **Idempotency by `(tenant_id, request_id)`.** A prior non-terminal ticket short-circuits to the original receipt + SLA deadline with no second audit/insert; a replay with a divergent `(data_subject_id, request_kind, jurisdiction)` tuple is a SEV-1 forensic anomaly surfaced as `DivergentPayload` (`crates/corelink-dsr/src/store.rs:133-158`).
- **Receipt + SLA.** On accept, a JWT (RS256) receipt is issued with a 90-day anti-replay expiry cap and an SLA deadline derived per jurisdiction (LGPD 15d / GDPR one-calendar-MONTH — a true `add_one_calendar_month_ms`, NOT a flat 30 days, so a Jan-31 submission is legally due Feb-28/29 not Mar-2 / CCPA 45d) by the `pub const fn sla_for` enforcer (`crates/corelink-dsr/src/receipt.rs:136-149`, `crates/corelink-dsr/src/event.rs:410-427`, `crates/corelink-dsr/src/lib.rs:116-119`).
- **Status poll is constant-time confidential.** `poll_status` returns the ticket status on a hit, but a miss OR a cross-tenant lookup both surface as `RequestRejected{IdentityVerificationFailed}` — never disclosing whether a `request_id` exists for another tenant (`crates/corelink-dsr/src/endpoint.rs:420-457`).
- **Live erasure intake (container).** `POST /_internal/dsr/erase` deserialises the `dsr.queued.v1` message (forwarded by the signup-worker queue consumer for the Clerk `user.deleted` path), maps it to a canonical `ErasureRequest` via `parse_request`, and drives the 12-backend orchestrator with `process_erasure` (`crates/corelink-container/src/routes/dsr.rs:465-481`, `crates/corelink-container/src/routes/dsr.rs:483`).
- **Self-serve account-delete uses the same DSR message + anchor (LIVE).** A self-serve account delete routes through `routes/customer.rs::handle_account_delete` (`crates/corelink-container/src/routes/customer.rs:955`), which builds a `dsr.queued.v1` message and `INSERT OR IGNORE`s a `dsr_requested` anchor row, then hands erasure to the `DsrErasureSink` trait — production wires `dsr::InProcessErasureSink` (via `routes/customer.rs::account_deletion_from_env`), which drives the **same** in-process, D1-backed erasure worker the `/_internal/dsr/erase` consumer runs (the container has no CF Queue producer, so the "enqueue" is a synchronous same-worker drive, not an async queue). `None` in dev/CI → the route fails CLOSED 503; in prod the sink is wired (deployed 2026-06-26).
- **The 12 backends, honestly reconciled.** `build_d1_worker` wires REAL transports for the 4 live planes — D1 erase-set, R2 CAS, R2 AC, and Stripe pseudonymisation — and reconciles the other 8 (Neon/KV/Loki/audit/legal-hold/evidence, not shipped in prod) to `NotApplicable` with a documented reason each, a truthful GDPR record not a silent skip (`crates/corelink-container/src/routes/dsr.rs:197-252`).
- **CAS tombstone / per-hash erase.** `POST /_internal/cas/:tenant/:hash/erase` deletes the blob from R2 and writes a durable `cas_tombstone` (migration 0067) so subsequent reads return 410 Gone, never 404 or 200 (`crates/corelink-container/src/routes/cas_erase.rs:1-8`, `crates/corelink-container/src/routes/cas_erase.rs:70`).

## The Wave-1 erasure transports (per-backend adapters)

The 4 live effective/pseudonymize adapters, the not-applicable reconciler, and the 3 D1-backed plumbing transports (audit / ledger / legitimacy) plus a shared D1-bridge helper module:

- **D1 control-plane erase (`BackendKind::D1`).** `D1EraseAdapter::erase` hard-deletes a tenant's subject PII in ordered groups — `tenant_id`-keyed child tables, then `namespace`-keyed registry tables (bound value is the tenant UUID, never the shared `'_public'`), then `signup_attempts` BEFORE `signup_orchestration`, then the root `tenant` row LAST so no orphan points at a deleted tenant; under `legal_hold` it preserves and returns `NotApplicable`. A CF-1 runtime drift `debug_assert!` fires BEFORE any delete if the classification is incomplete, so an unaccounted-for table can never run an erase that then attests `VerifiedComplete` (`crates/corelink-container/src/routes/dsr/adapter_d1.rs:402-441`).
- **D1 erase-set vs retain-set is now a COMPLETE, gated const partition (CF-1, 2026-06-28).** The erase-set is two compile-time constant table lists (`TENANT_ID_TABLES` / `NAMESPACE_TABLES`, injection-safe; only the tenant id is a bound `?1`) (`crates/corelink-container/src/routes/dsr/adapter_d1.rs:51-119`), and the retain-set (fiscal `stripe_*`, the erasure log/attestation, audit WORM, billing-reconciliation evidence) is guarded against accidental erase-set membership (`crates/corelink-container/src/routes/dsr/adapter_d1.rs:121-171`). CF-1 CLOSED the prior gap where tenant-keyed tables added after the 2026-06-11 ADR-S11-013 ratification silently escaped erasure: `team_member` (the worst case — a team's seat roster with raw Clerk `user_id` + `email_hash` that had survived a green attestation) plus 10 more (`cas_tombstone`, `pilot_tenants`, `runners_entitlement`, `monthly_request_counts`, `tier_selection_locks`, `stripe_checkout_sessions`, `gc_run`, `gc_candidates`, `region_migration_request`/`_progress`) were added to the DELETE set and to the verification sweep, and `RETAIN_SET` was PROMOTED out of `#[cfg(test)]` so it exists at runtime. Every live tenant-keyed table is now classified into EXACTLY ONE of {erase, namespace, retain, CAS-plane-owned, special}, enforced by a fail-closed completeness gate AND a migration-parsing test that makes a FUTURE tenant-keyed migration impossible to land without a conscious erase-vs-retain decision — so there is no more `VerifiedComplete` over-attestation (`crates/corelink-container/src/routes/dsr/adapter_d1.rs:197-305`, `crates/corelink-container/src/routes/dsr/adapter_d1.rs:553-585`).
- **Not-applicable reconciliation (un-shipped backends).** `NotApplicableAdapter` reports `BackendErasureOutcome::NotApplicable` for the 8 canonical backends (Neon/KV/Loki/audit/legal-hold/evidence) that hold no durable subject PII in shipped prod, carrying a `reason` so the per-backend audit row is a truthful GDPR record rather than a silent skip (`crates/corelink-container/src/routes/dsr/adapter_not_applicable.rs:49-72`).
- **R2 CAS erase is LIST-by-prefix, complete-by-construction.** `R2CasEraseAdapter::erase` derives the tenant prefix via `derive_prefix(tdk, tenant)` (no TDK ⇒ fail CLOSED), LISTs and DELETEs every object under `<region>/<tenant_prefix>/` across all five storage regions of the single `corelink-cas-prod` bucket, then defensively cleans the storage-layer D1 tables — independent of any D1 index (`crates/corelink-container/src/routes/dsr/adapter_r2_cas.rs:159-194`).
- **R2 AC erase sweeps the five per-region buckets (F-003 fix).** `R2AcEraseAdapter::erase` LIST-and-DELETEs every Action-Cache envelope under `<region>/<tenant_prefix>/` across the five `corelink-ac-<region>` buckets — mirroring the CAS sweep so it is complete-by-construction with no dependency on the never-populated `ac_meta` index (`crates/corelink-container/src/routes/dsr/adapter_r2_ac.rs:174-205`).
- **Stripe is pseudonymized, never deleted (fiscal retention).** `StripePseudonymizeAdapter::erase` reads the tenant's customer ids from the RETAINED `stripe_customers` table and overwrites email/name/phone/address + stamps `pii_redacted` via an idempotent `POST /v1/customers/:id`, returning `Pseudonymized` so the invoice/payment history survives for fiscal retention (`crates/corelink-container/src/routes/dsr/adapter_stripe.rs:145-193`).
- **Stripe verification is a LIVE re-fingerprint, not a sentinel.** `verification_hash` performs a live `GET /v1/customers/:id` per retained customer and asserts the email is a CoreLink redaction pseudonym; a non-redacted email yields a non-canonical mismatch hash (→ `VerifiedPartial`) and a missing key fails CLOSED, so the attestation is never falsely signed (`crates/corelink-container/src/routes/dsr/adapter_stripe.rs:195-230`).
- **Durable audit sink over `audit_outbox`.** `D1ErasureAuditSink::emit` appends each erasure CloudEvents envelope to `audit_outbox` as an `INSERT OR IGNORE` row keyed deterministically per `(request_id, event_type)` (so a pipeline retry is an idempotent no-op) and minimizes by OMITTING the raw `subject_id` entirely (`crates/corelink-container/src/routes/dsr/audit.rs:71-118`).
- **Durable idempotency ledger over `dsr_erasure_log`.** `D1ErasureIdempotencyLedger::upsert` selects the prior `(dsr_id, backend)` tombstone; an exact match on outcome + tenant + subject-hash + idempotency-key is a `Replayed`, any divergence is a SEV-1 `DivergentPayload`, and a fresh row is an `INSERT OR IGNORE` under the `UNIQUE (dsr_id, backend)` constraint (`crates/corelink-container/src/routes/dsr/ledger.rs:92-155`).
- **Durable legitimacy gate over `dsr_requested`.** `D1DsrLegitimacyStore::is_requested` selects a live (`requested`/`verified`) `dsr_requested` row bound on BOTH `dsr_id` AND `tenant_id`, so a forged body-asserted `tenant_id` cannot satisfy the gate; a D1 fault returns `Err` which the orchestrator maps to a `Rejected` (fail-CLOSED) (`crates/corelink-container/src/routes/dsr/legitimacy.rs:69-88`).
- **Shared async→sync D1 bridge + TDK loader.** `d1util` supplies the `block_in_place`/`block_on` bridge the synchronous erasure trait surfaces use to drive the async `D1HttpClient`, plus `load_tdk` which reads `R2_TDK_HEX` (64 hex → 32 bytes) and returns `None` on unset/malformed so the R2 adapters fail CLOSED (`crates/corelink-container/src/routes/dsr/d1util.rs:26-37`, `crates/corelink-container/src/routes/dsr/d1util.rs:62-71`).
- **Bloom-gated tombstone reads.** `BloomTombstoneStore::is_tombstoned` answers a definitely-absent fast-path only against a bloom seeded from the authoritative D1 set, falling through to D1 on maybe-present or a just-reloaded epoch (`crates/corelink-container/src/routes/cas_erase.rs:830-850`).
- **24h verify sweep + REAL signed + served attestation (Artifact 1, brutal-review H1 CLOSED).** `POST /_internal/dsr/verify` re-fingerprints every backend; on a fully `VerifiedComplete` decision it invokes `attestation::sign_and_persist` (`crates/corelink-container/src/routes/dsr.rs:560-572`). STATUS: that function now produces a REAL Ed25519 signature over the JCS-canonical payload and persists it ALL-OR-NOTHING fail-CLOSED (region-gated → R2 PUT FIRST → `erasure_public_keys` upsert → signed D1 index row carrying BOTH `signature_ed25519` AND `canonical_payload_jcs`); it is served by `GET /v1/public/attestation/{request_id}` + `GET /v1/public/keys/erasure/{region}.pub` (see the next bullet and the sibling `compliance/erasure-attestation`).
- **The verify-sweep attestation step signs + persists fail-CLOSED on bound evidence.** `sign_and_persist` runs only on the `VerifiedComplete` arm and re-derives `verified_evidence_segments` from the real per-backend completions before doing anything; on incomplete/unverified evidence it logs and returns without writing a row. On full, bound evidence it signs the JCS payload and persists STRICTLY ordered (R2 PUT FIRST → pubkey upsert → signed index row), aborting WITHOUT the index row if any step fails — so there is never a D1 row missing the signature/canonical, and never an index row before the R2 object exists (no dangling `r2_key`). The earlier UNSIGNED-`evidence_hash` theater row is gone; this is a real, offline-verifiable certificate (`crates/corelink-container/src/routes/dsr/attestation.rs:241-290`).

# Invariants

- **Audit-before-mutation, fail-CLOSED.** Every decision arm fires its canonical audit row BEFORE the state-mutating step; an audit failure aborts the request and propagates `DsrError::Audit` with no mutation past that point (`crates/corelink-dsr/src/endpoint.rs:312-318`).
- **MFA mandatory for Erasure + Rectification, never for read/policy arms.** The gate is structural in the orchestrator pipeline (`crates/corelink-dsr/src/endpoint.rs:354-379`); the verifier impl rejects `None`/empty tokens (`crates/corelink-dsr/src/mfa.rs:146-154`); token expiry is in the trait contract (`crates/corelink-dsr/src/mfa.rs:80-102`).
- **Tenant isolation is structural.** The ticket store is keyed `(tenant_id, request_id)` leftmost, so cross-tenant reads are impossible by construction (`crates/corelink-dsr/src/store.rs:45`).
- **Erasure intake is legitimacy-gated (anti mass-erase).** Every erase binds to a D1-authenticated `dsr_requested` row; a forged body-asserted `tenant_id` with the shared internal key lands as `Rejected` → HTTP 422, no fan-out, no bytes deleted; a D1 fault also fails CLOSED (`crates/corelink-container/src/routes/dsr.rs:451-452`, `crates/corelink-container/src/routes/dsr.rs:188-192`).
- **The destructive route is mounted only with a ≥32-char dedicated key.** `build_state_from_env` prefers `CORELINK_ERASE_AUTH_KEY`, falls back to the shared internal key, and refuses to mount below the 32-char floor (`crates/corelink-container/src/routes/dsr.rs:361-377`); the check itself is constant-time, length-folded (`crates/corelink-container/src/routes/dsr.rs:134-151`).
- **The evidence gate fires only when no data survives.** `sign_and_persist` runs only on the `VerifiedComplete` arm, and even then `verified_evidence_segments` re-checks every backend's verification hash against the canonical-empty sentinel before logging — surviving CAS/AC bytes yield a non-canonical hash → no `VerifiedComplete` (the gate also fail-CLOSES on incomplete evidence) (`crates/corelink-container/src/routes/dsr.rs:560-572`, `crates/corelink-container/src/routes/dsr/attestation.rs:241-290`, `docs/security/2026-06-23-secreview-gdpr-residency.md:75-85`). STATUS: on a bound `VerifiedComplete` the gate now signs (Ed25519) and persists the certificate fail-CLOSED — a signed proof is LIVE (Artifact 1, brutal-review H1 CLOSED), not deferred.
- **A tombstoned hash never resurrects.** A read of a tombstoned digest returns 410 on the native CAS route — the read-side enforcer short-circuits `Ok(true) => return (StatusCode::GONE, "erased")` BEFORE the R2 GET (`crates/corelink-container/src/routes/cas.rs:786-798`, tombstone-WRITE side `crates/corelink-container/src/routes/cas_erase.rs:1-8`), a re-PUT is refused, and a gate transport fault fails CLOSED 503; the bloom is re-seeded from D1 on every reload to close the cross-writer false-negative window (`crates/corelink-container/src/routes/cas_erase.rs:797-825`).
- **The receipt caps customer-side replay at 90 days.** `DsrReceipt::is_expired` enforces the `submitted + 90d` cap independent of DB state (`crates/corelink-dsr/src/receipt.rs:153-154`).

# Gotchas

- The `corelink-dsr` crate is the **pure-logic skeleton** (trait + in-memory fakes) for the self-service DSR API; its production CF Worker / RS256-from-KMS / WebAuthn / Neon `dsr_tickets` wiring is deferred to WI-S11-008 (`crates/corelink-dsr/src/lib.rs:1-15`). The bytes-actually-deleted path that is LIVE today is the container `routes/dsr.rs` Wave-1 engine, not this crate's `InMemoryErasureWorker`.
- In the container, an unconfigured `StorageEnv` makes `build_d1_worker` return `None`; the erase route then falls back to an all-placeholder worker whose EMPTY legitimacy store rejects EVERY request — deliberately fail-CLOSED, never an allow-all on a route-mountable path (`crates/corelink-container/src/routes/dsr.rs:159-174`). A self-serve account-delete with no real worker fails CLOSED 503 rather than silently "succeeding".
- The served erasure attestation is now LIVE. On a bound `VerifiedComplete` the verify sweep's `attestation::sign_and_persist` signs the JCS payload (Ed25519) and persists it ALL-OR-NOTHING fail-CLOSED (region-gated → R2 PUT → pubkey upsert → signed D1 index row), served by `GET /v1/public/attestation/{request_id}` + `GET /v1/public/keys/erasure/{region}.pub` (`crates/corelink-container/src/routes/dsr/attestation.rs:241-290`; sibling `compliance/erasure-attestation`). The signing gate still fail-CLOSES on incomplete/unverified evidence (no row), and a MISSING attestation does NOT mean the erasure failed — the erasure is already complete + audited + ledgered, attestation is an additional evidence artifact on top.
- LATENT (not a live hole): the R2Cas adapter does not sweep the separate `corelink-chunk-*`/`corelink-manifest-*` multipart buckets, but the container has zero chunk-bucket write-sites today, so no tenant bytes land there. This MUST be fixed before the multipart path ships or chunked content would survive a "complete" erasure (`docs/security/2026-06-23-secreview-gdpr-residency.md:126-150`).
- The verify sweep zeroes the salt and sets `subject_id == tenant_id`: the per-DSR erasure salt is not retained post-erasure and `verify_erasure` re-fingerprints by tenant, so do not expect the salt to be reusable after the fact.
