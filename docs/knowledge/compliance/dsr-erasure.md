CoreLink is a multi-tenant content-addressable cache sold self-serve to SMBs, so it holds tenant PII and content and must honour data-subject erasure (GDPR Art.17 / LGPD Art.18). The pipeline has two halves: a pure-logic **self-service DSR endpoint** (`corelink-dsr`) that intakes a request, gates destructive arms behind step-up MFA, and issues a signed receipt; and the **live Wave-1 erasure engine** in the container (`routes/dsr.rs`) that actually deletes real bytes across the configured backends and is re-confirmed by a 24h verify sweep. A go-live security review found erasure "complete-by-construction for the live data planes (CAS + AC + D1 + Stripe)" with no launch-blocking finding (`docs/security/2026-06-23-secreview-gdpr-residency.md:12-18`). The whole pipeline is regulatory-grade fail-CLOSED: every state mutation is preceded by a durable audit row, and an erasure is never attested complete while subject bytes survive.

# Role

This control implements the data-subject right-to-erasure (and the sibling DSR rights: access, portability, rectification, restriction, objection). It is the compliance seam that converts a customer's "delete my account/data" demand — whether self-served or originated from a Clerk `user.deleted` webhook — into a verified, audited, attested deletion across CoreLink's storage backends, with constant-time cross-tenant confidentiality and a customer-held proof-of-submission receipt.

# How it works

- **Intake (self-service endpoint).** `InMemoryDsrEndpoint::submit` runs a serial pipeline per request: it first fires the `request_received` audit row BEFORE any state mutation, then an idempotency lookup, then the MFA gate, then receipt-issue + store-insert (`crates/corelink-dsr/src/endpoint.rs:299-418`).
- **MFA step-up on destructive arms only.** Erasure and Rectification require a non-empty step-up token; without one the orchestrator returns `MfaRequired` after a `mfa_step_up_required` audit, with no store insert; read/policy arms skip the gate (`crates/corelink-dsr/src/endpoint.rs:351-379`).
- **The MFA verifier contract.** `MfaStepUpVerifier::verify` is fail-CLOSED: `None` token → `Required`, empty bytes / bad binding → `Invalid`, expired → `Expired`; production wiring binds it to a 5-min WebAuthn step-up token scoped to `op_class = "dsr_destructive"` (`crates/corelink-dsr/src/mfa.rs:80-102`).
- **Idempotency by `(tenant_id, request_id)`.** A prior non-terminal ticket short-circuits to the original receipt + SLA deadline with no second audit/insert; a replay with a divergent `(data_subject_id, request_kind, jurisdiction)` tuple is a SEV-1 forensic anomaly surfaced as `DivergentPayload` (`crates/corelink-dsr/src/store.rs:133-158`).
- **Receipt + SLA.** On accept, a JWT (RS256) receipt is issued with a 90-day anti-replay expiry cap and an SLA deadline derived per jurisdiction (LGPD 15d / GDPR one-calendar-MONTH — a true `add_one_calendar_month_ms`, NOT a flat 30 days, so a Jan-31 submission is legally due Feb-28/29 not Mar-2 / CCPA 45d) by the `pub const fn sla_for` enforcer (`crates/corelink-dsr/src/receipt.rs:136-149`, `crates/corelink-dsr/src/event.rs:410-427`, `crates/corelink-dsr/src/lib.rs:116-119`).
- **Status poll is constant-time confidential.** `poll_status` returns the ticket status on a hit, but a miss OR a cross-tenant lookup both surface as `RequestRejected{IdentityVerificationFailed}` — never disclosing whether a `request_id` exists for another tenant (`crates/corelink-dsr/src/endpoint.rs:420-457`).
- **Live erasure intake (container).** `POST /_internal/dsr/erase` deserialises the `dsr.queued.v1` message (forwarded by the signup-worker queue consumer for the Clerk `user.deleted` path), maps it to a canonical `ErasureRequest` via `parse_request`, and drives the 12-backend orchestrator with `process_erasure` (`crates/corelink-container/src/routes/dsr.rs:664-677`, `crates/corelink-container/src/routes/dsr.rs:678`).
- **The same surface now serves the READ-side rights (access / portability / rectification), single-sourced off the erase-set.** `dsr::router` mounts `POST /_internal/dsr/{access,portability,rectification}` on the SAME internal-auth gate as `erase`/`verify` (`crates/corelink-container/src/routes/dsr.rs:416-424`). The gather engine (`access::gather_subject_data`) does NOT keep a parallel table list: `build_gather_plan` walks the EXACT same tenant-keyed table registry the D1 erase adapter deletes — `adapter_d1::TENANT_ID_TABLES` + `NAMESPACE_TABLES` + the RETAIN-disclosable subset of `RETAIN_SET` (those consts were promoted to `pub(super)` precisely so access can single-source them, so a future tenant-keyed table is covered by erase AND access with no list to drift) (`crates/corelink-container/src/routes/dsr/access.rs:202-218`, `crates/corelink-container/src/routes/dsr/access.rs:263-277`). It is **fail-CLOSED**: the FIRST per-table query error aborts with `Err` (never a partial "complete" export). `run_access` (Art.15) returns the redacted `SubjectExport`; `run_portability` (Art.20) returns the same machine-readable bundle PLUS an `ExportReceipt` whose content digest is best-effort Ed25519-signed by reusing the erasure-attestation signer (`attestation::sign_export_digest`; fail-OPEN to an unsigned inline bundle when the region/seed cannot be trustworthily resolved — see sibling `compliance/erasure-attestation`); `run_rectification` (Art.16) corrects an editable subject field — the only allowlisted field is `tenant.email_hash`, whose new value is recomputed through the ONE shared `email_hash::hash_email` helper (CTRL-PRIV-001), NOT an inline SHA-256, so the rectification, the `customer_d1` team-invite write, and the signup-worker accept-match all bind a byte-identical pseudonym: HMAC-SHA256 under the server-held `EMAIL_HASH_SALT` when set, else the byte-identical legacy unsalted SHA-256 (zero pre-salt regression) (`crates/corelink-container/src/routes/dsr/access.rs:358`, `crates/corelink-container/src/routes/dsr/access.rs:396`, `crates/corelink-container/src/routes/dsr/access.rs:561`, `crates/corelink-container/src/email_hash.rs:45-58`). Every gathered row is passed through `redact_row`, which replaces any sensitive-named column's non-null value with `"<redacted>"` (presence disclosed, secret withheld; a SQL NULL stays null) so an access/portability export can never leak credential material (`crates/corelink-container/src/routes/dsr/access.rs:143-150`).
- **Customer-facing self-service privacy portal (`/v1/privacy/dsr/*`).** `dsr::portal::router` exposes the Clerk-SESSION dashboard surface — `POST /v1/privacy/dsr/{access,portability,rectification,erasure,restriction,objection}` plus `GET /v1/privacy/dsr` (list), `GET /v1/privacy/dsr/{request_id}/status`, and `POST /v1/privacy/dsr/{request_id}/verify-mfa` — mounted into the container router and reached via the Worker's `customer_v1` forward (a browser Clerk session, not a PAT). The destructive arms (erasure/rectification) are step-up-gated on the Worker-trusted `x-corelink-mfa-verified` freshness header, which the Worker is the SOLE setter of (a client cannot smuggle a forged value) (`crates/corelink-container/src/routes/dsr/portal.rs:717-732`).
- **Self-serve account-delete uses the same DSR message + anchor (LIVE).** A self-serve account delete routes through `routes/customer.rs::handle_account_delete` (`crates/corelink-container/src/routes/customer.rs:986`), which builds a `dsr.queued.v1` message and `INSERT OR IGNORE`s a `dsr_requested` anchor row, then hands erasure to the `DsrErasureSink` trait — production wires `dsr::InProcessErasureSink` (via `routes/customer.rs::account_deletion_from_env`), which drives the **same** in-process, D1-backed erasure worker the `/_internal/dsr/erase` consumer runs (the container has no CF Queue producer, so the "enqueue" is a synchronous same-worker drive, not an async queue). `None` in dev/CI → the route fails CLOSED 503; in prod the sink is wired (deployed 2026-06-26).
- **The 12 backends, honestly reconciled.** `build_d1_worker` wires REAL transports for the 4 live planes — D1 erase-set, R2 CAS, R2 AC, and Stripe pseudonymisation — and reconciles the other 8 (Neon/KV/Loki/audit/legal-hold/evidence, not shipped in prod) to `NotApplicable` with a documented reason each, a truthful GDPR record not a silent skip (`crates/corelink-container/src/routes/dsr.rs:205-260`).
- **CAS tombstone / per-hash erase.** `POST /_internal/cas/:tenant/:hash/erase` deletes the blob from R2 and writes a durable `cas_tombstone` (migration 0067) so subsequent reads return 410 Gone, never 404 or 200 (`crates/corelink-container/src/routes/cas_erase.rs:1-8`, `crates/corelink-container/src/routes/cas_erase.rs:70`).
- **Per-USER legitimacy-anchor register (GDPR1).** The per-hash erase authorises only against a `dsr_requested` row for `(dsr_id, tenant)`, but the two whole-account writers of that anchor (Clerk `user.deleted`; self-serve `/v1/customer/account/delete`) don't cover a per-user erasure inside a shared multi-user tenant (e.g. a git-CAS tenant hosting many forge users, none a Clerk user of the tenant). `POST /_internal/dsr/anchor` closes that: the erasure-REQUEST authority registers the anchor — the handler derives the deterministic `dsr_id` via the SAME `deterministic_dsr_id` the Clerk/self-serve paths use and `INSERT OR IGNORE`s the `dsr_requested` row, returning the `dsr_id` for the downstream per-digest erases (`crates/corelink-container/src/routes/dsr_anchor.rs:53`, `crates/corelink-container/src/routes/dsr_anchor.rs:136-176`). Anti-forge: it is gated by a DEDICATED `CORELINK_DSR_ANCHOR_AUTH_KEY` (shared-key fallback) that MUST be held by a DIFFERENT authority than the eraser — the anchor writer and the eraser being distinct parties is the whole point of the legitimacy gate (mirrors the Clerk model). Fail-CLOSED: 401 unauth (before body parse), 400 non-UUID-tenant / empty-subject, 500 on any D1 fault; idempotent; unmounted unless the key + D1 are present.

## The Wave-1 erasure transports (per-backend adapters)

The 4 live effective/pseudonymize adapters, the not-applicable reconciler, and the 3 D1-backed plumbing transports (audit / ledger / legitimacy) plus a shared D1-bridge helper module:

- **D1 control-plane erase (`BackendKind::D1`).** `D1EraseAdapter::erase` hard-deletes a tenant's subject PII in ordered groups — `tenant_id`-keyed child tables, then `namespace`-keyed registry tables (bound value is the tenant UUID, never the shared `'_public'`), then `signup_attempts` BEFORE `signup_orchestration`, then the root `tenant` row LAST so no orphan points at a deleted tenant; under `legal_hold` it preserves and returns `NotApplicable`. A CF-1 runtime drift `debug_assert!` fires BEFORE any delete if the classification is incomplete, so an unaccounted-for table can never run an erase that then attests `VerifiedComplete` (`crates/corelink-container/src/routes/dsr/adapter_d1.rs:454-499`).
- **D1 erase-set vs retain-set is now a COMPLETE, gated const partition (CF-1, 2026-06-28).** The erase-set is two compile-time constant table lists (`TENANT_ID_TABLES` / `NAMESPACE_TABLES`, injection-safe; only the tenant id is a bound `?1`) (`crates/corelink-container/src/routes/dsr/adapter_d1.rs:63-149`) — and the **BYOK Wave-2** tenant-keyed tables (`tenant_byok_config`, `tenant_byok_secret`) are now classified into this `tenant_id`-keyed erase-set, so a GDPR Art.17 deletion erases the tenant's BYOK configuration AND its wrapped key envelope (material — the wrapped TCS is key material, so leaving it behind would survive a "complete" erasure as recoverable secret state), and the retain-set (fiscal `stripe_*`, the erasure log/attestation, audit WORM, billing-reconciliation evidence) is guarded against accidental erase-set membership (`crates/corelink-container/src/routes/dsr/adapter_d1.rs:159-215`). CF-1 CLOSED the prior gap where tenant-keyed tables added after the 2026-06-11 ADR-S11-013 ratification silently escaped erasure: `team_member` (the worst case — a team's seat roster with raw Clerk `user_id` + `email_hash` that had survived a green attestation) plus 10 more (`cas_tombstone`, `pilot_tenants`, `runners_entitlement`, `monthly_request_counts`, `tier_selection_locks`, `stripe_checkout_sessions`, `gc_run`, `gc_candidates`, `region_migration_request`/`_progress`) were added to the DELETE set and to the verification sweep, and `RETAIN_SET` was PROMOTED out of `#[cfg(test)]` so it exists at runtime. The WP-E `tenant_org_map` (the Clerk org→isolated-tenant identity map, migration 0083) is likewise classified into the `tenant_id`-keyed erase-set, so a GDPR Art.17 deletion erases the org→tenant mapping along with the tenant — operational identity state with no retention basis (`crates/corelink-container/src/routes/dsr/adapter_d1.rs:132`). The **cf-multitenant runner-CI identity tables** — `tenant_gh_installation_map` (GitHub App installation→tenant, migration 0084) and `runner_repo_allowlist` (per-tenant repo allowlist, migration 0085) — are classified into the SAME `tenant_id`-keyed erase-set and the verification sweep, so a tenant's installation mapping and repo allowlist are erased along with it (both are operational identity/authorization state with no retention basis) (`crates/corelink-container/src/routes/dsr/adapter_d1.rs:138`, `crates/corelink-container/src/routes/dsr/adapter_d1.rs:142`, `crates/corelink-container/src/routes/dsr/adapter_d1.rs:289-291`). The **runner self-serve billing mirror** `runner_billing` (migration 0087 — the runner subscription↔tenant billing mirror, `tenant_id`-indexed) is likewise now in the `tenant_id`-keyed ERASE set: it is OPERATIONAL subscription-state (plan/status), NOT the retained fiscal record (the Stripe customer/invoice/subscription rows remain the 5y fiscal artifact), so it is the runner analog of `tenant_billing` and erased on an Art.17 deletion per ADR-S11-013 (`crates/corelink-container/src/routes/dsr/adapter_d1.rs:113-119`, `crates/corelink-container/src/routes/dsr/adapter_d1.rs:283`). The **customer Workspaces** table `workspaces` (migration 0088 — per-tenant named snapshots of the tenant's OWN cached state, tenant-leftmost composite PK `(tenant_id, workspace_id)`) is classified into the `tenant_id`-keyed ERASE set AND the completeness sweep, so a GDPR Art.17 deletion removes a tenant's workspace snapshots along with it (the tenant's own content, no retention basis) (`crates/corelink-container/src/routes/dsr/adapter_d1.rs:148`, `crates/corelink-container/src/routes/dsr/adapter_d1.rs:291`). The **dashboard ROI usage rollup** `usage_daily` (migration 0089 — per-tenant, per-day reads/writes/hits/misses DISPLAY telemetry, composite PK `(tenant_id, day)`) is likewise in the `tenant_id`-keyed ERASE set AND the completeness sweep: it is the tenant's own operational usage state with no retention basis, so an Art.17 deletion erases it too (`crates/corelink-container/src/routes/dsr/adapter_d1.rs:152`, `crates/corelink-container/src/routes/dsr/adapter_d1.rs:296`). Every live tenant-keyed table is now classified into EXACTLY ONE of {erase, namespace, retain, CAS-plane-owned, special}, enforced by a fail-closed completeness gate AND a migration-parsing test that makes a FUTURE tenant-keyed migration impossible to land without a conscious erase-vs-retain decision — so there is no more `VerifiedComplete` over-attestation (`crates/corelink-container/src/routes/dsr/adapter_d1.rs:227-346`, `crates/corelink-container/src/routes/dsr/adapter_d1.rs:589-628`).
- **Not-applicable reconciliation (un-shipped backends).** `NotApplicableAdapter` reports `BackendErasureOutcome::NotApplicable` for the 8 canonical backends (Neon/KV/Loki/audit/legal-hold/evidence) that hold no durable subject PII in shipped prod, carrying a `reason` so the per-backend audit row is a truthful GDPR record rather than a silent skip (`crates/corelink-container/src/routes/dsr/adapter_not_applicable.rs:49-72`).
- **R2 CAS erase is LIST-by-prefix, complete-by-construction.** `R2CasEraseAdapter::erase` derives the tenant prefix via `derive_prefix(tdk, tenant)` (no TDK ⇒ fail CLOSED), LISTs and DELETEs every object under `<region>/<tenant_prefix>/` across the storage-region set of the single `corelink-cas-prod` bucket, then defensively cleans the storage-layer D1 tables — independent of any D1 index. The region set is now the SINGLE SOURCE OF TRUTH `crate::storage::region_map::CAS_REGIONS` (re-exported here instead of a local const, and superset-gated so an Art.17 erase can never skip a colo) (`crates/corelink-container/src/routes/dsr/adapter_r2_cas.rs:168-203`).
- **R2 AC erase sweeps the per-region buckets (F-003 fix).** `R2AcEraseAdapter::erase` LIST-and-DELETEs every Action-Cache envelope under `<region>/<tenant_prefix>/` across the `corelink-ac-<region>` buckets — mirroring the CAS sweep so it is complete-by-construction with no dependency on the never-populated `ac_meta` index. AC no longer keeps its own region list either: it re-exports the SAME `region_map::CAS_REGIONS` as `AC_REGIONS`, so CAS and AC provably sweep an identical colo set (`crates/corelink-container/src/routes/dsr/adapter_r2_ac.rs:178-209`).
- **Stripe is pseudonymized, never deleted (fiscal retention).** `StripePseudonymizeAdapter::erase` reads the tenant's customer ids from the RETAINED `stripe_customers` table and overwrites email/name/phone/address + stamps `pii_redacted` via an idempotent `POST /v1/customers/:id`, returning `Pseudonymized` so the invoice/payment history survives for fiscal retention (`crates/corelink-container/src/routes/dsr/adapter_stripe.rs:145-193`).
- **Stripe verification is a LIVE re-fingerprint, not a sentinel.** `verification_hash` performs a live `GET /v1/customers/:id` per retained customer and asserts the email is a CoreLink redaction pseudonym; a non-redacted email yields a non-canonical mismatch hash (→ `VerifiedPartial`) and a missing key fails CLOSED, so the attestation is never falsely signed (`crates/corelink-container/src/routes/dsr/adapter_stripe.rs:195-230`).
- **Durable audit sink over `audit_outbox`.** `D1ErasureAuditSink::emit` appends each erasure CloudEvents envelope to `audit_outbox` as an `INSERT OR IGNORE` row keyed deterministically per `(request_id, event_type)` (so a pipeline retry is an idempotent no-op) and minimizes by OMITTING the raw `subject_id` entirely (`crates/corelink-container/src/routes/dsr/audit.rs:71-118`).
- **Durable idempotency ledger over `dsr_erasure_log`.** `D1ErasureIdempotencyLedger::upsert` selects the prior `(dsr_id, backend)` tombstone; an exact match on outcome + tenant + subject-hash + idempotency-key is a `Replayed`, any divergence is a SEV-1 `DivergentPayload`, and a fresh row is an `INSERT OR IGNORE` under the `UNIQUE (dsr_id, backend)` constraint (`crates/corelink-container/src/routes/dsr/ledger.rs:92-155`).
- **Durable legitimacy gate over `dsr_requested`.** `D1DsrLegitimacyStore::is_requested` selects a live (`requested`/`verified`) `dsr_requested` row bound on BOTH `dsr_id` AND `tenant_id`, so a forged body-asserted `tenant_id` cannot satisfy the gate; a D1 fault returns `Err` which the orchestrator maps to a `Rejected` (fail-CLOSED) (`crates/corelink-container/src/routes/dsr/legitimacy.rs:69-84`).
- **Shared async→sync D1 bridge + TDK loader.** `d1util` supplies the `block_in_place`/`block_on` bridge the synchronous erasure trait surfaces use to drive the async `D1HttpClient`, plus `load_tdk` which reads `R2_TDK_HEX` (64 hex → 32 bytes) and returns `None` on unset/malformed so the R2 adapters fail CLOSED (`crates/corelink-container/src/routes/dsr/d1util.rs:26-37`, `crates/corelink-container/src/routes/dsr/d1util.rs:61-70`).
- **Bloom-gated tombstone reads.** `BloomTombstoneStore::is_tombstoned` answers a definitely-absent fast-path only against a bloom seeded from the authoritative D1 set, falling through to D1 on maybe-present or a just-reloaded epoch (`crates/corelink-container/src/routes/cas_erase.rs:831-851`).
- **24h verify sweep + signed attestation (LIVE, Artifact 1).** `POST /_internal/dsr/verify` re-fingerprints every backend; on a fully `VerifiedComplete` decision it invokes `attestation::sign_and_persist` with the decision's REAL per-backend completions (`crates/corelink-container/src/routes/dsr.rs:733-745`). That signer produces a REAL Ed25519 certificate over the JCS-canonical payload and persists it (see the next bullet); the signed + served erasure attestation is now LIVE — served by `GET /v1/public/attestation/{request_id}` + `GET /v1/public/keys/erasure/{region}.pub` (`crates/corelink-container/src/routes/dsr/attestation.rs:249-298`).
- **The verify-sweep attestation step signs + persists ALL-OR-NOTHING, fail-CLOSED (Artifact 1, LIVE).** `sign_and_persist` runs only on the `VerifiedComplete` arm and is region-gated (it withholds the proof unless the operator EXPLICITLY asserted single-region, so an EU tenant's erasure is never signed with the wrong key), then re-derives `verified_evidence_segments` from the real per-backend completions (refusing unless every canonical backend is provably verified-empty), signs the JCS-canonical payload with the per-region Ed25519 key, and persists in STRICT order — R2 PUT of the signed bundle FIRST, then the `erasure_public_keys` upsert, then the `erasure_attestations` index row carrying BOTH `signature_ed25519` AND `canonical_payload_jcs`. ANY step failing aborts WITHOUT a row (never a dangling `r2_key`, never an unsigned row masquerading as a certificate) (`crates/corelink-container/src/routes/dsr/attestation.rs:249-298`, `crates/corelink-container/src/routes/dsr/attestation.rs:307-460`).

# Invariants

- **Audit-before-mutation, fail-CLOSED.** Every decision arm fires its canonical audit row BEFORE the state-mutating step; an audit failure aborts the request and propagates `DsrError::Audit` with no mutation past that point (`crates/corelink-dsr/src/endpoint.rs:312-318`).
- **MFA mandatory for Erasure + Rectification, never for read/policy arms.** The gate is structural in the orchestrator pipeline (`crates/corelink-dsr/src/endpoint.rs:354-379`); the verifier impl rejects `None`/empty tokens (`crates/corelink-dsr/src/mfa.rs:146-154`); token expiry is in the trait contract (`crates/corelink-dsr/src/mfa.rs:80-102`).
- **Tenant isolation is structural.** The ticket store is keyed `(tenant_id, request_id)` leftmost, so cross-tenant reads are impossible by construction (`crates/corelink-dsr/src/store.rs:45`).
- **Erasure intake is legitimacy-gated (anti mass-erase).** Every erase binds to a D1-authenticated `dsr_requested` row; a forged body-asserted `tenant_id` with the shared internal key lands as `Rejected` → HTTP 422, no fan-out, no bytes deleted; a D1 fault also fails CLOSED (`crates/corelink-container/src/routes/dsr.rs:679-686`, `crates/corelink-container/src/routes/dsr.rs:194-198`).
- **The destructive route is mounted only with a ≥32-char dedicated key.** `build_state_from_env` prefers `CORELINK_ERASE_AUTH_KEY`, falls back to the shared internal key, and refuses to mount below the 32-char floor (`crates/corelink-container/src/routes/dsr.rs:376-385`); the check itself is constant-time, length-folded (`crates/corelink-container/src/routes/dsr.rs:137-153`).
- **The signature is only ever emitted when no subject data survives.** `sign_and_persist` runs only on the `VerifiedComplete` arm, and even then `verified_evidence_segments` re-checks every backend's verification hash against the canonical-empty sentinel before signing — surviving CAS/AC bytes yield a non-canonical hash → no `VerifiedComplete` and no certificate (the gate also fail-CLOSES on incomplete evidence) (`crates/corelink-container/src/routes/dsr.rs:733-745`, `crates/corelink-container/src/routes/dsr/attestation.rs:187-247`, `docs/security/2026-06-23-secreview-gdpr-residency.md:75-85`). The proof binds the ACTUAL per-backend evidence hashes, so a signed attestation provably means every backend re-verified empty.
- **A tombstoned hash never resurrects.** A read of a tombstoned digest returns 410 on the native CAS route — the read-side enforcer short-circuits `Ok(true) => return (StatusCode::GONE, "erased")` BEFORE the R2 GET (`crates/corelink-container/src/routes/cas.rs:801-813`, tombstone-WRITE side `crates/corelink-container/src/routes/cas_erase.rs:1-8`), a re-PUT is refused, and a gate transport fault fails CLOSED 503; the bloom is re-seeded from D1 on every reload to close the cross-writer false-negative window (`crates/corelink-container/src/routes/cas_erase.rs:798-826`).
- **The receipt caps customer-side replay at 90 days.** `DsrReceipt::is_expired` enforces the `submitted + 90d` cap independent of DB state (`crates/corelink-dsr/src/receipt.rs:153-154`).

# Gotchas

- The `corelink-dsr` crate is the **pure-logic skeleton** (trait + in-memory fakes) for the self-service DSR API; its production CF Worker / RS256-from-KMS / WebAuthn / Neon `dsr_tickets` wiring is deferred to WI-S11-008 (`crates/corelink-dsr/src/lib.rs:1-15`). The bytes-actually-deleted path that is LIVE today is the container `routes/dsr.rs` Wave-1 engine, not this crate's `InMemoryErasureWorker`.
- In the container, an unconfigured `StorageEnv` makes `build_d1_worker` return `None`; the erase route then falls back to an all-placeholder worker whose EMPTY legitimacy store rejects EVERY request — deliberately fail-CLOSED, never an allow-all on a route-mountable path (`crates/corelink-container/src/routes/dsr.rs:168-175`). A self-serve account-delete with no real worker fails CLOSED 503 rather than silently "succeeding".
- The signed + served Ed25519 erasure attestation is LIVE (Artifact 1). On `VerifiedComplete` the verify sweep signs a REAL certificate and persists it all-or-nothing (`attestation::sign_and_persist`) for the public verifier to serve (`crates/corelink-container/src/routes/dsr/attestation.rs:249-298`; see the sibling `compliance/erasure-attestation` concept). It remains fail-CLOSED: a missing attestation does NOT mean the erasure failed — the erasure is already complete + audited + ledgered, and the signer withholds the proof (no row) whenever the region is not trustworthily resolvable, the R2 audit client is absent, the seed secret is unset, or the per-backend evidence is incomplete — never a forgeable unsigned row.
- LATENT (not a live hole): the R2Cas adapter does not sweep the separate `corelink-chunk-*`/`corelink-manifest-*` multipart buckets, but the container has zero chunk-bucket write-sites today, so no tenant bytes land there. This MUST be fixed before the multipart path ships or chunked content would survive a "complete" erasure (`docs/security/2026-06-23-secreview-gdpr-residency.md:126-150`).
- The verify sweep zeroes the salt and sets `subject_id == tenant_id`: the per-DSR erasure salt is not retained post-erasure and `verify_erasure` re-fingerprints by tenant, so do not expect the salt to be reusable after the fact.
