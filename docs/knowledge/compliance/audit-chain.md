CoreLink needs an audit log whose retroactive alteration an EXTERNAL reader can DETECT at verify time. It does this in two layers: a per-tenant BLAKE3 hash chain that makes any post-hoc edit/delete of a sealed row surface as a chain break when the daily verifier walks it (the RFC-6962-style transparency discipline applied to CloudEvents audit events), and an OPTIONAL public witness that submits a signed chain/attestation digest to the sigstore/Rekor transparency log. The live chain producer IS wired: the hourly `POST /_internal/audit/drain` drain (`crates/corelink-container/src/routes/audit_drain.rs`, mounted in `crates/corelink-container/src/main.rs:586-598`) seals pending `audit_outbox` rows into the chain in D1.

**Honest scope of the guarantee (do NOT oversell it).** The chain is tamper-EVIDENCE at verify time, NOT tamper-PROOF against an insider with D1 write. Three things bound it: (1) the per-LINK hash is **UN-KEYED** BLAKE3 (`Hasher::new()`, no `keyed_hash`/HMAC — `crates/corelink-audit-chain/src/chain.rs:156-162`, `:183-193`), so anyone who holds the rows can recompute a self-consistent chain BODY — though the chain HEAD checkpoint is now Ed25519-SIGNED (CF-6, see How-it-works + Gotchas), so a forged head no longer verifies and an insider DOES now lack a secret (the signing seed) for the head; (2) rows live PLAIN and mutable in `audit_outbox` for up to the ≤1h pre-seal window (`emitted_at IS NULL`) before they are chained, so a D1 writer can alter/delete an unsealed row with no trace at all (`crates/corelink-container/src/routes/audit_drain.rs:5-9`); (3) the storage-level immutability that would stop an insider rewriting the sealed rows + a fresh self-consistent chain — R2 Object-Lock — is now **WIRED** (`crates/corelink-container/src/routes/audit_archive.rs`), but it is a COPY, not the primary store: an insider with D1 write can still rewrite the D1 rows, and what the archive buys is that the rewrite no longer agrees with an immutable record a verifier can read. So "trust even if CoreLink itself is compromised" is NOT the current property: a relying party who holds an INDEPENDENT prior copy of the head (or the Rekor witness, when wired) can detect divergence; a party with only what CoreLink hands them cannot distinguish an honest chain from an insider-recomputed one. This control supports the SOC 2 CC7.2 audit-chain discipline as detect-at-verify EVIDENCE; the write-time chaining piece (sealing AT emit, closing the ≤1h pre-seal window) is DEFERRED, not live — but the keyed/signed-head piece and the storage-level 7-year append-only archive are now LIVE (CF-6 Ed25519-signs the chain head on advance + verifies on resume; tamper → fail-closed SEV-1).

# Role

Provide tamper-EVIDENT (detect-at-verify) auditing for security-relevant events (auth, CAS/AC, GC, quota, abuse, tenant lifecycle). The hash chain gives a per-tenant integrity check that a verifier holding an independent prior head can use to detect a retroactive edit/delete of a SEALED row; the Rekor submission seam (when wired) gives that independent head an external public anchor. Because the link hash is un-keyed and the pre-seal `audit_outbox` window is mutable, this is detection-against-a-known-reference, NOT cryptographic proof against an insider who can recompute the whole chain — see the honest-scope note above. Together they answer "has the sealed audit trail diverged from a head an external party already pinned?" — not "is CoreLink incapable of fabricating a consistent trail?".

# How it works

- Each audit event is a canonical CloudEvents 1.0 envelope (`specversion`/`type`/`source`/`subject`/`id`/`time_ms`/`datacontenttype`/`data` plus CoreLink extensions `tenant_id`/`region`/`sequence_number`/`prev_hash`), the same envelope the auth taxonomy emits into the outbox `docs/internal/auth-event-taxonomy.md:9-13` and materialized as the `AuditEvent` struct `crates/corelink-audit-chain/src/event.rs:308-369`.
- The chain link is `next_hash = BLAKE3(prev_hash_bytes || canonical_bytes(event))`, where the event is canonicalized with RFC 8785 JCS and streamed straight into the hasher `crates/corelink-audit-chain/src/chain.rs:152-162`, with canonical bytes computed via `serde_jcs::to_vec` `crates/corelink-audit-chain/src/chain.rs:97-99`. The hasher is a plain `Hasher::new()` — UN-KEYED, no `keyed_hash`/HMAC `crates/corelink-audit-chain/src/chain.rs:156`, `crates/corelink-audit-chain/src/chain.rs:183-193` — so the digest is a public function of the rows (the basis of the evidence-not-proof limit above).
- **The live producer is the drain, NOT `HashChainBuilder::append`.** `HashChainBuilder::append` is the write-time link primitive but is NOT how the live trail is sealed: the wired producer is the hourly `POST /_internal/audit/drain` `crates/corelink-container/src/routes/audit_drain.rs:487-514`, mounted in `crates/corelink-container/src/main.rs:586-598`. Rows are written PLAIN and UNCHAINED to `audit_outbox` first (`emitted_at IS NULL`), then sealed LATER at drain: the drain reads pending rows in deterministic order, JCS-canonicalizes each payload, links it via `link_chain_hash_from_canonical` (the verifier-path primitive), and writes the sealed columns + `audit_chain_head` checkpoint to D1 under a compare-and-set single-writer guard `crates/corelink-container/src/routes/audit_drain.rs:1023-1141`. So there is a ≤1h pre-seal window in which a row is mutable with no chain protection at all `crates/corelink-container/src/routes/audit_drain.rs:5-9`.
- **The offsite archive is a SEPARATE endpoint from the drain, on purpose.** `POST /_internal/audit/archive` (`crates/corelink-container/src/routes/audit_archive.rs`) reads rows the drain has ALREADY sealed, re-verifies every link from the persisted JCS bytes, and writes NDJSON chunks to the R2 bucket `corelink-audit-weur`, which carries the bucket-wide 7-year Object Lock rule `corelink-audit-7y-retention`. `crates/corelink-container/src/routes/audit_archive.rs:528-594`. It is not a write inside the drain because the drain must not acquire a new way to fail: an R2 outage inside the seal transaction would either abort the seal (leaving rows plain and mutable in the pre-seal window — strictly worse than no archive) or be swallowed. The split is also what lets the archiver walk BACKWARD over rows sealed long before it existed. Ordering is fixed: R2 first, `audit_outbox.archived_at` second (migration 0099), so a crash between them re-writes byte-identical bytes rather than marking rows archived against nothing `crates/corelink-container/src/routes/audit_archive.rs:388-402`. Writes are conditional (`If-None-Match: *` via `R2S3Client::put_if_absent`); a pre-existing key with identical bytes is idempotent success, a pre-existing key with DIFFERENT bytes is a hard failure that leaves the rows unarchived `crates/corelink-container/src/routes/audit_archive.rs:354-384`. The bucket default is a REAL, Object-Locked bucket, not one that has to be created first `crates/corelink-container/src/routes/audit_archive.rs:119`, resolved at boot `crates/corelink-container/src/routes/audit_archive.rs:154-200` and mounted fail-CLOSED `crates/corelink-container/src/main.rs:600-620`. The hourly driver is a sibling sweep of the drain cron `apps/signup-worker/src/webhooks/audit_archive_cron.ts:75-101`.
- **A partition whose chain is BROKEN no longer blocks its own healthy rows — clean prefix + quarantine.** Verification requires a CONTIGUOUS sequence, and a 17-minute seal fork on 2026-08-14 left 8 of 360 partitions with duplicated `sequence_number`s (each duplicate pair carrying a DIFFERENT `prev_hash`) and the following sequence missing, so those partitions were refused ENTIRELY and retried on every hourly tick, invisibly. The archiver now takes the LONGEST CONTIGUOUS VERIFYING PREFIX of the batch and archives it normally `crates/corelink-container/src/routes/audit_archive.rs:528-594`, then marks the unarchivable remainder — from the break through the end of the partition's currently-sealed set, bounded by a census MAX so rows sealed a moment later are not swallowed — with `quarantined_at` + a machine-readable `quarantine_reason` `crates/corelink-container/src/routes/audit_archive.rs:476-514`. Re-sequencing is FORBIDDEN: the sealed rows ARE the evidence, so the only columns the archiver ever writes are `archived_at`, `quarantined_at` and `quarantine_reason` `crates/corelink-container/src/routes/audit_archive.rs:424-435`, enforced by a test that re-reads the module's own source and fails on any `UPDATE` setting a chain column `crates/corelink-container/src/routes/audit_archive.rs:729-760`. Archiving RESUMES on later rows as a new chunk window, which is legal because a window's first row is checked against its own link only `crates/corelink-audit-chain/src/sealed_archive.rs:326`, `crates/corelink-audit-chain/src/sealed_archive.rs:351`. Quarantined rows leave the work queue (migration `0100_audit_outbox_quarantine.sql` adds a narrowed partial index alongside 0099's) and are reported, never merely logged: `rows_quarantined` / `partitions_quarantined` in the response `crates/corelink-container/src/routes/audit_archive.rs:660-661`, a WARN per segment, a dedicated cron line (the sibling `compliance/dsr-edge-crons` concept owns that plane), and an hourly census in `.github/workflows/audit-archive-lag.yml`. The sweep result carries the two counts back to the driver `apps/signup-worker/src/webhooks/audit_archive_cron.ts:125-126` and into the sweep result `apps/signup-worker/src/webhooks/audit_archive_cron.ts:139-140`.
- **The archive line carries the persisted bytes, not a recipe for them** (`crates/corelink-audit-chain/src/sealed_archive.rs`). The live chain seals GENERIC CloudEvents rows whose `id` is a composite dedup string, so they do not deserialize into the crate's typed `AuditEvent` — which is why the `corelink.audit.sealed.v1` line `crates/corelink-audit-chain/src/sealed_archive.rs:94` carries `audit_outbox.canonical_jcs` verbatim and the verifier recomputes `BLAKE3(prev_hash || canonical_jcs)` off it `crates/corelink-audit-chain/src/sealed_archive.rs:315-385`. Serialization refuses to emit bytes for a chunk that does not verify `crates/corelink-audit-chain/src/sealed_archive.rs:410-422`. The chunk key is `audit/<Y>/<M>/<D>/<tenant_id>/<region>/<8-digit-seq>.ndjson`: the partition segments are load-bearing, because the live chain numbers each `(tenant_id, region)` partition from its own 0 and `archive_producer::archive_chunk_key`'s documented `audit/<Y>/<M>/<D>/<seq>.ndjson` would collide between two partitions on the same day. The day slot comes from the event's own `enqueued_at`, never wall-clock-now, so a backfill files each chunk under the day it belongs to `crates/corelink-audit-chain/src/sealed_archive.rs:233-247`.
- **The CAS/AC data-plane audit INTAKE is a durable D1 `audit_outbox` sink.** The native CAS + AC handlers emit an audit row BEFORE every data-plane mutation into the SAME `audit_outbox` intake table this drain later seals; that intake sink is `D1AuditOutboxSink`, a single struct implementing BOTH `corelink_handler_cas::AuditSink` and `corelink_handler_ac::AuditSink` and appending each event as a PLAIN, UNCHAINED `INSERT OR IGNORE` row keyed deterministically per logical event (idempotent on a handler retry), with `emitted_at = NULL` and NO chain link — i.e. an ordinary pre-seal outbox row exactly like every other intake, sealed only later by the drain `crates/corelink-container/src/storage/d1_audit_sink.rs:134-151`, `crates/corelink-container/src/storage/d1_audit_sink.rs:167-189`. It is fail-CLOSED: the deployed CAS/AC handler builders wire it via `cas_audit_sink_from_d1` / `ac_audit_sink_from_d1`, which REFUSE (return `Err`, so the route mounts the 503 handler) when the D1 client can't be built — never the volatile `InMemoryAuditSink`, whose loss on restart would drop the pre-mutation audit row entirely `crates/corelink-container/src/storage/d1_audit_sink.rs:276-298`.
- **CF-6 keyed head (Ed25519-SIGNED).** Every checkpoint ADVANCE now also Ed25519-SIGNS the canonical head tuple `(tenant_id, region, head_hash, next_sequence)` (RFC-8785 JCS via `canonical_head_bytes`) and persists `head_signature` (base64) + `head_signed_at_ms` + `signing_key_id` (migration 0080) `crates/corelink-container/src/routes/audit_drain.rs:249-322`. On RESUME, once a seed is configured (the signing regime is ACTIVE), the resumed head MUST carry a signature that verifies under the CURRENT key id against the canonical tuple + the seed-derived public key; ANYTHING else is TAMPER → the drain refuses to extend the chain (fail-CLOSED, SEV-1): a verify failure, a NULL signature, a foreign `signing_key_id`, or a signed head with no seed to verify it `crates/corelink-container/src/routes/audit_drain.rs:559-617`. This closes the laundering hole (backend-audit §3) where an insider with D1 write STRIPS the signature to NULL — they lack the write-only seed so cannot re-sign, and the honest drain no longer re-signs an unverifiable head for them. So the chain HEAD is now tamper-evident against a D1-writer (who lacks the signing seed), not just un-keyed BLAKE3. The signing key REUSES the per-region erasure-attestation Ed25519 seed (`ERASURE_ATTESTATION_SEED_HEX`, or a dedicated `AUDIT_CHAIN_SIGNING_SEED_HEX`); with NO seed configured (dev/CI) the head is advanced UNSIGNED. Legitimate pre-0080 NULL heads + coordinated seed/key rotations are handled by an EXPLICIT, default-OFF, loudly-logged operator migration window (`AUDIT_CHAIN_TRUST_UNSIGNED_RESUME=1`) that temporarily tolerates NULL / foreign-key-id heads while the fleet is re-signed — never a silent tolerance.
- The 32-byte digest is a `ChainHash` newtype that serializes to lowercase hex on the wire `crates/corelink-audit-chain/src/event.rs:204-229`, and the genesis event uses the Bitcoin-style zero convention `prev_hash = [0u8; 32]` / `sequence_number = 0` `crates/corelink-audit-chain/src/event.rs:79-82`.
- `HashChainBuilder::append` is the typed write-time link primitive (it rejects a wrong `sequence_number` and rejects an event whose `prev_hash` does not match the current chain head before advancing `crates/corelink-audit-chain/src/chain.rs:285-303`), but the LIVE drain does NOT call it — the `audit_outbox` rows are generic CloudEvents JSON, not the crate's `AuditEvent` struct, so the drain canonicalizes the raw payload and drives `link_chain_hash_from_canonical` directly, seeding `(head, next_sequence)` via `HashChainBuilder::resume`/`new` `crates/corelink-container/src/routes/audit_drain.rs:77-87`. Write-time chaining (sealing AT emit, closing the pre-seal window) is therefore DEFERRED.
- The daily verifier walks an in-order `[start, end]` slice, recomputes every link with `link_chain_hash`, and advances the running head per event `crates/corelink-audit-chain/src/verifier.rs:186-191`, comparing each event's claimed `prev_hash` to the recomputed head in constant time via `subtle::ConstantTimeEq` `crates/corelink-audit-chain/src/verifier.rs:167-185`.
- On the first divergence the verifier fails CLOSED — it emits the `chain_break_detected` meta-audit BEFORE returning the `ChainBreak` error carrying the break sequence `crates/corelink-audit-chain/src/verifier.rs:174-184`, and reports the result (count, last good hash, optional break seq) in a `VerifyOutcome` `crates/corelink-audit-chain/src/verifier.rs:53-63`.
- The verifier also guards tenant isolation (every event's `tenant_id` must match the chain's) and sequence monotonicity before checking the link `crates/corelink-audit-chain/src/verifier.rs:140-156`.
- For the public witness, an already-signed payload is wrapped as a `SignedEntry` (canonical payload bytes + Ed25519 signature + PEM public key) `crates/corelink-transparency-log/src/entry.rs:28-41` and only its SHA-256 digest is computed `crates/corelink-transparency-log/src/entry.rs:63-66`.
- `to_rekor_hashedrekord` builds the canonical Rekor `hashedrekord` v0.0.1 proposed entry — submitting `{content_digest, signature, public_key}` so the raw payload bytes never leave CoreLink `crates/corelink-transparency-log/src/entry.rs:71-91`.
- `witness_or_degrade` drives the `RekorSubmitter` seam `crates/corelink-transparency-log/src/submit.rs:24-39` post-hoc and fails OPEN: a transient transport fault degrades to `WitnessOutcome::Degraded` for out-of-band retry rather than erroring `crates/corelink-transparency-log/src/submit.rs:101-107`, and even a deterministic Rekor rejection degrades instead of coupling to the caller's write path `crates/corelink-transparency-log/src/submit.rs:108-118`.

# Invariants

- INV-OBS-AUDIT-CHAIN-INTEGRITY: the per-tenant hash chain is unbroken and the daily verifier asserts every link's recomputed hash matches the claimed hash `crates/corelink-audit-chain/src/lib.rs:83-88`.
- INV-AUDIT-APPEND-ONLY: the LIVE property is tamper-EVIDENCE — a retroactive edit/delete of a SEALED row is DETECTABLE at verify time via the per-tenant chain, for a verifier holding an independent prior head. The crate doc-comment still frames this invariant as "R2 Object Lock Governance Mode 7y enforces append-only at storage level" `crates/corelink-audit-chain/src/lib.rs:89-92`, but that storage-level enforcement is NOT what runs: the live seal writes to D1 (`audit_outbox` / `audit_chain_head`), NOT R2, and the R2 Object-Lock binding is UNWIRED (Gotchas, and consistent with the lib doc-comment's own designed-vs-wired caveat). So of the three pieces that would make this true append-only — (a) R2/Object-Lock storage immutability, (b) a KEYED or signed chain head an insider cannot forge, (c) write-time chaining that closes the ≤1h pre-seal mutable window — (b) is now LIVE (CF-6 Ed25519-signs the chain head on advance + verifies on resume, fail-closed SEV-1), while (a) and (c) remain DEFERRED. The invariant as written still OVERSTATES storage-level append-only; treat it as detect-at-verify evidence (with a now-signed head) until (a)/(c) land.
- Genesis is the zero-hash position by construction: `prev_hash == [0u8; 32]` and `sequence_number == 0`, detected by `is_genesis` `crates/corelink-audit-chain/src/event.rs:439-445`.
- Sequence numbers are strictly monotonic increasing by 1; the builder advances with `saturating_add(1)` only after both link checks pass `crates/corelink-audit-chain/src/chain.rs:299-302`.
- Tamper detection surfaces at the first divergent sequence and is fail-CLOSED: the verifier returns `ChainBreak` after emitting the SEV-0 meta-audit `crates/corelink-audit-chain/src/verifier.rs:181-184`.
- Hash comparison in the verifier is constant-time to avoid a timing oracle over which/where bytes differ `crates/corelink-audit-chain/src/verifier.rs:167-173`.
- The audit data payload must be already-redacted of raw PII before reaching chain emit — the chain layer is purely structural and does NOT re-redact `crates/corelink-audit-chain/src/event.rs:46-57`.
- The Rekor witness is best-effort enrichment, never a gate: the entry is already durable before submission and a Rekor outage must not block the write path `crates/corelink-transparency-log/src/lib.rs:31-38`.
- CoreLink is a submitter only — it does not operate an append-only log or gossip checkpoints; that public good is delegated to sigstore/Rekor `crates/corelink-transparency-log/src/lib.rs:26-29`.

# Gotchas

- The chain link input includes the `prev_hash` slot itself (Bitcoin block-header pattern), so flipping a single bit of `prev_hash` changes the recomputed link too — but it also means producer and verifier MUST agree byte-for-byte on JCS canonical form; canonical-form drift (e.g. a `serde_jcs` bump) would silently corrupt every link. The pin is `serde_jcs = "0.2"` plus canonical-vector regression tests.
- The verifier never re-canonicalizes off the wire archive; it reads the persisted JCS NDJSON bytes and recomputes BLAKE3 directly, so the persisted bytes are load-bearing.
- **The seal still lands in D1, which is mutable; the R2 Object-Lock copy is an ARCHIVE, not the store of record.** Until 2026-08-23 this was worse: the archive did not exist at all, and `crates/corelink-audit-chain/src/archive_producer.rs` — which writes exactly the key shape the daily verifier looks for — was dead on two independent axes (its only caller sits behind the Cargo feature `cf-billing-real`, which no build or deploy path passes, inside a wasm cdylib the live Worker never imports), so the cron paged SEV-0 every day over a bucket that never existed. That is closed by `audit_archive.rs`. What remains true: the PRIMARY sealed rows are in D1, so an insider with D1 write can rewrite a sealed row AND, because the per-link hash is un-keyed, recompute a self-consistent chain BODY over the rewritten rows. With CF-6 the `audit_chain_head` checkpoint is now Ed25519-SIGNED, so a forged head fails signature verification on the next drain resume (fail-CLOSED, SEV-1) — the insider lacks the signing seed `crates/corelink-container/src/routes/audit_drain.rs:559-617`. An INDEPENDENT prior head (a pinned head, or — when wired — the Rekor witness) is still the strongest cross-check, and the per-link body + pre-seal window remain un-keyed.
- **The ≤1h pre-seal window is unprotected.** Until the hourly drain runs, `audit_outbox` rows are PLAIN, UNCHAINED CloudEvents (`emitted_at IS NULL`), so a D1 writer can alter or delete a not-yet-sealed row with ZERO chain evidence `crates/corelink-container/src/routes/audit_drain.rs:5-9`. Closing this requires write-time chaining (sealing at emit), which is deferred.
- BLAKE3 here is the per-tenant chain digest; the Rekor `hashedrekord` separately uses SHA-256 over the canonical payload (that is Rekor's required scheme), so two different hash families coexist by design — don't "unify" them.
- The SEV-1 auth events fan out directly to SIEM (not just the 60-s outbox drain); the chain/transparency layer is downstream of that fan-out and is not the incident-response fast path.
