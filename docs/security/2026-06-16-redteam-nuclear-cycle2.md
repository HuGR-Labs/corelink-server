## Root-cause triage — the 39 collapse to **7 clusters**
Almost every finding is the same defect class: **#297 hardened the native CAS/AC/Bazel/Turbo plane, but its sibling write/auth surfaces were not brought along.** The nuclear round's "second-order / incomplete-fix on a sibling route" directive is exactly what surfaced these.

### Cluster A — Customer/Users plane has NO `native_pat_gate` Argon2id backstop ⟵ contains the CRITICAL
**Findings:** A1 (CRITICAL), A17 (HIGH scope-escalation), A18–A23 (HIGH), A35/A37/A38/A39 (LOW). **~11 findings.**
**Root cause (cold-verified):** `CustomerRouteState` (`crates/corelink-container/src/routes/customer.rs:7`) has no `pat_gate` field; `routes.rs:462` builds + merges `customer_state` with zero backstop wiring (contrast `bazel_state.pat_gate` at `routes.rs:412`). `users.rs` (`/v1/users/me`) is likewise un-gated. So a **leaked `PAT_SIGNING_KEY`** lets an attacker HMAC-forge a PAT (Worker does HMAC fast-fail only on this path — `index.ts:720-726`), which reaches the customer plane with **no Argon2id check**, and `handle_keys_create` (`customer.rs:476` → `customer_d1.rs:902-972`) **mints a GENUINE `cas:rw` PAT for the victim tenant** (durable, survives key rotation) → cross-tenant cache read/write + **shared-cache poisoning → code execution in victim builds**. A17: the customer plane also enforces **no scope gate** → a read-only PAT mints itself a read-write PAT + Owner team-role.
**FIX (extends the #297 pattern):**
1. Add `pat_gate: Option<Arc<NativePatGate>>` to `CustomerRouteState` + the users route state; populate in `build_handlers_from_env`; wire `customer_state.pat_gate = native_pat_gate.clone()` at `routes.rs:462`. In each handler, after resolving `tenant()` from the header, `pat_gate.verify(&t, authz).await?` **before** any handler/storage call (Argon2id ⇒ HMAC-forged PAT fails closed). Skip the backstop for Clerk-session callers via the `x-corelink-token-prefix=="clerk"` sentinel (already edge-verified).
2. Scope enforcement on mint: `handle_keys_create` must reject minting a `cache:write`/`cas:rw` (or admin/Owner) credential from a read-only principal (read `x-corelink-scope`).
3. Strategic root: complete the F3 TODO — wire `NativePatGate` onto **ALL** tenant-data + tenant-control planes uniformly (native ✓ via #297; customer/users = the remaining gap), so a leaked signing key fails closed everywhere.

### Cluster B — Storage byte-accounting not wired on Bazel / OCI / adapter (cargo/brew/npm/pip) write surfaces
**Findings:** A2,A3,A4,A5,A6,A7,A10,A11,A12,A13,A14,A15 (all HIGH). **12 findings.**
**Root cause (cold-verified):** #297 wired `byte_accountant` onto native `cas.rs`/`ac.rs` and `turbo_state.bytes` (`routes.rs:466`), but **`bazel_state.bytes` is never set**, and the OCI + adapter-bridge CAS-write paths carry no accountant. So Bazel REAPI, OCI push, and the language adapters write blobs to R2 that **never accrue `tenant_storage_state.bytes_used`** → a Free tenant stores unlimited TB at $0; every tier's storage cap is fiction on those planes. A12/A13: OCI **also** bypasses the Worker `$`-ceiling quota path entirely (unmetered spend).
**FIX:** wire `ByteAccountant` into `BazelRouteState`, the OCI route state, and the adapter bridge CAS-write path; accrue on every write surface (mirror the native cas.rs accrual). Route OCI through the Worker quota/`$`-ceiling check like the other planes.

### Cluster C — Byte-accounting is accrue-AFTER-commit, no reservation, no release (race / over-commit / leak)
**Findings:** A9 (HIGH over-commit race), A16 (HIGH over-cap durably written), A32/A34 (MED delete never frees — `release()` dead code), A33 (MED over-cap commits before 402). **5 findings.**
**Root cause:** accrual runs **after** the R2 PUT with no pre-reservation and no compensating release; `release()` is dead code. ⇒ (a) concurrent native writes over-commit past the cap arbitrarily, (b) an over-cap blob lands durably and stays readable, (c) deletes never decrement `bytes_used` → headroom leaks forever within a cycle.
**FIX:** move to **reserve → commit → release-on-failure**: reserve bytes (atomic D1 UPSERT with cap check) **before** the R2 PUT; on PUT failure or over-cap, release the reservation (or compensating-delete the blob); wire `release()` on the delete paths (CAS + AC) so `bytes_used` decrements. This is the one genuinely concurrency-correctness-sensitive cluster — needs careful atomic semantics + a regression test.

### Cluster D — Monthly request-count quota is OFF (fail-open) in production
**Findings:** A25, A30, A31 (MED). **3 findings.**
**Root cause (cold-verified):** `requestQuotaEnabled = env.REQUEST_QUOTA_ENABLED === "true"` (`worker/src/index.ts:1933`) — unset in prod ⇒ `checkRequestQuota` no-ops ⇒ the contracted per-month request cap is unenforced.
**FIX:** default-on / fail-closed (or invert to an explicit `REQUEST_QUOTA_DISABLED` kill-switch) **and** set the var in the 5 prod envs (owner secret/var op — surface, don't block). Add a test asserting the gate is live by default.

### Cluster E — Backend error strings + storage topology leak into public HTTP responses
**Findings:** A24 (MED, **unauth-internet** — the only unauth finding: OCI `/token` leaks raw Cloudflare D1 API error, possibly SQL), A27/A28/A29 (MED adapter/OCI leak raw D1/R2 detail + per-tenant R2 prefix). **4 findings.**
**Root cause:** error envelopes reflect inner backend error strings verbatim.
**FIX:** sanitize all public error responses — map internal errors to opaque REAPI codes + a request-id; never reflect D1/R2/storage strings or the derived tenant prefix. **A24 first** (unauth-reachable). Pattern already exists in `session_exchange.ts` (collapse upstream non-200 to a generic 500) — apply uniformly.

### Cluster F — Bazel (and OCI/adapter) write path has no in-flight byte budget / per-tenant concurrency cap
**Findings:** A8 (HIGH). **1 finding (likely undercounted — rounds 3-4 DoS hunt was rate-limited).**
**Root cause:** #297 added the Turbo `FromRequestParts` byte-budget + concurrency guard, but the Bazel CAS write buffers the full 10 MiB body before any gate and has no per-tenant concurrency cap.
**FIX:** apply the same pre-body reservation extractor + global in-flight byte budget + per-tenant concurrency cap to the Bazel (and OCI/adapter) write handlers.

### Cluster G — `/_internal/pat/mint` rate (not just concurrency) unbounded
**Findings:** A36 (LOW). **1 finding.**
**Root cause:** #297 added a concurrency semaphore on the mint route but no **rate** limit; an internal-auth holder can sustain Argon2id CPU/RAM exhaustion under the concurrency cap.
**FIX:** add a token-bucket rate limit on `/_internal/pat/mint` (mirror the Worker-side `session_exchange` throttle, container-side).

### A36. [LOW] PAT mint concurrency limiter caps SIMULTANEOUS Argon2id but not RATE — internal-auth holder can sustain Argon2id CPU/RAM saturation of the shared container

- **persona:** Holder of the internal-auth key (compromised signup-worker / leaked CORELINK_INTERNAL_AUTH_KEY or CORELINK_PAT_MINT_AUTH_KEY)
- **class / reachability:** DoS / resource-exhaustion (CPU/memory-hard hash loop) / `leaked-secret-only` · **round** 1 · **votes** 3/5
- **preconditions:** Leaked/known internal-auth key (shared CORELINK_INTERNAL_AUTH_KEY, or the per-consumer mint key — which falls back to the shared key when unset). Not reachable by an ordinary tenant.
- **impact:** Sustained CPU + ~1 GB RAM saturation of the shared container → latency/availability degradation or OOM for all tenants on that container. The #297 concurrency cap mitigates burst memory but leaves a sustained-rate CPU/RAM DoS open to a key holder.
- **chain:** 1. Possess the internal-auth (or per-consumer PAT_MINT) key — the spec's leaked-secret-only precondition. 2. Fire 16 concurrent POST /_internal/pat/mint requests; MintInflightLimiter (internal_pat.rs:142-196, DEFAULT_MAX_INFLIGHT_MINTS=16) admits exactly 16 and 429s the rest — but it only bounds CONCURRENCY, not requests/second. 3. Each mint runs one Argon2id hash (m=65536 KiB ≈ 64 MB, t=3, p=4) on a tokio blocking thread. As each completes, immediately fire another. Sustained throughput ≈ 16 / hash_latency mints/sec, indefinitely. 4. 16 concurrent Argon2id = ~16 x 64 MB ≈ 1 GB working set continuously + full CPU on the blocking pool, starving async CAS/AC/Turbo handlers on the same shared container (no FIFO/priority fairness). - **fix:** Add a per-caller token-bucket/rate gate to the mint surface so the key holder cannot pin 16 concurrent hashes indefinitely. Concretely in crates/corelink-container/src/routes/internal_pat.rs: extend InternalPatRouteState (line 217) with a governor::RateLimiter (e.g. a low sustained rate like a few mints/sec + small burst, keyed globally since the real caller mints one PAT per new tenant), and check it in handle_mint AFTER the auth gate (after line 375) and BEFORE try_acquire (line 383), returning 429 on exhaustion. This caps requests/sec, not just concurrency, closing the sustained-throughput angle. Secondary defence-in-depth (tracked separately): restrict /_internal/pat/mint to a Worker-to-Worker Service Binding so it is not publicly routable (per the module's own "Recommended hardening" note, internal_pat.rs:15-18), and complete the per-consumer-secret split so a signup-worker leak does not exercise the mint at all.
