Workflow `corelink-redteam-brutal` (wf_d71b2c54-735): 121 agents, ~33 min. Boundaries mapped: 6; candidates: 35; **confirmed exploitable: 7** (by severity: {'high': 4, 'low': 3}).

## [1] HIGH — Storage quota is structurally inert — no code increments tenant_storage_state.bytes_used, so per-tier storage caps NEVER trip (unlimited storage on any tier, incl. Free)
- **class/persona/reach:** billing-abuse / malicious-tenant / any-free-tenant (votes 3/3)
- **Chain:** 1. Sign up for the Free tier (10 GB cap per QUOTAS table). 2. Mint a normal cas:rw PAT. 3. PUT arbitrary blobs to /v1/cas/<my-tenant>/<hash> in a loop (each up to the 5 MiB per-blob cap). 4. The Worker storage gate runs `SELECT SUM(bytes_used) FROM tenant_storage_state WHERE tenant_id=?` (worker/src/lib/quota.ts:297-302) and compares to the 10 GB free cap. But NOTHING in the live data plane ever INSERTs/UPDATEs bytes_used: the container CAS write handler (crates/corelink-container/src/routes/cas.rs:462 `state.write.write(req)`) only verifies the hash and writes to R2 — it never touches tenant_storage_state. The only writers found are corelink-eviction (DECREMENT on GC) and the customer-dashboard READ (customer_d1.rs:565). The corelink-billing CAS quota crate (crates/corelink-billing/src/quota/cas/cas.rs) is NOT wired into the container write route (container only imports corelink_billing for the Stripe webhook materializer — confirmed by grep of main.rs/cas.rs). 5. SUM(bytes_used) therefore stays 0 (or a never-incremented stale value) forever, so `totalBytes < quota.storageBytesMax` is always true → storage check always returns ok:true. Store unbounded bytes on a $0/mo Free account.
- **Impact:** The entire per-tier storage product axis (Free 10 GB / Solo 50 GB / Starter 150 GB / Pro 500 GB / Max 2 TB) is unenforceable. A Free tenant can store terabytes at $0; every paid tier's storage differentiator is meaningless. Direct, ongoing R2 cost (our COGS) with no revenue cap on the storage dimension — the storage cap that the pricing page sells does not exist in the running system.
- **Evidence:** worker/src/lib/quota.ts:297-312 (storage gate reads SUM(bytes_used), passes when total < cap); crates/corelink-container/src/routes/cas.rs:423-472 handle_write never accrues bytes_used; grep across crates+worker+apps finds NO INSERT/UPDATE of tenant_storage_state.bytes_used in any data-plane write path (only corelink-eviction decrements it, customer_d1.rs reads it). The 'DO's CAS quota enforcement (quota_fsm_state)' cited as the deeper net in worker/src/index.ts:1877 does not exist — the DO (worker/src/durable_object.ts:234 proxyToContainer) is a pass-through proxy with no byte gate.
- **Fix:** Accrue bytes_used on every successful CAS/AC write and decrement on delete, atomically, so the existing Worker gate (quota.ts:310 totalBytes < cap) has a real counter to read. Concrete approach: in crates/corelink-container/src/storage/r2_s3.rs handle of write() (after the Ok(()) branch at ~line 720, before returning CasWriteResponse), perform a single check-and-accrue against tenant_storage_state via the already-present D1HttpClient seam (the same StorageEnv the QuotaGuard uses): UPSERT `INSERT INTO tenant_storage_state(tenant_id,bytes_used,...) VALUES(?1,?2,...) ON CONFLICT(tenant_id) DO UPDATE SET bytes_used = bytes_used + ?2, bytes_used_updated_at_ms = ?3`, and mirror a saturating subtract in the delete()/eviction path (eviction already decrements at storage_state.rs:282, so only the increment side is missing). Do the cap CHECK in the same statement to close the TOCTOU race the reservation crate (crates/corelink-billing/src/quota/cas/cas.rs, core/check.rs:202 commit_reservation) was designed for — i.e., wire the existing corelink-billing CAS-quota reserve→commit (and add the corelink-eviction reservation dep) into the CAS write route instead of leaving it as dead pure-logic. Until per-byte accrual lands, as an interim hard backstop ensure quota_guard_from_env() is non-None in all 5 prod envs (QUOTA D1 storage env set) so the $5/mo op-count tripwire at least caps blast radius; but that is a stopgap, not the per-tier storage control. Must be guarded by INV-CAS byte-accounting invariant + a regression test that PUTs past the Free 10 GB cap and asserts 429 QUOTA_EXCEEDED.

## [2] HIGH — Turbo PUT buffers up to 100 MiB into heap BEFORE the per-tenant concurrency guard fires — shared-container OOM via concurrent uploads
- **class/persona/reach:** dos / malicious-tenant / any-free-tenant (votes 2/3)
- **Chain:** 1. Sign up for any tier (Free works) and obtain a cas:rw PAT. 2. Open many concurrent `PUT /v8/artifacts/<hash>?teamId=x` requests, each streaming a body just under the 100 MiB cap (TURBO_BODY_LIMIT_BYTES = 100*1024*1024). 3. axum extracts handler arguments BEFORE running the handler body: the `body: axum::body::Bytes` argument (turbo_v8.rs:344, the LAST arg of handle_put) buffers the ENTIRE 100 MiB into heap during argument extraction. The per-tenant concurrency guard (turbo_v8.rs:366-406, cap = TURBO_PUT_CONCURRENCY_LIMIT = 4) only executes INSIDE the handler body — i.e. AFTER all four-plus bodies are already resident. 4. The upstream rate-limit layer (ratelimit_layer.rs:192) permits a 200-request burst per tenant (DEFAULT_TENANT_BURST = 200) and only reads headers, so it does not stop concurrent body buffering. 5. Fire ~200 concurrent PUTs in one burst window: ~200 × 100 MiB ≈ 20 GB of transient heap on the shared container before any 429/concurrency rejection lands. The container OOMs, taking down EVERY co-tenant on that container instance.
- **Impact:** Shared-container OOM / crash → outage for all other tenants pinned to that container. The documented mitigation (TURBO_PUT_CONCURRENCY_LIMIT) is structurally ineffective because the body is buffered during argument extraction, before the guard runs. Memory pressure is N × 100 MiB where N is bounded only by the 200-token burst, not by the cap of 4.
- **Evidence:** crates/corelink-container/src/routes/turbo_v8.rs:338-345 (handle_put signature: `body: axum::body::Bytes` is the last extractor, buffered before the handler body); turbo_v8.rs:366-406 (concurrency guard runs INSIDE the handler, after buffering); turbo_v8.rs:100 (TURBO_BODY_LIMIT_BYTES=100 MiB) + turbo_v8.rs:277 (per-route DefaultBodyLimit raises the cap to 100 MiB); ratelimit_layer.rs:79-85 (200-token burst) + ratelimit_layer.rs:192-210 (layer reads headers only, cannot stop in-flight body buffering). The guard comment (turbo_v8.rs:105-111) claims it bounds peak working set to ~400 MiB, but that is false: the cap is enforced post-buffering, so peak is bounded by burst×100 MiB.
- **Fix:** turbo_v8.rs handle_put (lines 338-406): the cap-4 reservation must happen BEFORE the body is buffered. Extractors run before the body-consuming `Bytes` extractor, so convert the per-tenant in-flight reservation into a custom `FromRequestParts` extractor (it sees only headers/parts, runs before `body: Bytes`) that does the lock+count+increment and returns 429 if >= TURBO_PUT_CONCURRENCY_LIMIT, carrying the RAII PutGuard in its output so the slot releases on drop. Declare it as a handler argument ahead of `body: axum::body::Bytes`. This makes the cap-4 actually gate buffering, bounding peak per-tenant heap to ~4 × 100 MiB as documented. Defence-in-depth (SOTA): also add a process-wide aggregate in-flight-byte budget — either a global `tower::limit::ConcurrencyLimitLayer`/`LoadShedLayer` in main.rs around `axum::serve`, or a shared atomic byte accountant reserved in the same FromRequestParts extractor (reserve Content-Length, or the 100 MiB worst case when Content-Length is absent/chunked), so the bound holds even across many tenants sharing one container. Also correct the false "~400 MiB" comment at turbo_v8.rs:105-111. Lower the Turbo body cap or make it tier-aware if 100 MiB × 4 is still too large for the smallest container instance.

Items (1)+(2) are the F4 follow-ups already documented at index.ts:561-564; item (3) closes the trust-the-body authz gap.

## [4] HIGH — Leaked PAT_SIGNING_KEY + a victim's token_id → forge working cross-tenant PAT on native plane (no secret/Argon2id re-check)
- **class/persona/reach:** tenant-isolation / leaked-secret / leaked-secret-only (votes 3/3)
- **Chain:** 1. Attacker leaks PAT_SIGNING_KEY (hex, Worker env). 2. Attacker learns a VICTIM's 16-char token_id — it is NOT secret-grade: it is the indexed D1 lookup key, the cleartext-prefix segment of the victim's PAT, and is logged as `token_id = %pat.token_id` at mint (internal_pat.rs:355) and elsewhere. 3. Attacker fabricates a fresh random_secret, builds preimage `<token_id>.<random_secret>` and computes hmac_sig = HMAC-SHA256(PAT_SIGNING_KEY, preimage)[:16] base64url, assembles corelink_pat_<token_id>.<random_secret>.<hmac_sig>. 4. curl -H 'Authorization: Bearer <forged>' https://corelink-api.humangr.com/v1/cas/... 5. extractAuth verifies HMAC against the signing-key set (index.ts:794-799) → passes (attacker holds the key). 6. D1 lookup by token_id (index.ts:816-819) finds the VICTIM's row → resolvedTenantId = victim. The native plane NEVER Argon2id-verifies random_secret (decided posture, index.ts:775-784) and the container CAS/AC/Bazel routes contain ZERO PatVerifier/Argon2 calls — they trust the Worker-injected x-corelink-tenant-id. 7. Worker sets x-corelink-tenant-id=victim, x-corelink-scope=victim's scope, forwards. Attacker now reads/writes the victim's CAS/AC under that scope.
- **Impact:** Cross-tenant blob/AC read AND write (if the victim's pat.scope is cas:rw) for any tenant whose token_id is known — exfiltrate private build artifacts and POISON the victim's cache (write attacker bytes the victim will pull on a hit, with content-hash binding the only guard). Scope is bounded by the victim row's D1 scope, but admin-scoped rows widen it.
- **Evidence:** crates/corelink-pat/src/format.rs + mint.rs:92-96 (HMAC preimage = token_id.random_secret — tenant NOT in signed preimage; tenant binding is in D1 by token_id); worker/src/index.ts:775-784 (deliberate NO per-request Argon2id on native plane), :794-847 (HMAC + D1 token_id existence only, random_secret never checked); grep confirms NO argon2/PatVerifier in routes/cas.rs, ac.rs, bazel_v2.rs. token_id logged at internal_pat.rs:355.
- **Fix:** Wire the existing container-side Argon2id backstop onto the native plane so random_secret possession is verified even if PAT_SIGNING_KEY leaks (defense-in-depth the sibling adapters already have). Concretely: in crates/corelink-container/src/routes/cas.rs (handle_read/handle_write), ac.rs, and bazel_v2.rs, replace bare trust of x-corelink-tenant-id with a call through crate::adapter_pat::PatVerifier::verify (adapter_pat.rs:325) on the forwarded PAT — i.e. have the Worker forward the PAT plaintext (or a one-time DO-internal handle) and resolve tenant from PatVerifier::verify, which does the constant-time token_id match + HMAC + Argon2id-of-secret against pat_hash (adapter_pat.rs:28-30, verify_with_hash_multi). To keep the hot-path cpu budget, cache the (token_id -> verified tenant/scope) result per the verified random_secret with a short TTL (amortised Argon2id, exactly the 'cached per token_id' note at index.ts:780) so steady-state hits skip Argon2id but a forged secret (which is NOT in cache and fails Argon2id once) is rejected. This closes the gap because the leaked signing key alone no longer suffices — the attacker would also need the victim's 256-bit random_secret, which is never logged and never in the plaintext prefix. Independent of the fix: signing-key rotation (PAT_SIGNING_KEY_PREV/_NEW machinery already exists) is the incident response if a leak is suspected.

## [5] LOW — Monthly request cap (requestsPerMonthMax) is unenforced — checkRequestQuota is a hard-coded no-op, so the per-tier request quotas on the rate card do not exist

- **Chain:** 1. Free tier advertises 500K req/mo, Solo 2M, etc. 2. checkRequestQuota (worker/src/lib/quota.ts:363-380) unconditionally `return { ok: true }` — there is no monthly_request_counts table and no counter (acknowledged TODO). 3. The worker calls it (index.ts:1919) but it can never deny. 4. The only thing that eventually bites is the byte-blind $5 $-ceiling at ~5000 billable ops (see other finding), but non-billable routes and read amplification are not all $-charged.
- **Impact:** The monthly request entitlement that differentiates tiers on the signed rate card is not enforced anywhere. Free tenants get effectively unlimited monthly requests bounded only by req/s and the $5 op tripwire; the request-count product axis is fictional.
- **Evidence:** worker/src/lib/quota.ts:363-380 checkRequestQuota always returns ok:true; quota.ts:72-75/333-349 docstring admits the counter backend does not exist; worker/src/index.ts:1919 wires the no-op; crates/corelink-container/src/routes/ratelimit_layer.rs is in-memory + resets on restart (per the recon map).
- **Fix:** Wire the deferred counter that the docstring already specs. (1) Add migration: monthly_request_counts(tenant_id TEXT, year_month TEXT, request_count INTEGER, PRIMARY KEY(tenant_id, year_month)). (2) On the allow path in worker/src/index.ts (~after line 1919), atomically INSERT ... ON CONFLICT DO UPDATE SET request_count = request_count + 1 RETURNING request_count, guarded behind REQUEST_QUOTA_ENABLED. (3) In quota.ts:363 change checkRequestQuota to accept a D1 handle, SELECT request_count for (tenant_id, current year_month), and return {ok:false, retryAfterSec: secondsUntilNextMonthStart(), reason} when request_count >= _tierResult quota.requestsPerMonthMax — secondsUntilNextMonthStart() already exists (quota.ts:390). To avoid a per-request D1 write hot path, prefer a Durable Object counter (one per tenant) or batched/sampled increments rather than a synchronous D1 write on every cache lookup, since at 100 req/s a D1 write-per-request is itself a cost/latency hazard. Note: this is an owner-gated billing-feature build, not an emergency hotfix.

## [6] LOW — Brand-new tenant first billable op bypasses the $-ceiling entirely (unconditional accrue, not check_and_accrue) — concurrent burst over-admission on a fresh tenant
- **class/persona/reach:** billing-abuse / malicious-tenant / any-free-tenant (votes 2/3)
- **Chain:** 1. Use a tenant_id with no tenant_quota row yet (brand-new tenant — the common case at launch). 2. In QuotaGuard::check, when store.get returns None, `rolling=true` and the `existing.is_none()` branch calls store.accrue(...) — an UNCONDITIONAL DB increment with NO ceiling predicate (tenant_quota.rs:419-429). The steady-state path uses the atomic check_and_accrue with `WHERE accrued+delta <= budget`; the fresh-row path deliberately does not. 3. The comment assumes 'a single op's cost is far below the tripwire'. But under concurrency, fire N simultaneous first ops for the same fresh tenant: every request observes store.get == None (no row committed yet), every one takes the unconditional accrue path, and the D1 INSERT...ON CONFLICT DO UPDATE SET accrued = accrued + delta (d1_http.rs:461-478) SUMS them — none is ceiling-checked. All N ops are served regardless of whether N*cost exceeds the $5 budget. 4. The same unconditional-accrue gap exists on the post-roll path's seed of a brand-new row. This is the exact TOCTOU class the F13 fix closed for steady-state, re-opened for the fresh/seed path.
- **Impact:** A fresh tenant's first burst of billable ops is admitted with no $-ceiling check, allowing over-admission past the cumulative cost cap at tenant creation time. Lower blast radius than the inert-storage bug (bounded by how fast you can fire before the row commits) but it is a real, exploitable hole in the ADR-0068 fail-closed guarantee.
- **Evidence:** crates/corelink-container/src/tenant_quota.rs:419-429 (fresh-row path calls self.store.accrue, NOT check_and_accrue — no budget predicate); contrast tenant_quota.rs:447-467 steady-state uses check_and_accrue; crates/corelink-container/src/storage/d1_http.rs:461-478 tenant_quota_accrue is an unconditional `accrued = accrued + delta` with no ceiling WHERE.
- **Fix:** crates/corelink-container/src/tenant_quota.rs:424 — replace the unconditional `self.store.accrue(...)` seed with a budget-checked atomic seed so the fresh-row path matches the F13 guarantee. Add a `seed_and_accrue` store method whose D1 impl is `INSERT INTO tenant_quota (tenant_id, accrued_usd_micros, monthly_budget_usd_micros, cycle_anchor_ms, updated_at_ms) VALUES (?1, ?2, ?budget_default, ?anchor, ?ts) ON CONFLICT(tenant_id) DO UPDATE SET accrued_usd_micros = tenant_quota.accrued_usd_micros + excluded.accrued_usd_micros, updated_at_ms = excluded.updated_at_ms WHERE tenant_quota.accrued_usd_micros + excluded.accrued_usd_micros <= tenant_quota.monthly_budget_usd_micros RETURNING accrued_usd_micros`, plus an INSERT-side guard rejecting delta > DEFAULT_MONTHLY_BUDGET (so a single seed op can't exceed the cap either) — returning Ok(true) iff a row is returned. Then at tenant_quota.rs:419-429 treat Ok(false) as the 402 ceiling rejection exactly like the steady-state arm. This makes the seed serialize check-with-increment so N concurrent fresh-tenant ops sum under one cap predicate instead of all admitting. Add a concurrency regression test (M simultaneous max-batch first-ops on a fresh tenant must not accrue past budget).

## [7] LOW — Argon2id mint-loop CPU/RAM exhaustion on /_internal/pat/mint — unbounded, un-rate-limited 64 MiB+250 ms per call (requires the shared internal-auth secret)
- **class/persona/reach:** dos / leaked-secret / leaked-secret-only (votes 3/3)
- **Chain:** 1. Obtain CORELINK_INTERNAL_AUTH_KEY (shared with signup-worker; leaks via CI logs / config / env dump). 2. Loop `POST /_internal/pat/mint` with the valid header and a minimal valid body. Each accepted mint calls mint() → hash_random_secret() (Argon2id, 64 MiB + ~250 ms, argon.rs:43-50; invoked unconditionally at crates/corelink-pat/src/mint.rs:103). 3. This route is merged in main.rs:308 AFTER the rate-limit layer is applied (the layer wraps only build_with_factory's data plane; ratelimit_layer.rs:19-22 documents that /_internal/* is intentionally OUTSIDE the layer). There is therefore NO request-rate limit and NO Argon2 concurrency cap on mint. 4. Fire mints as fast as connections allow → each spawns a 64 MiB Argon2 working set; thousands of concurrent mints exhaust container RAM/CPU and OOM/wedge it, on top of the (already game-over) ability to mint admin PATs for any tenant.
- **Impact:** On top of any-tenant admin PAT minting, an unbounded Argon2 mint-loop is a pure resource-exhaustion kill of the shared container (64 MiB × concurrency, no rate limit, no concurrency cap). Compounds the F4 blast radius into an OOM/DoS.
- **Evidence:** crates/corelink-pat/src/mint.rs:103 (hash_random_secret called on every mint); crates/corelink-pat/src/argon.rs:43-50 (64 MiB Argon2id cost); crates/corelink-container/src/main.rs:299-310 (DefaultBodyLimit + rate-limit layer wrap build_with_factory; /_internal/pat/mint is .merge()d afterward, outside both); crates/corelink-container/src/routes/ratelimit_layer.rs:19-22 (explicitly states /_internal/* is outside the rate-limit layer); internal_pat.rs:259-310 (handler does the auth gate then mints with no rate/concurrency guard).
- **Fix:** Defense-in-depth for the internal mint surface so a leaked secret cannot ALSO trivially OOM the shared container: (1) Offload the Argon2 hash off the async runtime — wrap hash_random_secret in tokio::task::spawn_blocking inside mint()/handle_mint so floods are bounded by the blocking-pool size and never wedge tokio worker threads (crates/corelink-pat/src/mint.rs:103 path, or call it via spawn_blocking in internal_pat.rs handle_mint before/around the mint() call). (2) Add a bounded global concurrency gate on the mint route: a static `tokio::sync::Semaphore` (e.g. permits = num_cpus or a small fixed cap like 8) acquired at the top of handle_mint after the auth gate; over-cap requests return 503 + Retry-After. This caps peak Argon2 working set at permits × 64 MiB regardless of connection count. (3) Optionally apply tower::limit::ConcurrencyLimitLayer / a per-secret token bucket on internal_pat::router() (internal_pat.rs:242) so the internal surface carries its own in-app rate cap rather than relying solely on the repo-invisible CF WAF rule. The root critical (leaked shared-secret → any-tenant admin mint) is tracked separately (F4) and is the real fix priority — rotate/scope CORELINK_INTERNAL_AUTH_KEY and tighten its blast radius.
