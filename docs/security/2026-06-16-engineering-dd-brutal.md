## 2. Deal-Breakers (must-fix before close)

These are not "tech debt." They are representations in the data room that the code contradicts. Each must be remediated *or* the corresponding commercial claim struck from reps & warranties before signing.

**DB-1 — Storage quota enforcement is a no-op.** You sell 10GB→2TB tiered caps. **Nothing in production ever increments `tenant_storage_state.bytes_used`** — the column the Worker's quota gate sums. The reservation engine that would do it (`check_and_reserve`/`commit_reservation`) has zero callers, and `commit_reservation` is itself a documented no-op that "relies on a caller" that doesn't exist. The cap can never trip. *Every paying customer can store unlimited bytes.* This is both a revenue-integrity and a direct-COGS hole. **Fix:** atomic `bytes_used += size` on the durable write path + an end-to-end "Free tenant over 10GB is rejected" test. Until then, storage tiers cannot be advertised.

**DB-2 — Audit chain is fake on every paid adapter surface.** All six production adapter routers (cargo/npm/pip/brew/oci) construct `InMemoryAuditEmitter` — a type explicitly documented as a *test sink* — outside any `cfg(test)` guard. The "append-only Merkle audit chain (RFC-2119 MUST)" compliance claim is **false for the entire adapter surface**: nothing reaches the chain, and the unbounded `Vec` is a slow OOM on a long-lived 4GiB container. **Fix:** wire the real D1-backed chained emitter; add a build-time deny on constructing `InMemory*/Mock*/Fake*` outside tests. Until then, scope the compliance claim to exclude adapters in all DD reps.

**DB-3 — One internet-reachable shared secret = total platform takeover.** `POST /_internal/pat/mint` is served by the *public* edge Worker with no WAF / CF Access / IP allowlist — gated only by a constant-time compare against a single shared `CORELINK_INTERNAL_AUTH_KEY`. It mints a full `SCOPE_ADMIN_ALL` PAT for *any attacker-supplied tenant_id*, with zero per-tenant authorization. The **same** secret gates the GDPR erasure orchestrator and per-hash data-destruction endpoints. One leaked string = mint admin tokens for every tenant **and** irreversibly erase any tenant's data. The code itself documents this as known-and-unfixed. **Fix (all three, pre-close):** (1) move these routes to a Worker-to-Worker Service Binding so they are not internet-addressable; (2) split into per-consumer secrets; (3) require the caller to prove authority over the named tenant. The Service-Binding move is a config change, not a rewrite — there is no excuse for it being open at launch.

**DB-4 — "Network-effect dedup moat" does not exist in production.** The valuation thesis is "more tenants → fuller shared cache → cheaper for all." But CAS objects are keyed by *per-tenant prefix*, so the same blob from two tenants is stored at two keys — **no cross-tenant dedup, no shared cache, no network effect.** This is provable from the erasure adapter: it blindly LISTs-and-DELETEs a tenant's prefix with *no refcount check*, which is only safe *because* nothing is shared. The cross-tenant dedup tables are documented as "un-written in prod." **You cannot have both blind prefix-delete erasure and a dedup moat — the shipped code has chosen no-moat.** Either the architecture narrative is rewritten to match reality, or the dedup+refcount work is funded as a real (multi-quarter) deliverable and re-underwritten. This one should reset the valuation.

## 3. Major Risks

- **Capacity ceiling at 20 tenants (R-1).** One container per tenant DO, prod `max_instances=20`. The **21st concurrently-active tenant 503s.** A product "sold to thousands of SMBs" can serve ~20 live workloads at once. The container is already logically multi-tenant (per-tenant CAS namespacing + per-request PAT resolution), so a shared pool is achievable — but it is unbuilt and unmodeled (cold-start storm untested). This is the #1 capacity SLO and it has never been load-tested.

- **Storage grows forever; COGS leaks monotonically (R-2).** `corelink-gc` (mark/sweep/delete, ~3.7k LOC) is **dead code** — no src dependency, no caller, no prod cron; the D1 backend is "deferred to a ship gate." Eviction is likewise unwired. A content-addressed store that never GCs makes R2 cost unbounded — directly attacking the 80% margin thesis. (Also: the GC's pagination is OFFSET-based — O(n²) — and must go keyset before it runs.)

- **Bus factor = 1, with the keys to the kingdom on one Mac (R-3).** 2,265 of ~2,280 commits are one human. The **only copy** of 31 production secrets lives in one gitignored plaintext file (`.env.local`) on the founder's Mac — no vault, no escrow, no rotation automation. That **same Mac is the entire CI fleet** (self-hosted, already crash-prone at load 336, disk 98–100%, corrupting the shared cargo cache). One person owns all domain knowledge, the sole prod-credential copy, and the build/deploy infra simultaneously. **Acceptance test for close:** a *second* engineer independently executes a full deploy + secret rotation from the runbooks.

- **Secret concentration & over-privileged tokens (R-4).** Among the 31 secrets: zone-wide superadmin CF tokens (one of which can *mint* further R2 credentials), the `PAT_SIGNING_KEY` HMAC root for all tenant auth, Stripe/Clerk live keys. No managed store, no break-glass, no tested restore.

- **Auth root is a single HMAC key with no second factor on the native plane (R-5).** Argon2id second-factor exists *only* on adapter paths. Native CAS/AC/Bazel/Turbo trust a Worker-injected `x-corelink-tenant-id` header. **Leak `PAT_SIGNING_KEY` → forge a PAT for any tenant on the entire native surface, no DB touch.** Combined with R-4 (the key is in the plaintext file), the auth root is dangerously concentrated.

- **Compliance theater (R-6).** (a) Admin-UI ships a full "Withdraw consent" dashboard calling `/v1/consent*` endpoints **that have no backend and no `consent_ledger` table** — a law-mandated withdrawal that silently no-ops; E2E tests mock the backend so CI is green. (b) R2 buckets carry **no `jurisdiction` restriction** — "EU residency" is a string prefix in an object key, not Schrems-II-enforceable; real prod CAS is a single global bucket. (c) The DSR 24h verify sweep is documented **inert**, and Stripe erasure asserts "VerifiedComplete" without re-reading Stripe. Any of these is a regulatory-misrepresentation liability if sold as shipped.

- **Billing correctness — charge-then-serve, no refund (R-7).** The $-ceiling debits *before* the op runs; failed requests (your 503s) still permanently consume the ceiling, with no release path. A backend hiccup + client retries can drive a *paying* tenant to 402 lockout on requests that delivered zero value — self-inflicted DoS. Plus the monthly request-quota is a documented no-op and **Free-tier requests are entirely unmetered** — unbounded compute/egress on the zero-revenue tier.

- **Latent reliability traps (R-8).** The container reaches D1 over the *public* `api.cloudflare.com` REST API (not a binding) — ≥2 internet round-trips per cache hit, contradicting the "co-located, service-binding-only" architecture claim — and that HTTP client has **no timeout**, bridged through `block_in_place`+`block_on`, so a stalled D1 can pin runtime threads unbounded and wedge the container. Much of the "CI/prod flakiness" attributed to the Mac may partly live here.
