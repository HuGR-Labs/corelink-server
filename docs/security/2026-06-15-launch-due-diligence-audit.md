# CoreLink Pre-Launch Due-Diligence Audit — 2026-06-15

> 82 agents · 131 raw findings · 22 CRITICAL/HIGH adversarially verified · 21 confirmed. Target: integ/post-login-backlog (main + #269).

## VERDICT: NO-GO

NO-GO until the two CRITICALs and the top tier of HIGHs are fixed. The two CRITICALs each break a load-bearing launch path with no workaround: (1) the region fan-out has no termination guard, so EVERY non-IAD tenant gets a 503 on every request — the data-residency product (a headline launch promise) is 100% non-functional for exactly the tenants it exists to serve, and it passes IAD-only smoke tests so it would ship silently broken; (2) a transient PAT-mint failure during signup leaves a permanent PAT-less orphan tenant that never self-heals and emits no error — a launch-day money-path/onboarding break where a paying signup can never authenticate to the cache. Either alone is disqualifying.

Beyond the CRITICALs, several HIGHs cluster into systemic fail-open/feature-dead patterns that are individually launch-relevant: the F9 erasure-salt fail-closed guard is inert because ENVIRONMENT is never bound on the signup-worker (silent GDPR/LGPD unlinkability breach the moment ERASURE_SALT_KEY is unset — most likely at a fresh launch); the OCI registry is dead in prod due to the CORELINK_/HUGR_ token-key name drift while a green deploy gate hides it; the Turbo R2KvStore degrades to a PUBLIC predictable cross-tenant prefix instead of failing closed like CAS/AC; the data plane has NO request-rate limiting and its sole backstop is a repo-invisible CF zone rule that already self-DoS'd the SPA; the admin-ui CSP nonce never reaches Next.js so enforce-mode CSP blocks the app's own hydration scripts (admin-ui broken in prod); two HIGHs sell residency/Schrems-II/BYOK guarantees in a signed DPA that the launched data plane cannot deliver (contractual/GDPR-Art.28 exposure); the Bazel REAPI surface rejects every genuine SHA-256 Bazel upload with 422 (a sold surface that is non-functional). The PAT signing-key has no rotation overlap, so the documented incident-response (rotate on compromise) is a self-inflicted fleet-wide auth outage. And the tenant-isolation degraded-prefix path fails OPEN to a shared keyspace rather than closed.

These are not deep-architecture rewrites — the bulk are bounded, surgical fixes (bind one var, reconcile one secret name, add one termination guard, propagate one header, fail-closed one branch, fix one idempotency predicate). Recommendation: this is GO-WITH-FIXES in spirit but the must-fix set still contains two open CRITICALs and a payment/auth/compliance break, so the honest verdict TODAY is NO-GO. It converts to GO once the prioritized blocksLaunch:true items below are merged and verified (notably with a non-IAD regional-worker test and an auth-key-present transient-mint-failure test, the exact cases existing tests miss).

## Confirmed CRITICAL/HIGH (survived 2-vote adversarial refutation)

### 1. [HIGH] No signing-key rotation support — rotating PAT_SIGNING_KEY instantly invalidates every live PAT (fleet-wide auth outage)
- **Area:** PAT minting + signing key (mint() in corelink-pat, /_internal/pat/mint route, signup-worker issuePat, Worker native-plane PAT verify, container adapter PatVerifier, scope mapping, Argon2id)
- **File:** `crates/corelink-pat/src/verify.rs:46-90 + crates/corelink-pat/src/sig.rs:64-78 + worker/src/index.ts:748-755 + crates/corelink-container/src/routes/internal_pat.rs:433-438`
- **Impact:** types.rs:216 and key_management.md document a '24h rotation with overlap' but the code implements none. Any rotation of PAT_SIGNING_KEY (the documented incident response to a key compromise, and the cadence the docs claim) instantly breaks authentication for ALL self-serve customers' PATs across every cache surface, with zero overlap window — a self-inflicted fleet-wide outage. At launch the key effectively cannot be rotated without breaking every customer.
- **Fix:** Support an overlap set in verify: read PAT_SIGNING_KEY (current) + optional PAT_SIGNING_KEY_PREV/_NEW, and in verify_hmac_only/verify_with_hash and the Worker's verifyPatHmac try each key (constant-time over the small fixed set) so a mint under the old key still validates during the overlap window. Use the persisted signing_key_id to select the key. Until implemented, document loudly that rotation = re-mint-all and soften the '24h rotation' claim in types.rs:216 and key_management.md.

### 2. [HIGH] Degraded-prefix fallback produces a SHARED (not isolated) namespace and the storage op still PROCEEDS — empty prefix collapses all non-UUID tenants into one keyspace
- **Area:** Tenant isolation on storage keys (R2 prefix derivation / TDK; cas.rs + ac.rs r2_key / r2_list_prefix / cursor)
- **File:** `crates/corelink-container/src/storage/r2_s3.rs:419-441 (and r2_key:376-378, AC r2_key:966-969, r2_list_prefix:701-704)`
- **Impact:** If any non-UUID tenant id ever reaches the storage path, tenant isolation collapses for those tenants: cross-tenant read/overwrite/delete and full cross-tenant LIST under the shared empty prefix — a compliance/data-isolation breach. Reachability today is gated by the precondition that production tenant ids are canonical UUIDs (D1 schema declares `tenant_id UUID`; signup uses crypto.randomUUID; the Worker forwards the D1 PAT row's tenant_id). SQLite/D1 does not enforce UUID text format, so a malformed/legacy/seed row, a future code path that injects a non-UUID resolved tenant, or any regression in the upstream invariant silently degrades to the shared keyspace instead of failing closed.
- **Fix:** Make the degraded case fail CLOSED at the storage boundary, not just log. Have `tenant_prefix` (prod cfg) return `Result`/`Option` and have `r2_key`/`r2_list_prefix` propagate a hard error (mapped to 503/500), so a non-derivable tenant NEVER touches R2 with an empty prefix. At minimum, assert non-empty prefix in `blob_key`/`r2_key` and abort. Also correct the misleading 'isolated' comment to 'SHARED' and add a regression test that a non-UUID tenant on the prod path errors rather than writing under `<region>//`.

### 3. [HIGH] Bazel REAPI CAS surface uses BLAKE3 hash verification but REAPI v2 (and real Bazel clients) use SHA-256 — every genuine Bazel CAS upload is rejected with 422
- **Area:** Bazel REAPI v2 surface (crates/corelink-container/src/routes/bazel_v2.rs + crates/corelink-bazel-bridge/* + the production R2 CAS/AC handlers it delegates to)
- **File:** `crates/corelink-bazel-bridge/src/digest.rs:11 (doc 'SHA-256') vs crates/corelink-hash/src/digest.rs:30-31 (BLAKE3) enforced at crates/corelink-container/src/storage/r2_s3.rs:478-482,642-658`
- **Impact:** The advertised feature ('point --remote_cache=https://corelink-api.humangr.com/bazel/v2 and get distributed cache') is non-functional for any real Bazel client. CAS writes from genuine Bazel (SHA-256 digests) are universally rejected; even findMissingBlobs would report everything missing and uploads then 422. This is a correctness/launch-quality defect on a sold surface, not a security hole. (The InMemory dev handler hides it because tests use fake_hash for BOTH the claimed hash and verification, so the round trip passes in CI but not against real Bazel.)
- **Fix:** Decide the canonical CAS digest algorithm for the Bazel surface. REAPI v2 mandates the client-selected digest function (SHA-256 is the Bazel default). Either (a) compute SHA-256 in verify_content_hash for blobs that arrive via the Bazel route (route blobs through a SHA-256-keyed namespace), or (b) honor the REAPI digest-function negotiation and key/verify per algorithm. At minimum fix the digest.rs doc which currently claims SHA-256 while the system enforces BLAKE3, and add an integration test that uploads a real SHA-256-digested blob end-to-end through /bazel/v2 against the R2 (or a BLAKE3-faithful) handler rather than fake_hash.

### 4. [HIGH] Turbo R2KvStore does NOT fail closed when R2_TDK_HEX is absent/malformed — silently degrades to a PUBLIC, predictable, 16-char-truncated tenant prefix (cross-tenant co-residence risk), unlike CAS/AC which 503
- **Area:** Turborepo v8 + R2KvStore (crates/corelink-container/src/routes/turbo_v8.rs + storage/r2_kv.rs)
- **File:** `crates/corelink-container/src/storage/r2_kv.rs:106-115,154,175-186`
- **Impact:** R2_TDK_HEX is the SAME secret that gates CAS/AC isolation (matrix row #143). If it is ever unset, malformed, or mis-rotated on the container, CAS and AC fail loud (503) and refuse public co-residence, but the Turbo cache silently keeps serving with a PUBLIC, predictable 16-char prefix. pad16 truncates a UUID tenant to its first 16 chars; UUIDv7 tenants' first 16 chars are timestamp(ms)+version+partial-rand, so two tenants onboarded in the same millisecond can collide -> one tenant's Turbo build artifacts become readable/overwritable by another (cross-tenant cache leak + poisoning). This is a defense-in-depth gap the rest of the storage layer explicitly closes; the Turbo surface is the lone exception.
- **Fix:** Make the Turbo store match CAS/AC: (1) gate `pad16` behind `#[cfg(test)]`; (2) on the production path, when tdk is None or the tenant is not a parseable UUID, refuse to build / return an Internal error / empty-isolated prefix + loud error rather than a public predictable prefix; (3) make `build_r2_kv_from_env` fail closed (return Some(Err(..))) when R2 creds are present but R2_TDK_HEX is unset/invalid, mirroring build_r2_cas_handler_from_env, OR gate the turbo_v8 router mount on TDK presence in routes.rs:406-418 the way cas_erase is gated in main.rs:357-368.

### 5. [HIGH] OCI manifest PUT has NO body-size limit — unbounded heap allocation DoS
- **Area:** sccache (WebDAV / cargo HTTP build-cache adapter) + OCI registry (/v2 + /token)
- **File:** `crates/corelink-adapter-host/src/oci/server/handlers.rs:391`
- **Impact:** An authenticated tenant (any valid push-scoped PAT) can PUT a multi-GB body to `/v2/<repo>/manifests/<ref>`; the adapter buffers the entire body into a single Vec (`to_bytes(.., usize::MAX)`) and then serde-parses it, before the schemaVersion check ever runs. The OCI registry runs in ONE shared `_oci` container/DO for ALL tenants, so a handful of concurrent large-manifest PUTs can OOM the shared process and take the registry down for every tenant. The blob path was explicitly hardened against exactly this (F25 + 5 GiB cap + cumulative counter); the manifest path was left open.
- **Fix:** Apply a manifest-specific size cap (e.g. a few MiB — real OCI manifests are KBs) BEFORE buffering/parsing: replace `to_bytes(body, usize::MAX)` with `to_bytes(body, MAX_MANIFEST_BYTES)` and map the overflow to 413, mirroring the blob oversize handling. Add a `manifest_size_limit_bytes` to OciAdapterConfig.

### 6. [HIGH] OCI upload buffers are in-memory, per-session up to 5 GiB, no global cap and no abandoned-session reaper — shared-process memory exhaustion
- **Area:** sccache (WebDAV / cargo HTTP build-cache adapter) + OCI registry (/v2 + /token)
- **File:** `crates/corelink-container/src/routes/oci.rs:96`
- **Impact:** Worst case per tenant ≈ 4 × 5 GiB = 20 GiB resident heap; with N tenants this is N × 20 GiB with no global bound. A tenant can also permanently pin up to ~20 GiB by opening 4 sessions, PATCHing data near the limit, and never sending PUT/cancel (no reaper reclaims them until process restart). All OCI traffic shares one container, so this is a cross-tenant availability DoS from a single authenticated tenant. The code's own doc (oci.rs:88-95) acknowledges the N×5 GiB growth but the chosen cap (4) does not actually bound the bytes.
- **Fix:** Add (1) a global open-session and/or global in-flight-bytes ceiling across all tenants, (2) an abandoned-session reaper keyed on last-touched timestamp (sweep sessions idle > token TTL), and (3) consider a far smaller per-session interim cap or streaming-to-R2 instead of full in-memory buffering for the 5 GiB layer case.

### 12. [HIGH] Per-request CSP nonce never reaches Next.js → inline hydration scripts emitted nonceless and blocked under enforce-mode CSP
- **Area:** CSP + security headers (apps/admin-ui) — post-fix re-audit
- **File:** `apps/admin-ui/middleware.ts:49-50 (+ node_modules/next/dist/server/app-render/app-render.js:108-109)`
- **Impact:** In production (CSP_ENFORCEMENT defaults to enforce; NODE_ENV=production also resolves to enforce), Next's App Router dynamic pages (all routes are `export const dynamic = "force-dynamic"`) emit inline RSC-data/hydration scripts WITHOUT the nonce, which enforce-mode CSP blocks → React hydration data never loads → the admin-ui fails to hydrate / breaks for authenticated and signup flows. Add a render-path test asserting served HTML inline scripts carry the matching `nonce=`.

### 13. [LOW] next.config headers() emits a static CSP with a hardcoded, publicly-known nonce literal ('nonce-STATIC') on every path
- **Area:** CSP + security headers (apps/admin-ui) — post-fix re-audit
- **File:** `apps/admin-ui/next.config.ts:15,67-78`
- **Impact:** If the static-CSP header is ever the policy a browser honors for an HTML document (duplicate-header scenarios, or any response path that skips middleware), the nonce-based XSS protection is fully defeated: an injected inline script with `nonce="STATIC"` executes because the nonce is a public literal. At best (duplicate headers) it produces an unsatisfiable intersection (`nonce-REAL` ∩ `nonce-STATIC`) that blocks even legitimately-nonced scripts. - **Fix:** Do NOT emit a CSP containing a fake/literal nonce from next.config. For paths that genuinely bypass middleware there is no inline script needing a nonce, so emit a static CSP WITHOUT any nonce token (drop the `'nonce-...'` source from script-src for the static fallback, or omit the CSP entirely from next.config and rely solely on middleware which now covers all matched paths). Ensure only ONE Content-Security-Policy header is emitted per document response.

### 14. [HIGH] Data-plane (CAS/AC/Bazel/Turbo/OCI/cargo/npm/pip/brew) has NO request-rate limiting — only storage quota + a repo-invisible CF zone rule
- **Area:** Rate-limiting / DoS surface
- **File:** `crates/corelink-container/src/routes.rs:409-418 (and 458-532)`
- **Impact:** Any single authenticated PAT (self-serve $15/mo Solo tenant) can issue unbounded requests/sec against CAS read/write, AC, Bazel REAPI v2, and Turbo endpoints. Back it with durable D1 (the session_exchange.ts INSERT...ON CONFLICT...RETURNING count pattern) so it survives container cold-starts. Do NOT rely on the repo-invisible CF zone rule as the sole defense.

### 18. [CRITICAL] Transient PAT-mint failure leaves a permanent PAT-less orphan tenant — idempotency check never re-issues the PAT
- **Area:** signup-worker tenant provisioning (apps/signup-worker/src/webhooks/clerk.ts + lib/d1.ts)
- **File:** `apps/signup-worker/src/webhooks/clerk.ts:763-775 (idempotency check) + :638-663 (write ordering) + :972-973 (mint throw)`
