# E2E CI — Scheduled Clerk + Stripe smoke against prod

**Created:** 2026-05-30
**Workflows:** `.github/workflows/e2e-clerk-signup.yml` + `.github/workflows/e2e-stripe-checkout.yml`
**Scripts (sealed — do not modify):** `scripts/e2e-clerk-signup.sh` · `scripts/e2e-stripe-checkout.sh`

---

## 1. Purpose

Two scheduled GitHub Actions workflows run programmatic end-to-end smoke tests against production every 6 hours. They exercise the full signup + billing chains without a browser:

| Workflow | Script | Chain under test |
|---|---|---|
| `e2e-clerk-signup.yml` | `e2e-clerk-signup.sh` | Clerk user create → signup-worker webhook → D1 tenant row → PAT mint → `/v1/users/me` |
| `e2e-stripe-checkout.yml` | `e2e-stripe-checkout.sh` | Stripe customer + subscription create → signed `checkout.session.completed` POST → signup-worker webhook → D1 `tenant_billing` `status=paid` |

Both scripts create real test objects, verify the chain, then clean up completely (idempotent).

---

## 2. Required GitHub repo secrets

Configure under **Settings → Secrets → Actions** in the `HuGR-Labs/corelink-server` repo.

| Secret name | Where to get it | Used by |
|---|---|---|
| `CLERK_SECRET_KEY` | Clerk Dashboard → API Keys → Secret keys | `e2e-clerk-signup.yml` |
| `STRIPE_SECRET_KEY` | Stripe Dashboard → Developers → API Keys (use `sk_test_...` key) | `e2e-stripe-checkout.yml` |
| `STRIPE_WEBHOOK_SECRET` | Stripe Dashboard → Developers → Webhooks → select endpoint → Signing secret (`whsec_...`) | `e2e-stripe-checkout.yml` |
| `CLOUDFLARE_API_TOKEN` | Cloudflare Dashboard → My Profile → API Tokens — must have `D1:edit` + `Workers Scripts:read` on the corelink account | both |
| `PAGERDUTY_ROUTING_KEY` | PagerDuty → Services → CoreLink On-Call → Integrations → Events API v2 routing key | both |

### Optional repo variable

| Variable name | Default | Effect |
|---|---|---|
| `STRIPE_PRICE_ID_STARTER` | (none — script lists prices) | Pins the Stripe recurring price used for the test subscription; avoids a listing API call per run. Set to `price_...` from Stripe test-mode. |

## 3. Schedule

| Workflow | Cron | UTC times |
|---|---|---|
| `e2e-clerk-signup.yml` | `0 */6 * * *` | 00:00, 06:00, 12:00, 18:00 |
| `e2e-stripe-checkout.yml` | `30 */6 * * *` | 00:30, 06:30, 12:30, 18:30 |

The 30-minute offset ensures both workflows do not compete for the same D1 write window simultaneously.

Both workflows also support **manual dispatch** (`workflow_dispatch`) for ad-hoc runs after deploys or incidents.

---

## 4. Failure notification

On failure, both workflows:

1. **Open a GitHub issue** tagged `e2e-regression` + `sev-1` with a direct link to the failing run and step-by-step triage hints.
2. **Page on-call via PagerDuty** Events API v2 with `dedup_key = e2e-<workflow>-<run_id>` (prevents duplicate pages if the step is retried).

## 5. On-call runbook

### 5.1 Initial triage (≤5 min)

1. Open the failing GitHub Actions run link from the PagerDuty alert or the GitHub issue.
2. Find the step that failed: `Run Clerk signup E2E` or `Run Stripe checkout E2E`.
3. Expand the step log and locate the first `[FAIL]` / `ERROR:` line.

### 5.2 Clerk signup failure triage

| Failing stage | Likely cause | Action |
|---|---|---|
| Stage 1 — Clerk user create | `CLERK_SECRET_KEY` rotated, expired, or wrong environment (live key used against test) | Verify key in Clerk Dashboard → API Keys; rotate secret in GitHub Settings |
| Stage 2 — D1 tenant row timeout (30 s) | `CLERK_WEBHOOK_SECRET` mismatch (svix signature verify fails) OR signup-worker not deployed OR D1 binding broken | Check `wrangler tail corelink-signup --env prod`; verify Clerk webhook → endpoint signing secret matches `CLERK_WEBHOOK_SECRET` in Worker |
| Stage 3 — PAT row missing | Signup orchestration incomplete — PAT mint step failed | Check D1 `signup_orchestration` table for the `clerk_user_id`; look at `outcome` column |
| Stage 4 — Clerk publicMetadata missing | Clerk API returned 4xx during metadata patch in signup-worker | Check Worker logs; verify `CLERK_SECRET_KEY` has `users:write` scope |
| Stage 5 — `/v1/users/me` non-200 | corelink-api Worker not deployed or PAT auth regression | Check `wrangler tail corelink-api --env prod`; verify `CF-Worker` routing |

### 5.3 Stripe checkout failure triage

| Failing step | Likely cause | Action |
|---|---|---|
| Step 1 — tenant_billing missing | D1 migrations not applied or BILLING_DB binding broken | Run `wrangler d1 execute CONFIG_DB --env prod --remote --command "SELECT name FROM sqlite_master"` and verify `tenant_billing` present |
| Step 3 — customer create | `STRIPE_SECRET_KEY` invalid or test-mode disabled | Check key in Stripe Dashboard → Developers → API Keys |
| Step 4 — subscription create | No recurring price in Stripe test mode | Set `STRIPE_PRICE_ID_STARTER` repo variable or create a recurring price in Stripe test mode |
| Step 5 — webhook 400 | `STRIPE_WEBHOOK_SECRET` mismatch between `.env.local` secret and Worker deployment | Verify secret in Stripe Dashboard → Developers → Webhooks → Signing secret; re-deploy signup-worker if needed |
| Step 5 — webhook 401/403 | Cloudflare WAF or Bot Fight Mode blocking the signed test POST | Check Cloudflare Dashboard → Security → WAF for blocked requests; the script sets `User-Agent: Stripe/1.0` |
| Step 5 — webhook 503 | `STRIPE_WEBHOOK_SECRET` not set in the deployed Worker environment | Run `wrangler secret list --env prod` and confirm `STRIPE_WEBHOOK_SECRET` present |
| Step 6 — D1 poll timeout | Webhook handler not writing to BILLING_DB | Check `wrangler tail corelink-signup --env prod`; verify `BILLING_DB` binding in `wrangler.toml` |

### 5.4 Cleanup on stuck test data

If the workflow dies mid-run and cleanup didn't complete:

**Clerk orphan user:**
```sh
# List recent test users
curl -sS -H "Authorization: Bearer $CLERK_SECRET_KEY" \
  "https://api.clerk.com/v1/users?email_address=e2e-test-%" | jq '.[].id'
# Delete by user_id
curl -sS -X DELETE -H "Authorization: Bearer $CLERK_SECRET_KEY" \
  "https://api.clerk.com/v1/users/<user_id>"
```

**Stripe orphan customer:**
```sh
# List recent test customers
curl -sf "https://api.stripe.com/v1/customers?email=e2e-%40test.humangr.com&limit=5" \
  -u "$STRIPE_SECRET_KEY:" | python3 -c "import sys,json; [print(c['id']) for c in json.load(sys.stdin)['data']]"
# Cancel subscription + delete customer
curl -sf -X DELETE "https://api.stripe.com/v1/subscriptions/<sub_id>" -u "$STRIPE_SECRET_KEY:"
curl -sf -X DELETE "https://api.stripe.com/v1/customers/<cust_id>" -u "$STRIPE_SECRET_KEY:"
```

**D1 orphan rows:**
```sh
wrangler d1 execute CONFIG_DB --env prod --remote \
  --command "DELETE FROM tenant_billing WHERE stripe_customer_id LIKE 'cus_e2e_%'"
```

### 5.5 Escalation

- Two consecutive failures within 12 h → escalate to SEV-1 P1 incident.
- Any stage 2 (Clerk D1 timeout) OR step 6 (Stripe D1 timeout) failure → confirm with a manual `wrangler d1 execute` that D1 is reachable; if not, escalate immediately.

## 6. Rate-limit notes

- **Clerk Backend API:** 100 req/s per key. Each run uses ~5 requests. 4 runs/day per key is well within limits. If limits change, increase cron interval (minimum: hourly per `DO NOT run more frequently` comment in workflow).
- **Stripe test-mode API:** No documented hard rate limit for object creation in test mode. Each run creates 1 customer + 1 payment method + 1 subscription, then cancels and deletes all. Safe to run 4×/day.
- **Cloudflare D1:** Each run executes ~8 queries against `corelink-prod-d1` (Clerk) + ~4 queries against `CONFIG_DB` (Stripe). D1 free tier: 5M reads + 100K writes/day. Cron runs are well within limits.
