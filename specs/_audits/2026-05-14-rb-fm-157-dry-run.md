## 1. Scenario Injected

**Synthetic typosquat simulation:** attacker publishes `corelink-fake` on a
local crates.io clone (dev environment), visually similar to `corelink-server`.
Developer inadvertently runs `cargo add corelink-fake` in a test branch.

Simulation method (host-side):
1. Created a local `corelink-fake` crate fixture in a temporary registry
   (`/tmp/corelink-fake-registry/`) with version `0.1.0` and plausible metadata.
2. Added `corelink-fake = "0.1.0"` to `Cargo.toml` [dev-dependencies] in
   a test branch to simulate the typo add.
3. Ran `cargo update` to populate `Cargo.lock` with the new entry.
4. Opened a draft PR on the test branch to trigger lockfile diff review.

Note: No crates.io publish performed (per WI-S12-007 §6.2 anti-scope R-005:
"Use dev crates.io clone OR `cargo-publish-dry-run`"). The simulation validates
the detection layer, not the attacker's ability to publish.

## 5. Key Observation: cargo-deny Cannot Block crates.io Typosquats

This is the most important finding of the dry-run (expected, documented in WI spec):

- cargo-deny `[sources]` policy blocks crates from non-crates.io registries
  and git deps without pinned commit hash.
- A typosquatted crate published on crates.io itself passes cargo-deny sources policy.
- **Therefore:** the lockfile diff PR comment Action + CODEOWNERS mandatory
  supply-chain reviewer + SBOM DT new-component anomaly review are the three
  primary defences.
- Implication for on-call: **manual review is the last line of defence** for
  typosquatting. Automation provides the signal; human eyes close the gate.

Documented in RB-FM-157 v1.0.0 §Scenario + §Detecção.
