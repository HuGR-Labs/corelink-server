## 3. S-07 specific findings

- **INV-EVICT-SOFT-DELETE-FIRST canonical:** WI-S07-002 ships the
  eviction phase as soft-delete-first (sets `deleted_at`; NEVER R2
  DELETE direct); reuses S-06 GC grace period 72h. Re-upload within
  grace window correctly resurrects the blob via the existing
  `BlobMetaSoftDeleteStore::undelete` path (S-06 carry-forward). The
  INV-DEDUP-CONSISTENCY hot-fix path (write path lê tombstone_log +
  soft-block 24h re-write) is now enforceable because the S-07 dedup
  index `chunks` PK `(tenant_id, chunk_digest)` provides the canonical
  source of truth.
- **INV-EVICT-CASCADE-PREVENTED canonical (BLOB-scope per Lote
  10.7bis P0-8):** the pre-evict reachable check refuses if the blob
  is ref'd by active `ac_meta.blob_refs` via canonical `json_each` SQL
  idiom (inherited from S-06 reconcile). `prop_blob_only_scope`
  asserts the orchestrator has NO chunks-table dependency by type
  signature — chunks lifecycle is owned exclusively by S-06 GC via
  `chunks.refcount`.
- **Race-aware reachable check `<` evict / `>=` protect:** WI-S07-002
  mirrors S-06 INV-GC-004 strict-boundary semantic via
  `prop_evict_protect_if_re_referenced_strict_boundary`. Loosening to
  `<=` evict / `>` protect would be a data-loss bug pinned at the
  off-by-one boundary.
- **Dedup index idempotent re-upload behavior:** `prop_idempotent` +
  `prop_tenant_isolation` (10k iter) cover the canonical re-upload
  race scenario where a second worker writes the same chunk_digest
  during the grace window — the chunks PK + ON CONFLICT bumps refcount
  per Lote 10.7bis P0-1.
