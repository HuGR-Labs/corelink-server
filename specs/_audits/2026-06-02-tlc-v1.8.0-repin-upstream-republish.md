## Finding (root cause — legitimate upstream drift, NOT a compromise)

All 5 TLA+ model-check gates (`tla_check`, `tla_region_residency_check`,
`tla_runbooks_check`, `tla_dsr_erasure_check`, `tla_billing_check`) plus the
`nightly` TLC step hard-fail at the step **"Install pinned TLC v1.8.0 (SHA-256
verified)"**. They `curl -fsSL` `tla2tools.jar` from the official
`tlaplus/tlaplus` `v1.8.0` release and compare the SHA-256 against the pin from
ADR-0042 §A1 (pinned 2026-04-25). The downloaded hash no longer matches.

Root cause: the TLA+ project **re-published a freshly-built `tla2tools.jar` to
the same `v1.8.0` release tag** ("The Clarke release"). The jar is
**non-reproducible** — it embeds build timestamps — so the re-cut asset differs
byte-for-byte from the 2026-04-25 asset and therefore has a different SHA-256.
The pin is doing exactly its job (fail-closed on drift). This is:

- **NOT** a maintainer-key compromise, GitHub account takeover, or CDN MITM.
- **NOT** a macOS-runner / founder's-Mac issue — the asset bytes are identical
  on every platform, so it would fail identically on Linux.

1. **3× download, byte-identical.** Downloaded `tla2tools.jar` from the official
   v1.8.0 release three separate times. All three = **4357560 bytes**; `cmp`
   clean across every pair (jar1==jar2, jar2==jar3).
2. **Two independent hash tools agree.** GNU `sha256sum` and Perl/macOS
   `shasum -a 256` both produced
   `237332bdcc79a35c7d26efa7b82c77c85c2744591c5598673a8a45085ff2a4fb` for all
   three downloads — stable, zero variance.
3. **Confirmed official release asset** via
   `gh api repos/tlaplus/tlaplus/releases/tags/v1.8.0`:
   - Release name: "The Clarke release"; author `lemmy` (canonical TLA+
     maintainer); `published_at = 2026-05-26`.
   - Sole `tla2tools.jar` asset: `size = 4357560` (matches the download
     byte-for-byte), `content_type = application/zip`,
     `created_at`/`updated_at = 2026-05-26` — i.e. **re-cut on 2026-05-26**,
     AFTER the 2026-04-25 pin. This is the upstream re-publish event.
     `download_count` ≈ 37.8k (widely consumed; consistent with the real asset).
4. **CI cross-check.** The new hash prefix `237332bd…` matches the SHA observed
   STABLY across all 5 CI runners in the failing runs — the CI download and the
   local download see the same bytes.

## ⚠️ This WILL recur — permanent fix: vendor the jar

Because the jar is non-reproducible, **any** future re-cut of a TLA+ release
(even to the same tag) breaks this pin again and forces another re-pin ceremony.

**Recommended permanent fix — vendor the verified `tla2tools.jar`:** store the
exact verified bytes ourselves (R2 bucket, or Git LFS / an asset on our own
repo) and have CI fetch from the vendored copy under the pinned SHA, instead of
`curl`-ing GitHub's mutable release URL each run. Benefits:

- Removes the upstream **mutable-tag** dependency entirely — CI stops breaking on
  upstream re-publishes.
- **Hardens** the original threat model: a future malicious re-cut to the tag
  could no longer reach CI.
- Lets us **single-source** the SHA literal (today it is replicated across 6+
  workflow files + a shell script — see follow-ups), reducing re-pin toil and
  drift risk.
