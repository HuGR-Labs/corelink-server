# WP-5.2 mutation testing baseline — DEFERRED until post-code-freeze

## §1 Decision

**Mandate (2026-05-27, user):** *"nao adianta rodar isso antes de freezar
o codigo irmao"* — no point running mutation testing before code freeze.

**Action taken:** stopped the in-flight cargo-mutants byok run after the
hash crate completed; killed the cargo-mutants process; committed this
followup. The hash crate baseline (97.22% kill-rate, matching prior) is
preserved in the SEAL audit trail; byok + audit-chain are deferred.

## §2 Rationale

Mutation testing produces a kill-rate baseline that is **only meaningful
relative to a frozen codebase**. Running it during active development
churn (Wave 32 Phase B-I deploy work, Wave 33-36 absorbed crates still
settling, Phase 4 customer-driven feature work coming up) is wasted
effort because:

1. Each new commit potentially invalidates surviving mutants (a code
   change may move/delete the line targeted by a surviving mutant).
2. Each new commit may add NEW surviving mutants that aren't visible
   until re-run.
3. The cost is high (~36 hours for `corelink-byok` alone @ 725 mutants
   × ~3 min average; `corelink-audit-chain` not yet measured but
   similar order of magnitude).
4. The benefit (catching test-suite gaps) only banks on stable code.

## §3 Re-trigger condition

Run WP-5.2 in full when ONE of these is reached:

- **Wave 32 Phase I sign-off SEALed** — corelink-prod-deploy-v1 tag
  cut; codebase freezes for the GA release cadence.
- **First paying customer onboarded** — code freeze becomes implicit
  because we now have a customer to break.
- **2026-Q3 quarterly engineering review** — even if neither of the
  above happens, schedule the full sweep ahead of any external audit.
